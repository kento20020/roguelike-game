## 1. ゲームコンセプト

### 1.1 コアコンセプト

> **「どの敵を選ぶかが未来を変える、確率で削り合うフロア制ローグライト」**

- 分岐するノードマップから**次に戦う敵を選ぶ**意思決定がゲームの核
- 倒した敵によって次に戦える敵がアンロックされ、**選択の連鎖**が生まれる
- 戦闘は確率ベース。攻撃するたびに敵が確率で反応し、**結果はロールで決まる**
- プレイヤーはHPをどれだけ温存して先に進めるかを**常に計算する**

### 1.2 ゲームの目的

カジノタワーの各階層にいる「ゲート（胴元の関門）」を通過して上の階層へ登り続けること。
5フロアのゲートを全て突破して頂上に到達すれば**クリア**。HP0でゲームオーバー（パーマデス）。

### 1.3 プレイヤーの動機（v1.0確定）

> **「カジノタワーの頂上に待つ"全てを賭けた一勝負"を目指して登り詰める」**

この一文がフレーバーテキスト・死亡/クリア画面・コピーライティング全体の軸になる。

> **テーマ転換（v1.0）**：当初の「地下カジノに潜る」から「カジノタワーを登り詰める」へ変更。UI描画が下から上（row1が画面下、ゲートが画面上）のSlay the Spire型になったことに合わせ、物語も「登る」で一貫させた。

## 2. ゲームループ

### 2.1 マクロループ（ラン間）

```
ゲーム開始
  → [ラン] 1Fから開始 → 探索・戦闘・ビルド構築 → 5Fクリア or HP0
  → クリア時: 恒久強化ポイント（+1）獲得 → 数値強化に割り振り
  → 次ランへ（恒久強化の分だけ有利な状態でスタート）
```

**win-to-progress**：死亡では恒久強化ポイントは得られない。クリアのみが積み上がる。

### 2.2 ミクロループ（ラン内：1フロア）

```
フロア開始
  → マップ表示（ツリー構造。row1の3体のみ選択可能）
  → ノード選択 → phase遷移して「戦闘/宝箱/回復/ゲート」を解決
  → 解決後: アンロック発生 → 次ノードが選択可能になる
  → ゲートを通過 → 次フロアへ
```

## 3. デザインの3本柱

**① 意味のある選択（Meaningful Choices）**
全ての選択肢にトレードオフを持たせる。「とりあえず強い1択」を作らない。

**② 公平なランダム性（Fair Randomness）**
ランダム性は「新鮮さ」のため、公平性は「意思決定の納得感」のため。運だけで死なせない。

**③ 知識が報われる（Knowledge is Power）**
キャラは死んでもプレイヤーの理解は蓄積する。上達実感を最重視する。

## 4. フロア構造とアンロック連鎖

> **描画方向（v1.0確定）**：ツリーは**下から上へ**描画する（row1が画面下、ゲートが画面上）。プレイヤーは画面下のrow1から選び、上のゲートへ登り詰める（Slay the Spire型）。データ構造の進行（row1→row2→gate）は変わらず、TreeCanvasのy座標を反転するだけ。ロジックには一切影響しない。

### 4.1 ツリー形状（全フロア）

| フロア | 形状 | row1 | row2 | row3 | ゲート経路 |
|--------|------|:----:|:----:|:----:|:---------:|
| 1F | 形B [3, 3] | 3体 | 3体 | — | 1本（固定チュートリアル） |
| 2F | 形A [3, 4] | 3体 | 4体 | — | ≥2本 |
| 3F | 形C [3, 5] | 3体 | 5体 | — | ≥2本 |
| 4F | 形C [3, 5] | 3体 | 5体（抽選） | — | ≥2本 |
| 5F | 形D [3, 4, 3] | 3体 | 4体 | 3体 | ≥2本 |

> **5Fゲート1本問題対策**：形Dではrow3（3体）のうち最低2体がゲートへの有効経路を持つことを必須とする。

### 4.2 アンロック連鎖ルール（v0.7確定：ハイブリッド型）

**基本原則：**
- **多親ノード**：隣接する2体の上位ノードから解放される → ゲートへの有効ルート
- **単親ノード**：1体の上位ノードのみから解放される → 行き止まり（dead-end）。宝箱・回復のみ配置

#### 形A [3, 4] のマッピング

```
row1:   [L]      [M]      [R]
         │ ╲    ╱ │ ╲    ╱ │
         │  ╲  ╱  │  ╲  ╱  │
row2:  [A]   [B]    [C]   [D]

A = L のみ      → 単親 dead-end（宝箱/回復）
B = L + M       → 多親（ゲートルート）
C = M + R       → 多親（ゲートルート）
D = R のみ      → 単親 dead-end（宝箱/回復）
```

#### 形B [3, 3] のマッピング（1F）

```
row1:   [L]    [M]    [R]
         │ ╲   ╱│╲   ╱ │
row2:  [A]   [B]    [C]

A = L のみ      → 単親 dead-end（反射mod確定配置：チュートリアル用）
B = L + M       → 多親（ゲートルート）
C = M + R       → 多親（ゲートルート）
```

#### 形C [3, 5] のマッピング

```
row1:    [L]       [M]       [R]
          │ ╲     ╱ │ ╲     ╱ │
row2:  [A]  [B]    [C]    [D]  [E]

A = L のみ      → 単親 dead-end
B = L + M       → 多親（ゲートルート）
C = M のみ      → 単親 dead-end（中央の宝箱/回復）
D = M + R       → 多親（ゲートルート）
E = R のみ      → 単親 dead-end
```

#### 形D [3, 4, 3] のマッピング（5F）

```
row1:   [L]    [M]    [R]
         │╲    ╱│╲    ╱│
row2:  [A]  [B]   [C]  [D]
         │ ╲  ╱ │ ╲  ╱ │
row3:    [X]    [Y]    [Z]

row1→row2: 形Aと同じ（A=単親, B=多親, C=多親, D=単親）
row2→row3:
  X = A + B       → 多親（ゲートルート①）
  Y = B + C       → 多親（ゲートルート②）
  Z = C + D       → 多親（ゲートルート③）
  ※ X/Y/Z のうち最低2本がゲートへ接続（4.1の制約を満たす）
```

### 4.3 回復ノードの配置ルール

- row1とrow2の**間**にのみ配置（row2の単親dead-endに設置）
- **ゲート直前の最終rowには配置しない**
- 1フロアにつき最大**1個**
- 1Fには配置しない

### 4.4 体験タイプの段階導入

| フロア | 初登場する体験タイプ |
|--------|----------------|
| 1F | 削り合い、賭け |
| 2F | レース（ramp） |
| 3F | ずれ（evade） |
| 5F | カオス（複合） |

## 5. 情報開示レイヤー

| レイヤー | 取得条件 | 開示される情報 |
|---------|---------|-------------|
| **L1** | マップ全体から常に見える | ノードの存在、種類、ロック状態 |

## 7. ノード・イベント

### 7.1 敵ノード
- 選択した時点で**戦闘コミット**（キャンセル不可）→ `battle` phaseへ
- 倒すと先のノードがアンロック

### 7.2 宝箱ノード
- `treasure_preview` phaseへ → 「開封する / リロール（30G）」を選択
- リロール：開封前のみ。30G支払い再抽選
- 開封：`treasure_opened` phaseへ。mod確定
- **1宝箱＝1mod**、6種プールから置き戻し抽選、枯渇なし

### 7.3 回復ノード
- `heal` phaseへ → 大回復 / 小回復がランダム決定
- 使用は1回限り
- **回復量は固定値（v0.9確定）**：大回復 +30固定 / 小回復 +15固定
  - max_hpの%ではなく固定値。恒久強化でmax_hpが増える終盤ほど相対的に効果が薄くなる
- **回復sinkとは別系統（v1.0確定）**：回復ノード＝マップ上・無料・大小ランダム（運任せのドキドキ）／回復sink＝いつでも・有料・大小を選べる。「無料だが運任せ」vs「有料だが選べる」のトレードオフ。ギャンブルテーマと整合

### 7.4 ゲートイベント
- `gate_preview` phaseへ → ゲート保証sink使用可能（重ねがけ可）
- `gate_resolve` phaseで確率テーブルをロール

#### ゲートイベント結果テーブル（フロア別）

| 結果 | 1F | 2F | 3F | 4F | 5F | 被ダメ |
|------|:--:|:--:|:--:|:--:|:--:|------|
| 無傷通過 | 30% | 25% | 20% | 15% | 10% | 0 |
| 小ダメ通過 | 50% | 45% | 40% | 35% | 30% | max_hpの10% |
| 大ダメ通過 | 15% | 25% | 30% | 35% | 40% | max_hpの25% |
| 特殊 | 5% | 5% | 10% | 15% | 20% | 0（次フロア強化等） |

#### ゲート保証（v0.9確定：確率シフト型・重ねがけ可）

> **設計思想**：「確実に突破」はチートすぎるため廃止。ゲート保証は**大ダメの確率を削るだけ**で、確実な安全は買えない。

**基本ルール：**
- ゲート保証は**大ダメの確率の一部を、無傷・小ダメへ移す**
- **特殊（当たり）は減らさない**（保証を使っても一発逆転の目は残る）
- 同じゲートで**重ねがけ可能**。ただし効果半減＋コスト微増の二重ブレーキ

**重ねがけの数式：**
```
n回目のゲート保証:
  コスト     = 50G × (1.5)^(n-1)      ← コスト微増（1.5倍ずつ）
  大ダメ削減量 = 25% × (0.5)^(n-1)     ← 効果半減
  ※ 削った分は無傷・小ダメへ半々split（各50%）。特殊は維持（v1.0確定）
```

**5Fゲートでの重ねがけ例：**

| 回数 | この回のコスト | この回の削減量 | 大ダメ累計 | 累計コスト |
|:---:|:----------:|:---------:|:--------:|:--------:|
| 0回 | — | — | 40% | 0G |
| 1回 | 50G | -25% | 15% | 50G |
| 2回 | 75G | -12.5% | 約2.5% | 125G |
| 3回 | 約113G | -6.25% | ほぼ0%（必ず残る） | 238G |

効果半減で大ダメは収束して**必ず残り**、コスト微増で財布も尽きる。お金で完全な安全は買えない。

> ゲート保証（50G）使用時は§13.2のsink一覧にも反映。

## 8. 戦闘フロー

### 8.1 rampとevadeの区別

| 概念 | 性質 | 処理タイミング | データの在り処 |
|------|------|-------------|-------------|
| **ramp** | 状態量（毎ターン増加する蓄積ダメージ） | 攻撃前に状態更新 | 敵の `ramp_value` |
| **evade** | 行動テーブルの一結果（そのターン攻撃をかわす） | 行動ロール後に処理 | 行動テーブルの `weight` |

### 8.2 1ターンの流れ

```
プレイヤーが「攻撃する」を選択
  ↓
[ramp更新] レース系のみ: ramp_value += ramp_increment
  ↓
[stanceスロット] stance_multiplier = 1.0 固定（フェーズB用に予約）
  ↓
[与ダメ計算] player.attack × stance_multiplier → 敵HPに適用
  ↓
[行動テーブルを1回ロール] RNGストリーム2から weight比で抽選
      ├ "none"       → 被ダメ=0
      ├ "counter"    → 被ダメ=敵attack × counter_factor
      ├ "heavy_blow" → 被ダメ=敵attack × heavy_factor
      ├ "evade"      → 与ダメキャンセル + 被ダメ=0
      └ "ramp_hit"   → 被ダメ=現在のramp_value
  ↓
[mod適用] 重装甲の軽減・反射の追加ダメ・好機の追撃等
  ↓
[HP確認] 敵HP≤0 → 勝利 / プレイヤーHP≤0 → dead
  ↓
[ログ追記] 全ログ保持（§10.5）
```

### 8.3 行動テーブル全タイプ

| タイプ | 被ダメ | 特記 |
|--------|------|------|
| `none` | 0 | |
| `counter` | 敵attack × counter_factor（既定1.0） | 削り合い系の主行動 |
| `heavy_blow` | 敵attack × heavy_factor（既定1.8） | 賭け系。敵ごとに上書き可 |
| `evade` | 0（与ダメも0） | ずれ系の主行動 |
| `ramp_hit` | current_ramp_value | レース系のみ |

> **係数の扱い（v1.0確定：フォールバック設計）**：counter_factor / heavy_factor は config.json の全敵共通既定値（1.0 / 1.8）。敵が enemies.json で個別値を持てばそれを優先。コードは `enemy.get("heavy_factor", config["heavy_factor"])`。

**レース系の行動テーブル（v1.0確定・全7体共通）：**
```
ramp_hit: 60%   （蓄積値を放出）
counter:  30%   （反撃）
none:     10%
```

### 8.4 戦闘内意思決定（A案）

戦闘中のプレイヤー行動は「攻撃する」のみ。意思決定は100%マップ層。
フェーズB（スタンス選択）は将来追加。条件は§12.3に予約。

### 8.5 ダメージ式

```
与ダメ = player.attack × player.stance_multiplier
            ↑ stance_multiplierは複数ソースの乗算（v1.0確定）
            最終 = stance係数(将来) × attack_boost係数(使用時2.0) × …
            現在は通常1.0、攻撃ブースト使用時のみ次の1撃が2.0

被ダメ（counter）  = enemy.attack × counter_factor（既定1.0、敵ごと上書き可）
被ダメ（heavy）    = enemy.attack × heavy_factor（既定1.8、敵ごと上書き可）
被ダメ（ramp_hit） = enemy.ramp_value
被ダメ（evade/none）= 0
最終被ダメ = max(0, 計算被ダメ − 重装甲の軽減値)
```

**ramp_value（蓄積ダメージ）の計算（v1.0確定）：**
```
ramp_value(n) = base_initial(=5) + ramp_increment × (n − 1)
                    ↑ 全レース敵共通     ↑ 敵ごと（inc=2〜8）
n = そのレース敵との戦闘の経過ターン数
```
- 1ターン目から base_initial(5) 分のダメージを持つ（最初から無害ではない）
- 2ターン目以降は敵ごとのincで個性が出る（inc=2はゆるやか、inc=8は急激）

**multiplierの乗算ルール（v1.0確定）：**
- `stance_multiplier` は複数ソースを掛け合わせる統一経路で実装
- 現在：攻撃ブーストのみ（次の1撃を×2.0）
- 将来：フェーズB（スタンス）が乗る → `compute_multiplier()` に1行足すだけ
- 攻撃的スタンス中にブーストを切ると最大火力（シナジー）。爆発力はbotで監視

| タイプ | 感情体験 | 代表行動 | row1枠 | L2アイコン |
|--------|---------|---------|:------:|:--------:|
| **削り合い** | じりじりした削り合い | counter主体 | 枠A | ⚔️ |
| **賭け** | 大当たり/大外れのスリル | heavy_blow/none | 枠B | 🎲 |

| **ずれ** | 攻撃が空振りする徒労 | evade主体 | 枠C | 💨 |

### 9.1 row制約

**row1**：枠A=削り合い、枠B=賭け、枠C=レース/ずれ/カオス
**row2**：同一体験タイプは最大2体まで
**row3（5F）**：カオス以外を最低1体含める

### 9.2 カオスタイプ設計（v0.7確定：ランごとシード決定型）

カオス敵の行動テーブル比率は**ランごとにシードから決定**する。
「このランのカオスは何が来やすいか」を遊びながら読む体験になる。

```
ラン開始時、各カオス敵について:
  RNGストリーム8（chaos専用）から行動weightを生成
  例: あるランでは heavy_blow偏重、別のランでは evade偏重
  ベース比率はevade/counter/heavy_blow/ramp_hitの4種から
  ディリクレ分布的にランダム配分（合計1.0になるよう正規化）
```

> 同一ラン内では一貫しているため「学習可能」。ラン間では変わるためリプレイ性が出る。

## 10. 宝箱・modシステム

### 10.1 modリスト（6種）

| mod名 | 効果（1枚） | スタック時（2枚） | 影響先 |
|-------|-----------|--------------|------|
| **見切り** | evade weightを50%削減 | evade weight=0（完全無効化） | 行動テーブル weight |
| **加速止め** | ramp_incrementを50%削減 | ramp_increment=0 | ramp更新 |
| **重装甲** | counter/heavy被ダメを固定値軽減 | 軽減値加算（上限base_damageの50%）| 被ダメ計算 |
| **反射** | counter被弾時に追加ダメを敵へ | 追加ダメ値加算 | 被ダメ処理後 |
| **先読み** | 各戦闘1ターン目行動を事前公開 | 2ターン目まで公開 | 情報開示 |
| **好機** | heavy_blow被弾時に追加攻撃1回 | クールダウン短縮（毎ターン可）| 被ダメ処理後 |

### 10.2 スタックルール
- 同mod2枚目：上表「スタック時」適用 / 3枚目以降：2枚目と同じ
- 異なるmod：独立して重複 / 抽選：置き戻し / 枯渇：なし

### 10.3 リロールルール
- 開封前のみ可（30G）/ 開封後は不可（完全サプライズ維持）

### 10.4 modインタラクション（v0.7確定：拡張スキーマ）

矛盾・シナジーを以下のスキーマで管理する。`type` と `is_intended` を持たせ、後からシナジー行を追加できる構造。

```
mod_interactions: [
  {
    mods: ["見切り", "先読み"],
    type: "cancel",
    behavior: "先読みでevade予告されても与ダメ0は発生しない（見切り優先）。先読みは『evadeが来ない』確認のみ",
    is_intended: true
  },
  {
    mods: ["見切り", "好機"],
    type: "synergy",
    behavior: "evade weight=0により相対的にheavy_blowが来やすくなり、好機の発動頻度が上がる",
    is_intended: true
  },
  {
    mods: ["反射", "重装甲"],
    type: "synergy",
    behavior: "被ダメ軽減後の値に反射追加ダメを乗せる。あえてcounterを受ける『被弾上等』立ち回りが成立",
    is_intended: true
  }
]
```

**運用方針（面白さの非対称な扱い）：**
- **死にmod**（腐る組み合わせ）：統計で検出して**潰す**
- **壊れmod**（爆発する組み合わせ）：統計で検出するが**残す**（クリア率を破壊するレベルのみ調整）
- `±8pt`の寄与制約は「常時の平均寄与」であり、「引けたときの爆発力」は均さない

**拡張性：** modを追加する際は「攻撃前/行動ロール後/被ダメ計算後」のフックに効果ハンドラを差し込むだけ。インタラクションは `synergy` 行を足すだけで「狙って組みたい組み合わせ」を増やせる。

### 10.5 コンバットログ（v1.0確定：表示専用・使い捨て）

- 戦闘中の全ログを保持し、スクロールで遡れる（表示行数はUI側で調整、デフォルト8行）
- **combat_logは表示専用・使い捨て**。戦闘終了で破棄してよい。統計には使わない
- **RunRecordとは同期しない**（別目的のため）。combat_log=表示、RunRecord=統計と役割を完全分離
- これによりログのズレるバグ（表示は勝利・記録は敗北等）が構造的に起きない

> **ログ二重管理の解消（v1.0）**：combat_log（表示・使い捨て）とRunRecord（統計・永続）を別物として扱う。将来リプレイ機能が必要になっても、SFC32のseedから戦闘を完全再現できるため、ログを永続保存する必要はない。

| `gold` | 0 | 敵撃破・sink・恒久強化（+初期gold） |
| `mods` | [] | 宝箱開封 |
| `stance_multiplier` | 1.0 | フェーズB（現在固定） |

### 12.2 ダメージ式・スケーリング

**敵HPスケーリング：** `enemy.hp = base_hp × (1.0 + 0.15 × (tier - 1))`

| tier | 1 | 2 | 3 | 4 | 5 |
|:---:|:--:|:--:|:--:|:--:|:--:|
| 倍率 | 1.00 | 1.15 | 1.30 | 1.45 | 1.60 |

**ゴールドドロップ：** `gold_base × floor_multiplier × 強敵ボーナス`

| フロア | 1F | 2F | 3F | 4F | 5F |
|:-----:|:--:|:--:|:--:|:--:|:--:|
| floor_multiplier | 1.00 | 1.25 | 1.50 | 1.75 | 2.00 |

### 12.3 恒久強化システム（v0.7確定：問E）

**仕組み：** ポイント割り振り型。1クリア=1ポイント獲得。5項目に自由配分。

| 強化項目 | 1レベルあたり効果 | 上限Lv | 最大累計 |
|---------|---------------|:----:|--------|
| +max_hp | +10 | 5 | +50 |
| +attack | +2 | 5 | +10 |
| +初期gold | +15G | 5 | +75G |
| +gold_drop率 | +10% | 3 | +30% |
| -sinkコスト | -5G | 3 | -15G |

- 全項目MAX（26点）まで26クリア必要
- 数値はデータ駆動で調整、上限レベルの構造は確定
- **拡張性**：強化項目はテーブル定義。後から項目追加が容易

**フェーズB（スタンス）予約事項：**
- ダメージ計算は必ず `attack × multiplier` の形で記述（直接代入禁止）
- RNGストリームに `stance`（番号6）を予約
- フェーズB追加時は統計再検証が必要（想定済み）

## 13. ゴールドシステム

### 13.1 獲得（フロア別期待値、叩き台）

| フロア | 1F | 2F | 3F | 4F | 5F | 累計 |
|-------|:--:|:--:|:--:|:--:|:--:|:---:|
| 期待値 | 15-25G | 25-40G | 35-55G | 45-65G | 55-75G | 175-260G |

### 13.2 Sink一覧と使用タイミング（v0.9確定）

| sink | コスト | 効果 | 使用タイミング | 種別 |
|------|:-----:|------|------------|:---:|
| スカウト | 15G | 次ターン行動先読み（強敵戦で輝く） | **いつでも** | 守り |
| 小回復 | 20G×フロア係数 | **+15固定**回復 | **いつでも**（満タンでも可、溢れは捨て） | 守り |
| 大回復 | 40G×フロア係数 | **+30固定**回復 | **いつでも** | 守り |
| ゲート保証 | 50G×(1.5)^(n-1) | 大ダメ確率を削る（重ねがけ可・特殊維持） | **gate_preview時のみ** | 守り |
| 宝箱リロール | 30G | 宝箱を開封前に引き直し | **treasure_preview時のみ** | 守り |
| **攻撃ブースト** | 30G（叩き台） | **次の1撃のみ attack +100%** | **battle時のみ** | **攻め** |

> **攻めのsink追加（v0.9）**：従来のsinkは全て「リスクを減らす」守りだった。攻撃ブーストは唯一の「攻め」のsink。次の1撃だけattackを上書きする（ダメージ式 `attack × stance_multiplier` の multiplier を一時上書き）。

#### 回復コストのフロア係数（v0.9確定）

| | 1F | 2F | 3F | 4F | 5F |
|---|:--:|:--:|:--:|:--:|:--:|
| 小回復 | 20G | 25G | 30G | 35G | 40G |
| 大回復 | 40G | 50G | 60G | 70G | 80G |

終盤は回復が高額化し、無限回復ができなくなる。回復量固定（§7.3）と合わせて、終盤は「大きく削られて・少ししか回復できない」緊張感を作る。

#### スカウトの位置づけ（v0.9明確化）

- 通常敵：15Gで次1ターン先読みは割高に感じる（使わなくても対処可能）
- 強敵戦（difficulty≥4）：「次にheavy_blowが来るか」を読む命綱になり、同じ15Gが安く感じる
- 暗黙知型（確率非公開）だからこそ、強敵の読めない恐怖に対して情報を売る価値が出る
- 攻撃ブーストとのシナジー：スカウトで危険を察知 → ブーストで先に倒し切る

#### 攻撃ブーストの設計意図（v0.9）

- レース系の敵に刺さる（早く倒せばramp_hitを受ける回数が減る）
- 強敵を早期決着させ被ダメ機会を減らす
- 「攻撃ブーストで早期決着 vs 回復でHP管理」の2戦略が生まれる
- 実装：`stance_multiplier` を次の1撃だけ上書き。フェーズB（スタンス）と同じ計算経路に乗る

### 13.3 貯め込み逓減（v0.7確定：問F＝自然解決）

- 所持上限なし・減衰なし
- sinkを使わないと死にやすい難度設計で「使った方が得」を自然に成立させる
- Phase4で「ゴールドをほとんど使わずクリアするランの割合」を監視
- 多すぎる場合のみ対策（上限/減衰）を後から検討

          │ SQLite       │ ← 将来PostgreSQL移行
          │ (game.db)    │
          └──────────────┘

### 22.2 技術選定一覧

| レイヤー | 技術 | 選定理由 | 将来の移行先 |
|---------|------|---------|------------|
| フロントエンド | React + TypeScript + Vite | デファクト・起動が速い | — |
| 状態管理 | Zustand | 11phaseの管理に強い・2KB軽量 | + TanStack Query |
| スタイリング | Tailwind + clsx + CSS Variables | テーマ一元管理・ランタイムコストゼロ | — |
| バックエンド | Python + FastAPI | Swagger自動生成・型安全・非同期 | — |
| ORM | SQLAlchemy | DB切り替えがコード変更最小 | — |
| DB | SQLite | 設定ゼロ・ローカル開発に最適 | PostgreSQL |
| 通信 | REST API | ターン制と相性◎・botと同じエンジンを使える | — |
| リポジトリ | モノレポ | 管理が楽・ポートフォリオで見せやすい | — |

### 22.3 設計原則（移行容易性の確保）

実装開始時点から以下を守ることで、将来の技術移行コストを最小化する。

| 原則 | 目的 |
|------|------|
| ゲームロジックは全てPython。Reactは計算しない | botシミュレーターとUIで同じエンジンを共有 |
| API通信は `gameApi.ts` に集約（直接fetchしない） | TanStack Query移行時にこのファイルだけ変更 |
| DB操作はSQLAlchemy経由（生SQLを書かない） | PostgreSQL移行をコード1行で実現 |
| ダメージ計算は `attack × multiplier` で記述 | フェーズB（stance）追加に備える |

## 25. APIエンドポイント仕様

### 25.1 設計方針

- ゲームの全ロジックはバックエンド。フロントは操作を送って新しい状態を受け取るだけ
- 各レスポンスは**完全なゲーム状態**を返す（フロントは差分計算不要）
- `session_id` でランを識別。DBに永続化

### 25.2 エンドポイント一覧

| メソッド | パス | 用途 | リクエスト | レスポンス |
|---------|------|------|----------|----------|
| POST | `/api/run/new` | 新規ラン開始 | `{ seed?: int }` | `GameState` |
| GET | `/api/run/{session_id}` | 状態取得（再開） | — | `GameState` |
| POST | `/api/run/{session_id}/select-node` | ノード選択 | `{ node_id }` | `GameState` |
| POST | `/api/run/{session_id}/attack` | 攻撃 | — | `GameState` |
| POST | `/api/run/{session_id}/sink` | sink使用 | `{ sink_type }` | `GameState` |
| POST | `/api/run/{session_id}/treasure/open` | 宝箱開封 | — | `GameState` |
| POST | `/api/run/{session_id}/treasure/reroll` | 宝箱リロール | — | `GameState` |
| POST | `/api/run/{session_id}/gate/resolve` | ゲート通過 | — | `GameState` |
| POST | `/api/run/{session_id}/upgrade` | 恒久強化割り振り | `{ upgrade_type }` | `UpgradeState` |
| GET | `/api/stats/history` | RunRecord履歴 | — | `RunRecord[]` |

> **sink_typeの値**：`scout` / `heal_small` / `heal_large` / `gate_guarantee` / `treasure_reroll` / `attack_boost`
> **ゲート保証の重ねがけ**：`sink_type: "gate_guarantee"` を `gate_preview` phaseで複数回POSTできる。サーバーが現在の重ねがけ回数 `n` を保持し、コスト `50G×1.5^(n-1)` と削減量 `25%×0.5^(n-1)` を計算してGameStateに反映。ゴールド不足時は400を返す。
> **攻撃ブースト**：`sink_type: "attack_boost"` は `battle` phaseでのみ有効。次の `attack` 1回だけ `stance_multiplier` を上書き。

### 25.3 GameStateレスポンスの形

```json
{
  "session_id": "uuid",
  "phase": "exploring",
  "current_floor": 2,
  "player": {
    "hp": 80, "max_hp": 100, "attack": 15,
    "gold": 45, "mods": ["反射", "見切り"],
    "stance_multiplier": 1.0
  },
  "floor": {
    "tree_shape": [3, 4],
    "nodes": [
      { "id": "n1", "type": "enemy", "row": 1, "locked": false,
        "experience": "削り合い", "is_strong": false, "resolved": false }
    ],
    "edges": [ { "from": "n1", "to": "n4" } ]
  },
  "battle": null,
  "combat_log": [],
  "available_sinks": ["scout", "heal_small", "heal_large"]
}
```

### 25.4 エラーハンドリング

| ステータス | 意味 |
|----------|------|
| 400 | 不正な操作（ロック中ノード選択・ゴールド不足等） |
| 404 | session_idが存在しない |
| 409 | phase不整合（戦闘中にノード選択等） |

### 25.5 型共有

`backend/app/schemas/api_schemas.py`（Pydantic）と `frontend/src/api/types.ts`（TypeScript）で同じ型を定義。
将来的にはOpenAPIスキーマからTypeScript型を自動生成することも可能（FastAPIがSwaggerを吐くため）。
