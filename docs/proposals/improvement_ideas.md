## アイディア 1: 検死レポート＆リプレイシアター

### ① ねらい

死んだ瞬間が一番学びたい瞬間なのに、現状の DeadPage は死因1行＋集計値のみ。ここに**「同じ山札（seed）での反実仮想」**を突きつける：「3ターン前にガードしていれば、この敵は倒せていた」。fun_metrics PR-6（回避可能死）のインフラをそのまま UI に出す。決定論エンジンだから、これは推定ではなく**事実としての分岐タイムライン**を見せられる——ここが普通のゲームには真似できない点。near-miss の可視化はリトライ動機（指標13）の仮説そのもの。

### ② UX / UI

- DeadPage にタブ追加：[結果] [検死レポート] [リプレイ]。カジノの意匠は「監視カメラ映像をディーラーと見返す」。
- リプレイ：ターン単位のタイムラインスクラバー。各ターンで双方 HP バー・chips・行動アイコン・ダメージ数字を再生。倍速/コマ送り。
- 検死レポート：
  - ラン全体の勝率推定カーブ（WinModel の p_t を面グラフで。ラン後表示なので情報リークなし）。急落点に「ここで運命が変わった」アノテーション（surprise 最大点）。
  - 分岐タイムライン：死亡直前 L=5 決定点から反実仮想の枝を出す。枝をタップ→「ガード → 残HP12で勝利（同一seedでの実測）」。**実測枝（決定論 rollout）は実線、モデル推定値は点線＋「推定」ラベルで厳密に区別する**。
  - 文言は責めない。ディーラー口調：「悪くない打ち筋だった。ただ、あの場面——」。回避不能死のときは明示的に「あれは避けられなかった。山が悪い」（②公平性の演出として超重要。回避不能死をちゃんと「理不尽だった」と認めるゲームは信頼される）。
- 共有ボタン：p カーブ画像＋死因の1枚絵を書き出し（アイディア8と連動）。

### ③ 裏の技術

- 前提：人間ランの操作履歴永続化（現状は in-memory のみ）。`run_actions` テーブル（run_id, decision_index, action JSON）を Alembic で追加。ラン終了時に一括 INSERT（ターン毎 INSERT は不要、終局時 flush で十分）。
- 死亡確定時に FastAPI BackgroundTasks でポストモーテム計算：`replay(seed, actions)` → L×候補≈15 本の決定論 rollout ＋ WinModel で p 系列。結果 JSON を `postmortems` テーブル（run_id PK, payload JSON, model_meta）に保存。計算量はミリ秒〜数百ms オーダー、Celery 等は不要（過剰設計）。
- API：`GET /api/run/{run_id}/postmortem`（計算済みを返す。未完なら 202）。
- WinModel の pickle をアプリ起動時ロード。レスポンスに feature_version / model_file を刻印（モデル更新でカーブの意味が変わるため）。
- フロント：曲線描画にチャートライブラリ、スクラバーはローカル state（zustand は任意）。

### ④ 技術ギャップ

- チャートライブラリ未導入 → recharts（宣言的・React 親和・学習コスト最小）。
- 操作履歴の永続化が未実装（OPEN-025 の拡張として先行実装が必要）。
- WinModel の API 同梱（simulation → api への依存追加。`app/services/win_model_service.py` に隔離し、routes から simulation を直 import しない）。

### ⑤ バランス・リスク

- 「回避可能だった」の突きつけはフラストレーション源にもなる。→ 表示は任意タブ、文言はディーラーの敬意ある講評。**回避不能死の明示とセットで初めて成立する**。
- モデル曲線は bot 分布で学習した推定値。人間プレイは分布外なので、当面「参考曲線」表記＋人間データが貯まったら再学習（fun_metrics 仕様 §10 と同じ制約）。

### ⑥ 効果検証

- 指標13（リトライ率）の A/B：検死レポート有効/無効をプロファイル設定でランダム化（自分1人の間は期間交互で擬似 A/B）。
- 指標5（回避可能死率）の分布と、レポート閲覧後の行動変化（guard 使用率の推移）。

## アイディア 2: サイドベット「読み宣言」

### ① ねらい

暗黙知（隠し weight）の学習成果を**チップで直接換金**させる。戦闘中、自分の行動前に「次の敵行動」へ任意でベット。配当は固定オッズ（例：5〜20G ベット、的中3倍）——真の weight は開示しないまま、「知っている者だけがプラス EV になる」構造。**カードカウンティングのゲーム化**であり、カジノテーマの本丸。毎ターンに小さな意思決定（賭ける/賭けない/どれに/いくら）が生まれ、close-call が構造的に増える。

### ② UX / UI

- BattlePage 下部にフェルト調のベットスポット：5 行動アイコン（none/counter/強打/回避/ランプ）を横並び。タップでチップを積む（5/10/20 をトグル）、長押しで取消。
- 結果演出：的中でチップが跳ねて手元に着地（音：チップのクリンク）、外れでディーラーが回収。連続的中ストリーク表示（配当は増やさない。表示のみ——分散を上げすぎない）。
- 敵ごとの自分の的中率をスポット脇に小さく表示（アイディア3の調書と連動）。
- **賭けない選択が常にデフォルト**（未選択＝ベットなし）。テンポを壊さないことが絶対条件：ベット UI は行動ボタンと同一画面・追加確認なし。

### ③ 裏の技術

- エンジン：attack/guard のペイロードに `side_bet: {behavior, amount} | null` を追加。判定は**そのターンの stream2 ロールをそのまま使う**（新規乱数消費ゼロ＝§17.2 の消費契約を変えない。ここ重要）。
- 検証：phase 外・残高不足・上限（1戦闘あたり合計ベット上限、config 化）は 400/409 の既存マトリクスに従う。
- テレメトリ：side_bets を RunRecord 拡張 or run_actions から導出。**予測的中率＝スキルの直接測定**になる（§18.1 のスキル幅指標より筋が良い。informed-bot 代理ではなく人間の知識そのもの）。
- バランス設計はシミュレーションで：informed bot は期待収支プラス、naive bot はハウスエッジ分マイナス、になるようオッズを解く（fun_metrics PR-7 の変種がそのまま使える）。行動4種+none の平均出現率から、固定3倍が「無知には -EV、知識には +EV」となる帯を計算して config に落とす。

### ④ 技術ギャップ

- なし（既存スタックで完結）。演出はアイディア7の基盤に依存。

### ⑤ バランス・リスク

- 経済インフレ：informed 級プレイヤーの収支上振れが sink 設計（§13）を歪める。→ 戦闘毎ベット上限＋フロア毎の総ベット上限。**Phase4（経済検証）にサイドベット込みシナリオを追加してから本採用**。
- 「毎ターン UI を触らされる」疲労：デフォルト賭けなし＋ワンタップ完結を厳守。

### ⑥ 効果検証

- close-call 率（指標2）が battle_action カテゴリで上がるか。
- 的中率の学習曲線（ラン数に対する的中率の混合効果回帰）＝③知識が報われるの直接実証。

## アイディア 3: ディーラー調書（個人統計図鑑）

### ① ねらい

隠し weight を開示せずに、**「自分が観測した頻度」だけを信頼区間つきで見せる**。「この敵の counter: 観測 42%（n=31、95%CI 26–59%）」。プレイヤーの頭の中の曖昧な感覚を、自分のデータで裏づける——③知識が報われるの可視化であり、**統計教育コンテンツ**でもある（Zenn ブランドとゲームが合流する場所）。ゲーム内で Wilson 区間を表示するゲームは他にない。独自性の柱になる。

### ② UX / UI

- StartPage から入る「調書」ページ。敵1体＝1枚のディーラーカード（マグショット風）。
- カード内容：行動頻度の横棒グラフ＋CI ヒゲ、遭遇数 n、対戦績（勝率・平均撃破ターン）、初遭遇日。n が小さいほどヒゲが長い＝「まだ読み切れていない」が視覚で伝わる。
- **ラン中は見られない**。「テーブルへのメモ持ち込みは禁止だ」——カジノルールとして世界観に織り込む（ラン中は記憶で戦う緊張を守る）。
- データ鮮度の演出：バランス調整（data_version 変更）が入ったら、カードに「ハウスがディーラーを入れ替えた」帯を表示し、旧観測をアーカイブ（グレー表示で残す）。調整で過去の知識が無価値化する問題を、隠さず世界観で告知する。**誠実さがそのまま演出になる**。

### ③ 裏の技術

- 観測データ：戦闘ログから (enemy_id, observed_behavior, data_version) を抽出しラン終了時に `observations` テーブルへ集約 INSERT（生ログ保存でなく集計で持つならサイズ最小。ただし将来の再集計を考え、run_actions があるなら導出テーブル扱いにして再構築可能に）。
- API：`GET /api/profile/dossier` → 敵ごとの頻度・Wilson 95%CI（閉形式なので scipy 不要、純 Python 数行）・戦績。data_version でパーティション。
- **開示不変条件の維持**：返すのはプレイヤー自身の観測集計のみ。真の weight・カオス比率は当然含めない（snapshot 非露出テストと同系の assert を API テストに追加）。
- フロント：CI ヒゲは SVG 自作 or recharts の ErrorBar。

### ④ 技術ギャップ

- recharts（アイディア1と共通）。他は既存で足りる。

### ⑤ バランス・リスク

- 学習加速で informed との差が縮む＝難易度曲線が前倒しになる。→ 指標8（情報価値）の informed−naive ギャップを世代別に監視。
- 見せすぎ注意：ヒント（「counter が多め」等の要約文）は付けない。

### ⑥ 効果検証

- （v0.1 受領時点で未収録。追補予定）

## アイディア 9: ベット連勝パワー（読み宣言の勝ち数で強くなる）

> 2026-07-09 デザイナー起票。「賭けを何回もして、かつ（勝ち）回数が増えると何かパワーを得る。**持っている金額ではなく賭けに勝った回数**を軸にする」。

### ① ねらい

サイドベット『読み宣言』（アイディア2・実装済み）は現状チップの増減のみで、読みの上手さが**経済にしか還元されない**。勝ち回数そのものをラン内の強化資源にすることで、(a) 賭ける動機が常時発生する、(b) チップが尽きても「読みの腕」で巻き返せる、(c) 3本柱③「知識が報われる」が戦闘力に直結する。金額軸でなく回数軸なのは、少額安全ベットの繰り返しと高額一発を等価に扱い「読みの試行回数×的中率」だけを測るため。

### ② UX / UI

- 戦闘HUDに連勝/累計勝ち数のバッジ（例: 🎯×3）。閾値到達時に次段の報酬をプレビュー表示。
- 報酬候補（叩き台）: 3勝=次の受けの減衰段を1つ回復／5勝=先読み1ターン付与／7勝=攻撃ブースト無料1回。**連勝（streak）か累計（count）かは要決定**。
- 賭けマークと行動アイコンの体系（今回のUI統一で導入する `labels.ts` の behavior アイコン正本）をそのまま使う。

### ③ 裏の技術

- エンジン: `Battle` or `RunRecord` に bet_wins（累計）/ bet_streak（連勝）を追加。判定は既存の side_bet 解決ロジック（`_resolve_battle_turn`）に1行。報酬付与はエンジン内（Reactは計算しない）。
- テレメトリ: RunRecord に bet_wins を刻印（fun_metrics の読み精度指標と接続可能）。
- API: battle_state に bet_wins/streak と次段報酬を公開（BattleOut 契約テスト必須＝v1.8 guard_uses の教訓）。

### ④ 技術ギャップ

なし（既存インフラで足りる）。

### ⑤ バランス・リスク

- **支配戦略リスク（OPEN-018の教訓）**: 報酬が強すぎると「毎ターン最小額ベット」が義務化する。→ 賭け可否は現行の per_battle_cap 維持＋報酬は逓減 or 上限。bot に賭け方策を実装して ablation（guard_sensitivity.py と同型の感度分析）で検証してから数値確定。
- 外れのペナルティ（連勝リセット）が強すぎると賭け抑制になり本末転倒。
- 数値は全てデザイナー決定。

### ⑥ 効果検証

- サイドベット使用率・的中率（テレメトリ実装済み）の変化、ベット有無コホートのクリア率差（CRN対標本）、fun_metrics の緊張指標。

## 採用時の進め方（本リポジトリの運用への接続）

1. アイディアを採用する場合、まず **クラスS の docs PR** で正本（`game_design.md` / `api_contract.md` / `data_model.md` 等）へ仕様として起こす。必要なら OPEN 表・changelog・ADR を伴う。
2. 数値（オッズ・上限・コスト等）はデザイナーが決める（本書の数値は全て叩き台）。
3. DB テーブル追加（run_actions / postmortems / observations）は OPEN-025 / OPEN-027（Alembic 等の運用基盤）と依存関係があるため、先行整備の要否を判断する。
4. 実装は「テスト→エンジン→API→UI」の順（CLAUDE.md）。
