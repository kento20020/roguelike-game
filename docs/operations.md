## 18. バランス検証フレームワーク

### 18.1 合格条件

| 指標 | 目標（効果量ベース） | 状態 |
|------|------|:---:|
| **強プレイのクリア率** | **25〜40%**（**midパネル＝〜6クリア相当を固定**して測定・v1.10改訂） | ★確定・**実測 31.1% CI[28.3,34.0]＝帯内（v1.10）** |
| ランダムプレイのクリア率 | 1〜5% | 暫定 |
| スキル幅（強−ランダム差） | クリア率差 ≥ **X=20pt**（CI下限が0を跨がない＋最小効果量・v1.11事前登録） | **確定・実測PASS（v1.11）**：maxed−random 差の下限≈79.6pt／mid−random ≈27.9pt |
| 初手別クリア率差 | ±5pt以内（最大−最小の効果量で判定） | 実測（v1.11）：maxed 2.0pt=PASS・**mid 6.3pt=超過（warn・L有利・OPEN-045）** |
| 選択感度 | 効果量 ≥ **Y=2pt**（p値のみで判定しない・v1.11事前登録） | **実測PASS（v1.11・midパネル）**：6.3pt・FDR有意。maxedは天井効果で検出されず |
| 死亡フロア分布 | 終盤集中は許容。最終フロア以外の単一フロアが死亡の **Z=50%** を超えない（v1.11事前登録） | 実測PASS（v1.11）：最終以外の最大＝4F 33.8% |
| 単一mod寄与 | ±8pt以内（平均寄与のみ） | 暫定 |
| modペア寄与（synergy） | 主要ペアの交互作用が ±**W=10pt** 以内（v1.11事前登録） | 暫定（追加・OPEN-023／Phase3 で測定） |
| 初クリアまでの期待ラン数（人間相当bot） | 観測のみ・閾値なし（win-to-progress の体験曲線監視・OPEN-029) | 暫定（追加） |
| 全死亡に占めるゲート死率 | 観測のみ・閾値なし（柱②「運だけで死なせない」の納得感監視。`gate_results` から算出可） | 暫定（追加・v1.9） |
| チップ枯渇率 | 観測のみ・閾値なし（枯渇状態での戦闘突入比率。§13.3 の枯渇側監視） | 暫定（追加・v1.9） |
| サイドベット収支・的中率 | 観測のみ（informed=+EV / naive=−EV の帯検証は Phase4・OPEN-031） | 暫定（追加・v1.9） |
| 1ラン実時間（duration） | 観測のみ（目標は PRD §27.3 のプレイ時間目標表。テレメトリ追加は OPEN-031 と併走） | 暫定（追加・v1.9） |
| 公平性監視（ゲート大ダメ連続回数・回避不能死率・未使用チップ死亡率・scout/guard未使用死亡率） | 観測のみ・閾値なし（柱②の担保・PRD §3.1。極端な偏りが出た場合のみ bad-luck protection をクラスSで検討） | 暫定（追加・v1.9） |

> **有意性ハック回避（§18.4 Goodhart）**：bot大量試行では n が大きく僅差でも p<0.05・CI0非跨ぎを満たすため、スキル幅・選択感度・初手差は**最小効果量（X/Y pt）を CI下限とともに要求**する（`balance_stats.py` の TOST=同値検定も併用）。
> **死亡フロア分布**：難度ランプのあるパーマデスでは終盤集中が正常。「集中しない」は偽陽性を生むため、終盤集中を許容し「最終フロア以外の単一フロアが過度に偏らない」基準へ置換。
> **クリア率帯の測定条件（v1.10 改訂・デザイナー決定 2026-07-11）**：帯（25-40%）は **mid パネル（〜6クリア相当：hp2/atk2/gold2/drop1/sink1）を基準**に測る。旧基準「未強化パネル」は、現行の恒久強化幅（attack 15→26 等）と両立不可能なことが OPEN-030 のシミュレーションで判明した（base を帯に入れる難易度では maxed が形骸化する・balance_model.md）。**base・maxed は別帯の観測対象**（v1.10 実測: base 1.2%＝初クリア現実化・maxed 82.5%）。未強化での帯達成を目指す場合は恒久強化の効果値圧縮（OPEN-002）とセットで再設計する。
> **strong戦略の版固定**：クリア率帯は strong bot の賢さに対する相対値。`strategy_version` で strong 戦略を凍結し「確定帯は当該版に対してのみ有効」とする（戦略変更時は帯を再検証）。**バランス検証全体が bot の人間代表性に依存する**点は運用上の前提として明記。
> **効果量閾値の事前登録**：X/Y/Z/W の値は**Phase2 開始前に数値で確定して本表へ記入する（事前登録）**。データを見てから閾値を決めるのは効果量版 p-hacking であり禁止。値の決定はデザイナー（人間）、以後の変更は変更履歴で管理。**v1.11（2026-07-11）で X=20pt／Y=2pt／Z=50%／W=10pt をデザイナー確定・登録済み**（Phase2 実施前に確定。実施記録は [reports/2026-07-11_phase2_report.md](reports/2026-07-11_phase2_report.md)）。
> **確定帯と guard の不整合（OPEN-018）**：帯 25-40% は **guard 無し bot** での測定値だった。v1.8 でジャストガード再設計・bots.py（strong-v2）への受け方策実装・感度分析による数値確定（heavy0.9/decay0.5）が完了し、guard 数値起因の Phase1 ブロッカーは解消した。**Phase1 前に残るのは深度カーブ・depth_scaling 等の数値調整**（§18.2 の v1.4注記）。

- 統計指標は合格条件であり最適化目標ではない

### 18.5 受け入れ基準（完了の定義 / Definition of Done）

§18.1 はバランスの合格条件。本節は**実装完了の定義**を分けて明文化する（v1.1で追加）。

**機能**
- 新規ラン開始 → 1F〜5F進行 → 5Fゲート通過で `cleared`、HP0で `dead` に遷移する
- ノード選択・戦闘・宝箱（開封/リロール）・回復・ゲートが各phaseで解決できる
- クリア時に恒久強化ポイントを1獲得し割り振れる

**データ（§20.5 機械検証）**
- config/enemies/mods/floors のロード成功
- 全非カオス敵の behaviors weight 合計＝100／全フロアのゲート確率合計＝1.0（loader.validate・v1.4）
- アンロック整合（多親=親2／単親=親1・生成フロアは `validate_floor` が生成毎に検証）・存在しないノード参照なし

**API**
- 全エンドポイントが正常系/異常系テストを通過
- phase不整合=409／チップ不足・未対応操作=400／不明session=404（§25.4）

**UI**
- 各phaseに対応画面が表示される／`available_actions` 外の操作は実行不可
- ツリーは row1=画面下・ゲート=画面上で描画（§4・§26.1）

**RNG / テレメトリー**
- 同一seed・同一操作列で同一結果（Python/TS黄金テスト）
- ラン終了時に RunRecord が保存され、`cleared`/`dead` が正しく記録される

> **TS版SFC32の用途**：本番のクライアント計算は無い（原則1「Reactは計算しない」）。TS黄金テストは将来のオフライン/演出用途に向けた**RNGパリティの凍結**であり、演出で使う場合も rng 状態は露出しない演出専用シードに限定する。

### 18.6 人間プレイテスト計画（v1.9 追加）

バランス検証全体が bot の人間代表性に依存する（§18.1 注記）ため、Phase1 の帯確定後に人間プレイテストを行う。**実施計画の正本は [playtest_plan.md](playtest_plan.md)**（対象者区分・人数・観察項目・質問例・記録テンプレート。v1.9 新設）。本節は要点のみ：

- botで測れないもの（面白いか・理解できるか・理不尽に感じたか・もう1回やりたいか）を測る
- **収集**：RunRecord（`bot_type=human`。UIクライアントは bot_type を送出しない規約＝§25.2）＋口頭フィードバック。統計比較は `data_version` で世代を固定して行う
- OPEN-029（初クリア曲線）・OPEN-032（放棄点）・OPEN-043（FTUE）の検証手段を兼ねる
- テスト結果は「合格条件」ではなく**デザイナーの判断材料**（§18.4 Goodhart 回避に準拠）

### 18.7 バランス変更手順（クラスB・v1.9 追加）

> `backend/app/data/*.json`（config / enemies / mods / floors）の数値のみを変更する PR（CONTRIBUTING §3 クラスB）の実手順。構造変更（新フィールド・新挙動）を伴う場合はクラスS（docs PR 先行）に切り替わる（判定基準は CONTRIBUTING §3・data_model.md §20.9 冒頭）。目標カーブとの照合は [balance_model.md](balance_model.md) を使う。

1. **変更目的を1文で書く**：PR 本文に「何のためにどの数値を変えるか」を明記する（例：「5F 大ダメ率が高すぎるため gate_result_table を調整」）。数値の最終判断はデザイナー（人間）であり、PR は判断結果の反映である（CLAUDE.md）
2. **対象 JSON を変更する**：該当ファイルのみ編集。構造（キー名・ネスト）は変えない
3. **`loader.validate()` を通す**：データロード時の機械検証（§20.5）。ローカルでは `pytest` 実行時にロードが走る
4. **`docs/schemas/` ミラーを同期する**：クラスBは docs PR 先行が不要な代わりに、**同一PR内での schemas ミラー同期が CI（`check-docs`）で強制**される（CONTRIBUTING §3・§7）。GDD 本文の数表への追随は任意
5. **smoke bot を回す**：`python -m app.simulation.phase12_harness` を少数試行で実行し、エラーなく完走することを確認
6. **必要なら N=1000 の検証を回す**：クリア率帯（§18.1）や mod 寄与に影響し得る変更は `balance_stats.py` / `balance_analysis.py` で効果量を確認。閾値は §18.1 の事前登録値を参照し、データを見てから閾値を決めない
7. **変更前後を比較する**：クリア率・死亡フロア分布・mod 寄与などの §18.1 指標＋balance_model.md の目標列と比較。効果量とCI下限で判断し p値のみで判断しない（§18.4）
8. **意図的な変更なら baseline を更新する**：`python -m app.simulation.gen_baseline` で回帰基準を再生成。これは**意図的変更の承認手順**であり、デザイナーの確認を経てから実行・コミットする（無断更新は回帰検知を無効化するため禁止）
9. **`data_version` は自動で変わる**：4JSON の内容 sha256（§19.1）のため手動の版付けは不要。旧世代の RunRecord とは自動的に分離される
10. **changelog は任意**：CONTRIBUTING §5 のとおりクラスBの記載は任意（影響の大きい変更は記載を推奨）
11. **PR を出す**：`balance/` ブランチで作成。CI（`balance` / `lint` / `check-docs`）green の後 self-merge 可（CONTRIBUTING §2）

> **クラスB↔S の境界**：数値を変えるだけでなく「新しい判定方式を導入する」「フックの挿入点を増やす」等の挙動変更を伴う場合はクラスSへ昇格し、docs PR を先行させる（CONTRIBUTING §3「迷ったらS」）。

### 18.8 QAチェックリスト（手動・v1.9 追加）

> 自動テスト（`pytest` / typecheck / balance 回帰）で担保できない**手動確認**の一覧。リリース前（runbook.md §7 の公開前チェックリスト実行前）、または API/phase 遷移に関わるクラスS PR のマージ前に実施する。§18.5（受け入れ基準）の人手での再確認であり、§18.5 を代替しない。

**Smoke（一連の流れが通ること）**

| # | 項目 | 確認方法 |
|:-:|---|---|
| 1 | 新規ラン開始 | `POST /run/new` → `exploring` phase の GameState が返り、1F固定レイアウトが表示される |
| 2 | 戦闘勝利 | 敵ノードを選択して攻撃を繰り返し、敵HP 0 で `exploring`（ドロップ無）または `treasure_preview`（撃破ドロップ有）へ遷移する（§6.1） |
| 3 | 戦闘死亡 | HP0 まで被弾させ `dead` phase へ遷移し、`run_record`（cleared:false）が返る |
| 4 | 宝箱開封/リロール | `treasure_preview` で開封→mod確定。リロール（30G消費・phase不変）で再抽選される |
| 5 | 回復ノード | `heal` phase で大/小回復が反映され `chips` は変動しない（§7.3 無料） |
| 6 | ゲート通過 | `gate_preview` → `gate/resolve` で被ダメ反映・`next_floor`/`cleared`/`dead` のいずれかへ遷移 |
| 7 | 5Fクリア | 5Fゲート通過で `cleared`・恒久強化ポイント +1（§18.5） |
| 8 | 恒久強化割り振り | `POST /upgrade` で該当 Lv が +1 され、次回 `POST /run/new` の初期値に反映される |
| 9 | 死亡後の検死/調書 | 戦闘死後に検死レポート（3分類のいずれか）が表示され、ゲート死では「検死レポートがない」旨が出る（§15.2） |
| 10 | サーバ再起動後のセッション復元 | 進行中ラン作成後にサーバを再起動し、`GET /run/{id}` が中断前と同一状態を返す（runbook.md §1・`rebuild_engine`） |
