### 0.4 スコープ（v1.x）

**実装対象（v1.x）**：5フロアのノード探索／確率ベース戦闘（攻撃＋受け）／敵36体／mod 6種／宝箱・回復・ゲート／チップ経済（sink）／恒久強化（単一プロファイル）／RunRecord保存／基本UI／REST API／botシミュレーション連携。

> フロア数は**v1.x では5固定**。将来拡張する場合はデータ駆動で対応可能だが、`game_engine.MAX_FLOOR`・5F専用のrow3判定（`floor_generator`/`loader`）・テストの固定値の修正を伴う（§4.1脚注参照）。

## 1. ゲームコンセプト

### 1.1 コアコンセプト

> **「どの敵を選ぶかが未来を変える、確率で削り合うフロア制ローグライト」**

- 分岐するノードマップから**次に戦う敵を選ぶ**意思決定がゲームの核
- 倒した敵によって次に戦える敵がアンロックされ、**選択の連鎖**が生まれる
- 戦闘は確率ベース。攻撃するたびに敵が確率で反応し、**結果はロールで決まる**
- プレイヤーはHPをどれだけ温存して先に進めるかを**常に計算する**

### 1.2 ゲームの目的

カジノタワーの各階層にいる「ゲート（胴元の関門）」を通過して上の階層へ登り続けること。
5フロアのゲートを全て突破して頂上に到達すれば**クリア**。HP0でゲームオーバー（パーマデス）。

### 1.3 プレイヤーの動機

> **「カジノタワーの頂上に待つ"全てを賭けた一勝負"を目指して登り詰める」**

この一文がフレーバーテキスト・死亡/クリア画面・コピーライティング全体の軸になる。

> **テーマ転換**：当初の「地下カジノに潜る」から「カジノタワーを登り詰める」へ変更。UI描画が下から上（row1が画面下、ゲートが画面上）のSlay the Spire型になったことに合わせ、物語も「登る」で一貫させた。

## 2. ゲームループ

### 2.1 マクロループ（ラン間）

```
ゲーム開始
  → [ラン] 1Fから開始 → 探索・戦闘・ビルド構築 → 5Fクリア or HP0
  → クリア時: 恒久強化ポイント（+1）獲得 → 数値強化に割り振り
  → 次ランへ（恒久強化の分だけ有利な状態でスタート）
```

**win-to-progress**：死亡では恒久強化ポイントは得られない。クリアのみが積み上がる。

### 2.2 ミクロループ（ラン内：1フロア）

```
フロア開始
  → マップ表示（ツリー構造。row1の3体のみ選択可能）
  → ノード選択 → phase遷移して「戦闘/宝箱/回復/ゲート」を解決
  → 解決後: アンロック発生 → 次ノードが選択可能になる
  → ゲートを通過 → 次フロアへ
```

## 3. デザインの3本柱

**① 意味のある選択（Meaningful Choices）**
全ての選択肢にトレードオフを持たせる。「とりあえず強い1択」を作らない。

**② 公平なランダム性（Fair Randomness）**
ランダム性は「新鮮さ」のため、公平性は「意思決定の納得感」のため。運だけで死なせない。

**③ 知識が報われる（Knowledge is Power）**
キャラは死んでもプレイヤーの理解は蓄積する。上達実感を最重視する。

### 3.1 公平なランダム性の担保（柱②の運用定義・v1.9 追加）

「何をもって公平とするか」を定義し、「結局運ゲー」という印象を構造的に防ぐ。

**担保すること：**
- **死因が説明可能である**（戦闘死＝検死レポート §15.2 が回避可能性を必ず答える。ゲート死＝事前に確率テーブルを公開した上での選択の結果である §7.4/§26.4）
- **重要なリスクは事前に示唆される**（L2体験タイプ・強敵表示・ramp蓄積表示・テル・ゲート確率の事前公開）
- **リスクを下げる選択肢が常にある**（情報=scout/yomi、防御=guard、経済=回復/ゲート保証。ただし完全な安全は買えない §7.4）
- **連続不運が体験を壊していないか監視する**（下記の監視指標）

**意図的に許容すること：**
- 完全な結果保証はしない（ゲート保証は確率シフトであって確実突破ではない §7.4）
- 不運なランは存在する（パーマデスの前提。ただし「不運だった」と事後に納得できる説明を必ず添える）
- カオス敵は分散の大きさ自体を体験として扱う（§9.2・OPEN-028）

**監視指標**（operations.md §18.1 の公平性監視行・観測のみ）：ゲート大ダメの連続回数分布／回避不能死の割合（postmortem 由来）／未使用チップを多く残した死亡率／scout・guard 未使用の死亡率。これらが極端に偏る場合のみ bad-luck protection（連続不運の緩和）の導入をクラスSで検討する（現状は入れない）。

## 16. 世界観・テーマ

### 16.1 設定（問D＋テーマ転換）

> **舞台：カジノタワー（高層の賭博都市）**

- メカニクス（確率・賭け・リスクとリワード）と世界観が完全一致
- プレイヤーは流れ者の賭博師。**タワー頂上の「全てを賭けた一勝負」を目指して登り詰める**
- 各フロアのゲート＝胴元の関門。**上層ほど胴元が強大**
- 描画も下から上（登攀方向）でテーマと一致

### 16.2 用語の読み替えイメージ

| 機能 | カジノテーマ表現 |
|------|--------------|
| ゲートイベント | 胴元の関門・ハウスルール |
| 宝箱mod | イカサマ道具・必勝の秘技 |
| 回復ノード | バーカウンター・控え室 |
| ゴールド | チップ |
| 強敵 | 大物・名うての胴元 |
| 恒久強化 | 賭博師としての成長・評判 |
| 5F頂上 | タワー最上階・頂上の大広間 |

### 16.3 拡張余地

世界観が決まったことで、将来の商人イベント（闇の道具屋）、呪いイベント（イカサマがバレる）等のフレーバーが一貫した世界観で設計できる。

> **賭博テーマの公開時注意**：本作の「チップ」は**ゲーム内通貨のみ・リアルマネー無し**。公開時は README／ストア記載に「リアルマネー・実賭博なし、ゲーム内通貨のみ」を明記し、年齢レーティング・課金誤認防止に配慮する（**OPEN-035**。旧参照 OPEN-027 は運用基盤の項で当タスクを含まないため付替え）。

## 27. ターゲット・プラットフォーム・成功指標（v1.9 追加）

> バランスの合格条件（operations.md §18.1）は品質ゲートであってプロダクトの物差しではない、という穴を埋める章。数値・対象はいずれも**叩き台（要デザイナーレビュー）**。

### 27.1 ターゲットプレイヤー（v1.9 デザイナーレビューで具体化）

**Primary Persona**
- Slay the Spire / Balatro / Dicey Dungeons などのローグライト/ローグライクデッキビルダーが好き
- 確率・期待値・リスク管理の判断そのものを楽しめる
- 負けから学ぶことに抵抗がない（パーマデス＋win-to-progress・ADR-0004 を受け入れられる）
- 1ラン 10〜25分程度の短いローグライトを好む（§27.3）

**Secondary Persona**
- カジノ風テーマ・賭けの演出が好き
- 厳密な最適化よりも、賭け・読み合い・運試しの雰囲気を楽しみたい（サイドベット・テル・調書が刺さる層）

**Tertiary**
- 開発者コミュニティ（ポートフォリオ閲覧者。統計/シミュレーション設計・Wilson CI 表示などの技術面に関心のある読者）

**対象外（設計上、満足させにいかない）**
- アクション性・リアルタイム操作を求める人
- 運要素を強く嫌う人（確率ロールが核のゲームである）
- 長編ストーリーを期待する人
- 対人・リアルマネーのカジノゲームを期待する人（§16.3 公開時注意）

> 前提知識ゼロの一般層は v1.x の主対象にしない（発見型チュートリアル §14 が成立する前提）。ターゲットが変わる場合は情報量・説明量の設計（§5・§14）から見直しになる。

### 27.2 プラットフォーム・配布

- **デスクトップブラウザ**（min-width 1024px・§26.8）。モバイルは非スコープ（§0.4）
- 対応ブラウザ（叩き台）：Chromium系（Chrome/Edge）・Firefox の最新2版。Safari はベストエフォート
- 配布形態は未確定（ローカル実行〜小規模公開）。公開時の必須タスクは **OPEN-035**（レーティング・LICENSE・データ取り扱い）

### 27.3 セッション設計（プレイ時間目標）

可変深度 2/3/4/5/6（§4.1）前提の目標値。深度カーブ調整（**OPEN-030**）と戦闘テンポの調整はこの表との整合で判断する（proposals/floor_depth_randomization.md §2 が指摘した「プレイ時間増×パーマデスの消耗感」の判断基準）。数値はいずれも叩き台（デザイナーレビュー 2026-07-11 反映。旧記述「1ラン20〜30分」はこの表に置換）。

| 指標 | 目標（叩き台） |
|---|---|
| 1戦闘の平均ターン数 | 3〜6ターン |
| 1フロアの平均時間 | 2〜4分 |
| 死亡ランの平均時間 | 8〜15分 |
| クリアランの平均時間 | 15〜25分 |
| 初回プレイ（1ラン目終了まで） | 20分以内 |
| 死亡後リトライ開始まで | **10秒以内**（DeadPage→[もう一度]→1F開始。検死レポート閲覧は任意なので強制しない） |

- **計測基盤の欠落（既知）**：RunRecord に開始時刻・実時間（started_at / duration_seconds）が無く、実時間系の目標は実測できない。追加は OPEN-025 と同型のテレメトリ小改修（Alembic）として **OPEN-031 と併せて**扱う。1戦闘平均ターン数は既存の `total_turns`／`enemies_defeated[].turns` で今すぐ実測可能（balance_model.md と接続）

### 27.4 プロダクト成功指標（観測のみ・閾値なし）

| 指標 | 意味 | 依存 |
|---|---|---|
| リトライ率 | 死亡後に次ランを開始する割合（死の納得感の代理指標） | run_records の時系列 |
| 初クリアまでのラン数 | win-to-progress の入口体験 | OPEN-029 と共有 |
| ラン放棄率 | どのフロア/敵で投げたか（離脱シグナル） | OPEN-032 の記録方針が前提 |
| 完走後の継続ラン数 | メタ進行完走（21クリア・§27.6）後の長期動機 | — |

数値目標は置かない（統計指標を最適化目標にしない・§18.4 Goodhart 回避に準拠。観測して判断材料にする）。

### 27.5 非機能要件（叩き台・要デザイナー確定）

- 通常操作の API 応答：**p95 < 200ms**（完全状態返却込み・ローカル/同一ネットワーク想定）
- キャッシュミス時（`rebuild_engine` による再構築）：**< 1s**。超えるアクション列長が観測されたら **OPEN-036** で対策
- 想定同時プレイヤー：**1〜10**（単一プロファイル・workers=1 前提・§22.3）
- 受け入れ基準（§18.5 DoD）への性能項目の追加は、上記数値のデザイナー確定後に行う

### 27.6 メタ進行完走後の想定

全項目MAX（21クリア・§12.3）以降は恒久強化の無い**純粋なスキル/シード遊び**に移行する（ランダム生成＋カオスのラン別比率がリプレイ性を担保）。長期動機の追加（デイリーシード等・improvement_ideas #8）は v2.x 検討。完走後の継続ラン数は §27.4 で観測する。win-to-progress の設計根拠と引き受けるリスクは **ADR-0004** を正本とする。

### 27.7 リプレイ性目標（ビルド多様性・v1.9 追加）

v1.x では、**最低3系統のプレイスタイルが成立する**ことを目標とする（成立＝そのビルド軸を狙ったランが、狙わないランと体感的に異なる意思決定を生み、かつクリアに寄与し得る）。

| 系統 | 主なmod / 資源 | 体験 |
|---|---|---|
| 防御反撃 | 反射（hansha）・重装甲（juso） | 被弾を利用して勝つ（「被弾上等」シナジー §10.4） |
| 読み特化 | 先読み（yomi）・好機（kouki）＋テル/スカウト | 敵行動を読んでジャストガード・追撃・サイドベットでリターンを取る |
| 回避制御 | 見切り（mikiri）・加速止め（kasoku_dome） | evade/ramp を抑えて分散を殺し、安定して削り切る |
| 経済活用 | チップ系sink（回復・保証・ブースト・スカウト） | mod運に頼らず情報と資金でリスクを管理する |

> 成立本数の検証は Phase3（mod単体・ペア寄与）と fun_metrics の探索的分析で行う（±8pt の平均寄与制約 §10.4 は維持——「常時強い」ではなく「引けたとき戦い方が変わる」が成立条件）。「死にmod は潰す」（§18.4）はこの目標の下位規則。系統が3未満しか成立しない場合は mod 追加（§20.9 コンテンツ追加手順）よりも先に interaction（synergy 行）の追加で系統を立てる。
