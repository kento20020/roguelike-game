## 0. 文書管理・本書の使い方

### 0.1 文書管理

| 項目 | 内容 |
|------|------|
| 文書名 | カジノタワー・ローグライト ゲーム仕様定義書 |
| ファイル | `docs/game_design_document.md`（**バージョンレス固定名**） |
| バージョン | v1.2（実装整合・ドキュメントのみ改訂） |
| ステータス | 実装フェーズ移行可能 |
| 対象読者 | ゲーム/UI実装者、データ調整担当、レビュワー |
| 技術構成 | React + TypeScript + Vite / FastAPI / SQLite |
| 正本データ | `backend/app/data/*.json`（§20.5） |
| 関連文書 | 本書 / API実形=`engine.snapshot()` / `backend/app/simulation/INTEGRATION.md` |

> **版管理ルール（齟齬防止）**：本書の**ファイル名はバージョンを含めず固定**（`game_design_document.md`）。版は①この文書管理表の「バージョン」、②タイトル行（`# ゲーム設計書 vX.Y`）、③冒頭注記（先頭の「※ vX.Y は…」）、④巻末フッタ（`*最終更新：… vX.Y*`）、⑤巻末「付録: 変更履歴」、⑥git履歴で管理する。**バージョンを上げてもファイル名・参照リンクは変更しない**ため、CLAUDE.md・README 等の参照が版ごとにズレることがない。
> **部分更新の禁止**：版を上げるときは「①タイトル・②管理表・③冒頭注記・④フッタ・⑤変更履歴を**同一コミットで一括更新**」する。どれか1箇所だけ先行して書き換えない（v1.1→v1.2の移行時に変更履歴だけ先行して版表記が割れた事例の再発防止）。作業途中の版は変更履歴に `(WIP)` と明記し、確定するまでタイトル・管理表・フッタの版は上げない。

### 0.2 正本（source of truth）の優先順位

本書・JSON・コードで記述が食い違った場合、**何を真実とみなし、どちらを直すか**を以下で固定する。

| 対象 | 正本 |
|------|------|
| 設計意図・体験設計・状態遷移・ルールの構造 | **本書（GDD）** |
| 数値（戦闘係数・確率・敵パラメータ・sink・恒久強化） | **`backend/app/data/*.json`** |
| APIレスポンスの実形・フィールド名 | **`engine.snapshot()` / `backend/app/schemas`（Pydantic）** |

- ドリフトを検知したら、上表の**正本でない側を修正**し、巻末「変更履歴」に記録する。
- 本書本文の数表（敵HP表・ゲート確率表など）は**要約・参考**であり、実装は必ずJSONを読む（§20.5）。
- 「矛盾ゼロ」を保証する運用はしない。代わりに**機械検証**でドリフトを検出する。検証器は `backend/app/data/loader.py` の `GameData.validate()`（データロード時に必ず走る fail-fast）＝**実在**。検査項目：敵ID一意／非カオス敵の behaviors weight 合計=100／カオス敵は behaviors 空＋`chaos:true`／`ramp_hit` を持つ敵は `ramp_increment` 必須／mod ID一意／floor の pool ID が実在／アンロック親整合（多親=2親・単親=1親・親の実在）。pytest（`backend/tests/`）でも同じ不変条件を回帰する。
- **未カバーの検査（OPEN-013）**：ゲート確率合計=1.0／dead-end に敵を置かない kind 整合／5F row3→ゲート経路≥2／恒久強化の上限Lv合計=21 は現 `validate()` に無い（§20.5 の検査項目へ追加予定）。

### 0.3 通貨・主要キーの正準（gold / chips）

通貨は実装上3つの呼び名が併存する。本書では**現状を正準として明文化**する（リネームはしない）。

| 層 | 正準名 | 例 |
|----|--------|----|
| 実行時ドメイン / フロント / API | **`chips`** | `player.chips`、`schemas/models.py` の `Player.chips`、`types.ts` |
| 永続・統計スキーマ（RunRecord/DB） | **`gold_*`**（歴史的経緯で保持） | `gold_earned` / `gold_spent`（`db/models.py`） |
| config 内部パラメータ名 | **`gold`** | `config.json` の `gold.floor_multiplier` |
| 恒久強化キー（初期チップ） | **`init_gold`**（歴史的経緯で保持） | `config.permanent_upgrades.items.init_gold` / `ProfileRow.init_gold`（表示は「初期チップ」） |
| UI表示名 | **「チップ」** | ヘッダのチップ残高 |

- **`chips` は実行時の唯一の通貨変数**。`gold_earned`/`gold_spent` は**書き出し専用ミラー**（統計）で、`chips` → `gold_*` の写しは RunRecord 生成・sink 支出記録の1経路のみ。`init_gold`（恒久強化）は**ラン開始時に `chips` へ初期付与**するキー。それ以外で名前を混ぜない。
- 本書本文で「ゴールド」「G」と書いている箇所は**表示・口語表現**であり、内部キーは上表に従う。
- その他の用語揺れも同様に実形へ寄せる：状態フェーズは `phase`（旧 `game_phase`）、ノードのロック状態は `state`（`available`/`locked`/`resolved`。旧 `locked` 単独フラグは廃止）。

## 1. ゲームコンセプト

### 1.1 コアコンセプト

> **「どの敵を選ぶかが未来を変える、確率で削り合うフロア制ローグライト」**

- 分岐するノードマップから**次に戦う敵を選ぶ**意思決定がゲームの核
- 倒した敵によって次に戦える敵がアンロックされ、**選択の連鎖**が生まれる
- 戦闘は確率ベース。攻撃するたびに敵が確率で反応し、**結果はロールで決まる**
- プレイヤーはHPをどれだけ温存して先に進めるかを**常に計算する**

### 1.2 ゲームの目的

カジノタワーの各階層にいる「ゲート（胴元の関門）」を通過して上の階層へ登り続けること。
5フロアのゲートを全て突破して頂上に到達すれば**クリア**。HP0でゲームオーバー（パーマデス）。

### 1.3 プレイヤーの動機

> **「カジノタワーの頂上に待つ"全てを賭けた一勝負"を目指して登り詰める」**

この一文がフレーバーテキスト・死亡/クリア画面・コピーライティング全体の軸になる。

> **テーマ転換**：当初の「地下カジノに潜る」から「カジノタワーを登り詰める」へ変更。UI描画が下から上（row1が画面下、ゲートが画面上）のSlay the Spire型になったことに合わせ、物語も「登る」で一貫させた。

## 2. ゲームループ

### 2.1 マクロループ（ラン間）

```
ゲーム開始
  → [ラン] 1Fから開始 → 探索・戦闘・ビルド構築 → 5Fクリア or HP0
  → クリア時: 恒久強化ポイント（+1）獲得 → 数値強化に割り振り
  → 次ランへ（恒久強化の分だけ有利な状態でスタート）
```

**win-to-progress**：死亡では恒久強化ポイントは得られない。クリアのみが積み上がる。

### 2.2 ミクロループ（ラン内：1フロア）

```
フロア開始
  → マップ表示（ツリー構造。row1の3体のみ選択可能）
  → ノード選択 → phase遷移して「戦闘/宝箱/回復/ゲート」を解決
  → 解決後: アンロック発生 → 次ノードが選択可能になる
  → ゲートを通過 → 次フロアへ
```

## 3. デザインの3本柱

**① 意味のある選択（Meaningful Choices）**
全ての選択肢にトレードオフを持たせる。「とりあえず強い1択」を作らない。

**② 公平なランダム性（Fair Randomness）**
ランダム性は「新鮮さ」のため、公平性は「意思決定の納得感」のため。運だけで死なせない。

**③ 知識が報われる（Knowledge is Power）**
キャラは死んでもプレイヤーの理解は蓄積する。上達実感を最重視する。

## 4. フロア構造とアンロック連鎖

> **描画方向**：ツリーは**下から上へ**描画する（row1が画面下、ゲートが画面上）。プレイヤーは画面下のrow1から選び、上のゲートへ登り詰める（Slay the Spire型）。データ構造の進行（row1→row2→gate）は変わらず、TreeCanvasのy座標を反転するだけ。ロジックには一切影響しない。

### 4.1 ツリー形状（全フロア）

| フロア | 形状 | row1 | row2 | row3 | ゲート経路 |
|--------|------|:----:|:----:|:----:|:---------:|
| 1F | 形B [3, 3] | 3体 | 3体 | — | 1本（固定チュートリアル） |
| 2F | 形A [3, 4] | 3体 | 4体 | — | ≥2本 |
| 3F | 形C [3, 5] | 3体 | 5体 | — | ≥2本 |
| 4F | 形C [3, 5] | 3体 | 5体 | — | ≥2本 |
| 5F | 形D [3, 4, 3] | 3体 | 4体 | 3体 | ≥2本 |

> **5Fゲート1本問題対策**：形Dではrow3（3体）のうち最低2体がゲートへの有効経路を持つことを必須とする。
> **row2の配置**：形Cのrow2（3F/4F）は floors.json の row2_pool から敵プール抽選（RNGストリーム1）で配置を決める。3F/4Fで挙動差はない（旧版の「（抽選）」注記は4Fのみに付いていたが、両者同一のため統一）。**敵プール抽選の対象は敵ノード（多親・非終端単親）のみ。終端単親dead-endには敵を置かず宝箱/回復を配置する**（§4.2）。
> **フロア数**：v1.x では**5フロア固定**。本表・§7.4ゲート表・§20.1 floor_number 等が5前提。将来拡張はデータ駆動で可能だが `game_engine.MAX_FLOOR`・5F専用row3判定・テスト固定値の修正を伴う（§0.4）。

### 4.2 アンロック連鎖ルール（ハイブリッド型）

**基本原則：**
- **多親ノード**：隣接する2体の上位ノードを親に持ち、**いずれか1体を倒すと解放**される（OR/any）→ ゲートへの有効ルート
- **単親ノード**：1体の上位ノードから解放される。子ノードの有無で2種に分かれる：
  - **終端単親（dead-end）**：子ノードを持たない行き止まり。**宝箱・回復のみ**配置（敵は置かない）
  - **非終端単親**：上位rowへ続く子ノードを持つ中継点。**通常の敵ノード**を配置（5F形DのA/Dが該当）

> **データ表現（実装準拠）**：各ノードは `parents`（接続元ノードIDの配列）と `parent_type`（`root`/`single`/`multi`）を持つ（設計上の旧称 `unlock_condition` は実装 `parent_type` に一本化。`multi` が OR/any 解放）。dead-end 判定は「子ノードを持たない単親」で機械的に導出する（`floor_generator.py`。CI検証は §20.5）。
> **多親（ゲートルート）敵の宝箱**：多親ノードは敵ノードだが、**撃破時に確率で宝箱をドロップ**する（`has_treasure`：多親 30%／親が強敵なら +20pt=50%。§11.4）。ドロップ時は `treasure_preview` phase へ入り、通常宝箱と同じく開封/リロールできる（`pending.source="enemy"`）。
> **row2_pool が空の場合（1F）**：多親スロットに割り当てる敵がいないため、多親ノードは**敵のいない `gate_route`（通過専用）ノード**になる。よって 1F は row1×3 のみが敵（=全36体の内訳と一致し、38体にはならない）で、row2 は A=反射確定宝箱・B/C=`gate_route`。B/C いずれかを選んで通過するとゲートへ到達する（§14）。`gate_route` の通過は無料・即 `resolved`。

#### 形A [3, 4] のマッピング

```
row1:   [L]      [M]      [R]
         │ ╲    ╱ │ ╲    ╱ │
         │  ╲  ╱  │  ╲  ╱  │
row2:  [A]   [B]    [C]   [D]

A = L のみ      → 単親 dead-end（宝箱/回復）
B = L + M       → 多親（ゲートルート）
C = M + R       → 多親（ゲートルート）
D = R のみ      → 単親 dead-end（宝箱/回復）
```

#### 形B [3, 3] のマッピング（1F）

```
row1:   [L]    [M]    [R]
         │ ╲   ╱│╲   ╱ │
row2:  [A]   [B]    [C]

A = L のみ      → 単親 dead-end（反射mod確定配置：チュートリアル用）
B = L + M       → 多親（ゲートルート）
C = M + R       → 多親（ゲートルート）
```

#### 形C [3, 5] のマッピング

```
row1:    [L]       [M]       [R]
          │ ╲     ╱ │ ╲     ╱ │
row2:  [A]  [B]    [C]    [D]  [E]

A = L のみ      → 単親 dead-end
B = L + M       → 多親（ゲートルート）
C = M のみ      → 単親 dead-end（中央の宝箱/回復）
D = M + R       → 多親（ゲートルート）
E = R のみ      → 単親 dead-end
```

#### 形D [3, 4, 3] のマッピング（5F）

```
row1:   [L]    [M]    [R]
         │╲    ╱│╲    ╱│
row2:  [A]  [B]   [C]  [D]
         │ ╲  ╱ │ ╲  ╱ │
row3:    [X]    [Y]    [Z]

row1→row2: 形Aと同じ接続（A=単親, B=多親, C=多親, D=単親）
  ※ 形DのA/Dは row3(X/Z) の親を持つ**非終端単親＝敵ノード**（dead-endではない）
row2→row3:
  X = A + B       → 多親（ゲートルート①）／A・Bのいずれか1体で解放（OR）
  Y = B + C       → 多親（ゲートルート②）／B・Cのいずれか1体で解放（OR）
  Z = C + D       → 多親（ゲートルート③）／C・Dのいずれか1体で解放（OR）
  ※ X/Y/Z のうち最低2本がゲートへ接続（4.1の制約を満たす）
```

### 4.3 回復ノードの配置ルール

- row1とrow2の**間**にのみ配置（row2の**終端単親dead-end**に設置）
- **ゲート直前の最終rowには配置しない**
- 1フロアにつき最大**1個**

## 7. ノード・イベント

### 7.1 敵ノード

- 倒すと先のノードがアンロック

### 7.2 宝箱ノード
- `treasure_preview` phaseへ → 「開封する / リロール（30G）」を選択
- リロール：開封前のみ。30G支払い再抽選
- 開封：`treasure_opened` phaseへ。mod確定
- **1宝箱＝1mod**、6種プールから置き戻し抽選、枯渇なし

> **リロールの限界（OPEN-017）**：中身は非公開（§10.3 完全サプライズ）かつ6種iid・置き戻しのため、隠し札と再抽選札は同分布＝**期待値改善0**（「この中身が嫌だから引き直す」判断が原理的にできない死にsinkになりやすい）。加えて **1Fの反射確定宝箱（`fixed_mod`）はリロールしても常に反射**（`treasure_open` は `fixed_mod` を優先）＝30Gの空費。対策（開封前ヒント付与 or リロール廃止／確定宝箱ではリロール非提示）は OPEN-017。

### 7.3 回復ノード
- `heal` phaseへ → 大回復 / 小回復がランダム決定
- 使用は1回限り
- **回復量は固定値**：大回復 +30固定 / 小回復 +15固定
  - max_hpの%ではなく固定値。恒久強化でmax_hpが増える終盤ほど相対的に効果が薄くなる
- **回復sinkとは別系統**：回復ノード＝マップ上・無料・大小ランダム（運任せのドキドキ）／回復sink＝探索/戦闘中・有料（満タン時は不可・§13.2）・大小を選べる。「無料だが運任せ」vs「有料だが選べる」のトレードオフ。ギャンブルテーマと整合
- **回復ノードは満タンでも自動解決**（選択で即 heal・溢れは捨て）。満タン拒否（400）は**回復sinkのみ**。回復ノードで満タン踏みを避けたい場合の disabled 化は UI 側の任意対応

### 7.4 ゲートイベント
- `gate_preview` phaseへ → ゲート保証sink使用可能（重ねがけ可）
- `gate_resolve` phaseで確率テーブルをロール

#### ゲートイベント結果テーブル（フロア別）

| 結果 | 1F | 2F | 3F | 4F | 5F | 被ダメ |
|------|:--:|:--:|:--:|:--:|:--:|------|
| 無傷通過 | 30% | 25% | 20% | 15% | 10% | 0 |
| 小ダメ通過 | 50% | 45% | 40% | 35% | 30% | max_hpの10% |
| 大ダメ通過 | 15% | 25% | 30% | 35% | 40% | max_hpの25% |
| 特殊 | 5% | 5% | 10% | 15% | 20% | 0（被ダメなし） |

> **「特殊」の効果について（実装準拠）**：特殊＝**被ダメ0＋ボーナスチップ +40G**（`config.gate_special.bonus_gold`。`game_engine.gate_resolve` で `chips += bonus_gold`・`run.gold_earned += bonus_gold`）。5Fの特殊20%は「一発逆転の当たり」として無視できない確率質量を持つ。`floors.json` の `gate_damage.special` コメントが言う「次フロア強化等」の**さらなる追加効果は未実装**（現状はチップボーナスのみ）。効果拡張は **OPEN-011**（ゲート特殊効果）で追跡。

> **ゲート通過時の死亡判定（実装準拠）**：被ダメ適用後 `hp = max(0, hp − dmg)`。**HP0なら `dead`（5Fでも `cleared` より優先）**、HP>0かつ1〜4Fなら `next_floor`、HP>0かつ5Fなら `cleared`。特殊ボーナス(+40G)はHP判定前に付与する（`game_engine.gate_resolve`）。

#### ゲート保証（確率シフト型・重ねがけ可）

> **設計思想**：「確実に突破」はゲームバランスを損なうため採用しない。ゲート保証は**大ダメの確率を削るだけ**で、完全な安全は提供しない。

**基本ルール：**
- ゲート保証は**大ダメの確率の一部を、無傷・小ダメへ移す**
- **特殊（当たり）は減らさない**（保証を使っても一発逆転の目は残る）
- 同じゲートで**重ねがけ可能**。ただし効果半減＋コスト微増の二重ブレーキ

**重ねがけの数式：**
```
n回目のゲート保証:
  コスト     = round(50 × (1.5)^(n-1))           ← コスト微増（1.5倍ずつ・round）
  大ダメ削減量 = min(現在の大ダメ率, 25% × (0.5)^(n-1))  ← 効果半減＋下限クランプ
  ※ 削った分は無傷・小ダメへ半々split（各50%）。特殊は維持
```
> **下限クランプ（実装準拠）**：削減量は `min(現在の大ダメ率, 理論削減量)` を取るため、大ダメ確率が**負になることはない**（実装 `gate_resolver.py` の `removed = min(t["major"], reduction)`）。コストは `round` で整数化（§8.6 丸め規約）。

**5Fゲートでの重ねがけ例：**

| 回数 | この回のコスト | この回の削減量 | 大ダメ累計 | 累計コスト |
|:---:|:----------:|:---------:|:--------:|:--------:|
| 0回 | — | — | 40% | 0G |
| 1回 | 50G | -25% | 15% | 50G |
| 2回 | 75G | -12.5% | 2.5% | 125G |
| 3回 | 112G | -2.5%（クランプで2.5%しか削れない） | 0% | 237G |

効果半減で大ダメ削減は収束し、コスト微増で所持チップへの負担が急増する。下限クランプにより大ダメ率は0%まで下がり得るが**負にはならず**、コストが先に尽きるため、チップで完全な安全は買えない。上表は開始時major=40%が上限で大ダメを0%まで消せる例（"最大50%付近"という旧記述は開始major値依存のため撤回）。

> **削減0でも課金される（OPEN-016）**：現実装は大ダメ率が0%に達した後も `gate_guarantee` を重ねがけでき、削減0のままコストだけ課金される（`available_actions` も残高があれば提示する）。「効果0の操作はサーバが拒否」の原則（§22.3）に反するため、大ダメ0%到達時は重ねがけ不可（400）＋アクション非提示に直すのが望ましい。コード変更を伴うため OPEN-016 で追跡。

> ゲート保証（50G）使用時は§13.2のsink一覧にも反映。

## 8. 戦闘フロー

### 8.1 rampとevadeの区別

| 概念 | 性質 | 処理タイミング | データの在り処 |
|------|------|-------------|-------------|
| **ramp** | 状態量（毎ターン増加する蓄積ダメージ） | 攻撃前に状態更新 | 敵の `ramp_value` |
| **evade** | 行動テーブルの一結果（そのターン攻撃をかわす） | 行動ロール後に処理 | 行動テーブルの `weight` |

### 8.2 1ターンの流れ

```
プレイヤーが「攻撃する」or「受ける（guard）」を選択
  ↓
[ramp更新] has_ramp敵（レース系＋カオス）: turns++ → ramp_value = round(base_initial + eff_inc×(turns−1))
           eff_inc = ramp_increment × 加速止め係数（加速止めフックはここ＝ramp更新時に適用）。
           カオスは ramp_increment=0 のため常時 base_initial(=5)。1ターン目=base_initialのみ。§8.5
  ↓
[与ダメ計算] 攻撃: player.attack × stance_multiplier × attack_boost係数（使用時2.0・消費）
             受け: player.attack × stance_multiplier × guard.deal_factor(0.5)（boostは消費しない）
             → 敵HPへ適用
  ↓
[行動ロール] RNGストリーム2から weight比で1回抽選（先読み済みなら先引き値を消費）
      ├ 見切りフックは**ロール前**に evade weight を改変（1枚=半減/2枚=0）
      ├ "none"       → 被ダメ=0
      ├ "counter"    → 被ダメ=敵attack × counter_factor
      ├ "heavy_blow" → 被ダメ=敵attack × heavy_factor
      ├ "evade"      → 与ダメをキャンセル（enemy.hp を巻き戻し）+ 被ダメ=0
      └ "ramp_hit"   → 被ダメ=現在のramp_value
  ↓
[post_damageフック] 順序=重装甲(軽減) →（受けなら incoming × guard.incoming_factor(0.25)）→ player被弾
                   → 反射(counter被弾時 敵へ固定ダメ) → 好機(heavy被弾時 追撃1回)
  ↓
[HP確認] enemy.hp<0→0。敵HP≤0 と プレイヤーHP≤0 が同時なら【勝利優先】（敵撃破を取る）
         player_dead = (player.hp≤0 and not enemy_dead)。player.hp<0→0にクランプ
  ↓
[ログ追記] 全ログ保持（§10.5）
```
> **同時死亡＝勝利優先（実装準拠）**：同一ターンで両者HP≤0になった場合は敵撃破を優先する（`combat_resolver.py` の `player_dead = player.hp<=0 and not enemy_dead`）。反射・好機で敵を倒し切れば、自分が0以下でも勝利になる。**このときプレイヤーHPは0にクランプされる（負値→0）。現状コードはHP1補正をしない**ため、HP0のまま `exploring` へ戻り得る（§1.2「HP0でゲームオーバー」は被弾・ゲート時の判定を指し、勝利優先の同時死亡はその例外）。"HP0でも生存" の違和感を消すために勝利時HPを1へ補正する案は**コード変更を伴うため OPEN-010（§21.2）**として保留。
> **evadeの処理順（実装準拠・注記）**：実装は「与ダメを先に敵HPへ適用 → 行動ロール → evadeなら巻き戻す（`enemy.hp += dealt`）」順。動作は正しいが「適用→巻き戻し」はやや脆い。将来は「行動ロール → evade判定 → 与ダメ算出」の順に整理する余地がある（仕様変更ではなく実装リファクタの候補）。

### 8.3 行動テーブル全タイプ

| タイプ | 被ダメ | 特記 |
|--------|------|------|
| `none` | 0 | |
| `counter` | 敵attack × counter_factor（既定1.0） | 削り合い系の主行動 |
| `heavy_blow` | 敵attack × heavy_factor（既定1.8） | 賭け系。敵ごとに上書き可 |
| `evade` | 0（与ダメも0） | ずれ系の主行動 |
| `ramp_hit` | current_ramp_value | レース系のみ |

> **係数の扱い（フォールバック設計）**：counter_factor / heavy_factor は config.json の全敵共通既定値（1.0 / 1.8）。敵が enemies.json で個別値を持てばそれを優先。コードは `enemy.get("heavy_factor", config["heavy_factor"])`。

**レース系の行動テーブル（全7体共通）：**
```
ramp_hit: 60%   （蓄積値を放出）
counter:  30%   （反撃）
none:     10%
```

### 8.4 戦闘内意思決定（A案改訂：攻撃／受け）

戦闘中のプレイヤー行動は「**攻撃する**」「**受ける（guard）**」の2択（`POST /attack`・`POST /guard`）。意思決定の主体は依然マップ層だが、先読み（yomi/scout）を活かして被弾を抑える戦闘内の攻防選択が加わる。
- **受け（guard）**：与ダメ ×`guard.deal_factor`（0.5）／被ダメ ×`guard.incoming_factor`（0.25、重装甲の軽減後にさらに乗算）。攻撃ブーストは**消費しない**。回数無制限（攻撃を捨てる機会コストが抑制）。数値は叩き台（`config.combat.guard`）。
- `available_actions` は battle 中に `{type:"attack"}` と `{type:"guard"}` を常時提示する。

> **設計意図の追認（OPEN-018）**：当初 A案は「戦闘中は攻撃のみ」だったが、実装は受け（guard）を追加済み。**同一エンジンをbot/UIが共有＝同一行動空間**の原則（§22.3）を保つには bot（`bots.py`）の戦略も guard を行動空間に含める必要がある。guard を正式機能として確定するか、数値・bot代表性を bot 再検証で見極めるかは OPEN-018。フェーズB（スタンス選択）は別軸で将来追加（§12.3・OPEN-006）。

### 8.5 ダメージ式

```
与ダメ = player.attack × player.stance_multiplier
            ↑ stance_multiplierは複数ソースの乗算
            最終 = stance係数(将来) × attack_boost係数(使用時2.0) × …
            現在は通常1.0、攻撃ブースト使用時のみ次の1撃が2.0

被ダメ（counter）  = enemy.attack × counter_factor（既定1.0、敵ごと上書き可）
被ダメ（heavy）    = enemy.attack × heavy_factor（既定1.8、敵ごと上書き可）
被ダメ（ramp_hit） = enemy.ramp_value
被ダメ（evade/none）= 0
最終被ダメ = max(0, 計算被ダメ − 重装甲の軽減値)
```

**ramp_value（蓄積ダメージ）の計算：**
```
ramp_value(n) = base_initial(=5) + ramp_increment × (n − 1)
                    ↑ 全レース敵共通     ↑ 敵ごと（inc=2〜8）
n = そのレース敵との戦闘の経過ターン数
```
- 1ターン目から base_initial(5) 分のダメージを持つ（最初から無害ではない）
- 2ターン目以降は敵ごとのincで個性が出る（inc=2はゆるやか、inc=8は急激）
- **カオス敵も has_ramp**（`EnemyInstance.has_ramp = chaos or 行動にramp_hitを含む`）。カオスは `ramp_increment` を持たない＝0 のため、ramp_hit を引いても被ダメは**常に base_initial(=5)**（None参照の例外にもならず、無害化もしない）。
- 実効 increment は加速止めmodで減衰（`eff_inc = ramp_increment × 加速止め係数`。1枚=×0.5／2枚=×0）

**multiplierの乗算ルール：**
- `stance_multiplier` は複数ソースを掛け合わせる統一経路で実装
- 現在：攻撃ブーストのみ（次の1撃を×2.0）
- 将来：フェーズB（スタンス）が乗る → `compute_multiplier()` に1行足すだけ
- 攻撃的スタンス中にブーストを切ると最大火力（シナジー）。爆発力はbotで監視

### 8.6 数値の丸め規約（実装準拠）

小数が出る計算の整数化は**実装の実態に合わせて `round()` で統一**する。Pythonの `round()` は **ties-to-even（いわゆる銀行丸め）**——`.5` は最近接の偶数へ丸める（例: `round(112.5)=112` / `round(113.5)=114`）。TypeScript側で同一結果が必要な場合は Python互換（ties-to-even）の丸めを実装する。

| 計算 | 丸め | 実装箇所 |
|------|------|---------|
| 与ダメ / 被ダメ（counter/heavy/ramp等） | `round()` | `combat_resolver.py` |
| ramp_value | `round()` | `combat_resolver.py` |
| 敵HPのtierスケーリング | `round()` | `loader.py`（§11.3） |
| ゴールド（チップ）ドロップ・sinkコスト | `round()` | `game_engine.py` |
| ゲート保証コスト・ゲート被ダメ | `round()` | `gate_resolver.py` |
| **重装甲の軽減値** | `int()`（切り捨て）※唯一の例外 | `combat_resolver.py` |
| 回復量（+15/+30固定） | 丸め不要（整数定数） | — |

> 確率（0.0〜1.0）は内部ではfloatのまま扱い、UI表示時のみ百分率へ丸める。

> **重装甲の軽減式（実装準拠）**：`軽減 = int(min(固定軽減値, cap_ratio × base_damage))`。`base_damage`＝そのヒットの**軽減前被ダメ**（`base_inc`）、`cap_ratio=0.5`。`int()` は0方向の切り捨て（TS移植は `Math.trunc` 相当）。被ダメ本体は `round()`（ties-to-even）のため、軽減=`int()`と本体=`round()`が混在する点をPython/TS双方で一致させる。

### 9.1 row制約

> **枠とノード位置の対応**：row1の **枠A=L（左）／枠B=M（中）／枠C=R（右）**（§4.2のL/M/Rに対応）。

**row1**：枠A(L)=削り合い、枠B(M)=賭け、枠C(R)=レース/ずれ/カオス
**row2**：同一体験タイプは最大2体まで
**row3（5F）**：カオス以外を最低1体含める

> **1Fは枠規則の対象外**：1Fは固定配置（§14）で枠C(R)=賭け（乱れ打ちの賭博師）。枠規則は**2F以降の生成フロア**に適用する（row制約をCI検証へ落とす際は1F固定配置を除外する）。

### 9.2 カオスタイプ設計（ランごとシード決定型）

カオス敵の行動テーブル比率は**ランごとにシードから決定**する。
「このランのカオスは何が来やすいか」を遊びながら読む体験になる。

```
ラン開始時、各カオス敵について（実装: chaos_weights.py）:
  対象4種 = {counter, heavy_blow, evade, ramp_hit}
  各種に最低保証 _FLOOR_PT = 5 を確保（合計20）→ 残り80を分配
  分配比率は 真の Dirichlet(1,1,1,1)（＝単体上の一様分布）:
    RNGストリーム8から U を引き、Gamma(1)=Exp(1) サンプル X = −ln(1−U) を4本生成し総和で正規化
  整数化の端数は最大剰余法(Hamilton)で配る（系統的偏りを作らない）
  → behaviors と同じ形式 list[(type, weight)]、weight合計=100 を返す
  消費する乱数は敵あたり4回（id昇順で消費＝決定論）
```

> **実装の補足**：旧実装の「一様値をそのまま正規化」は単体の中心へ集中し『heavy偏重/evade偏重』が出にくかったため、真のDirichletに修正済み（ランごとの偏りが出やすい）。なお最低保証 5pt×4=20 を引いた残り80をDirichlet配分するため、各カテゴリの取り得る範囲は **5%〜85%**（特定カテゴリが総量の過半に寄るランも一定割合で出る）。weightは **合計100の整数**（"合計1.0に正規化"ではない）。
> 同一ラン内では一貫しているため「学習可能」。ラン間では変わるためリプレイ性が出る。
> **決定論の担保（実装準拠）**：カオス比率は**サーバ（Python）が確定**し敵の behaviors を構築する内部データ。`snapshot()` には **`chaos_weights` を含めない**ため TS が再計算する余地はなく、言語間の `log` ビット差を心配しなくてよい。退化（Dirichletサンプル総和0）は均等配分（各25＝5+20）へフォールバック。整数化端数は小数部の大きい順（Hamilton最大剰余法）で配る。ストリーム8の消費は敵あたり4回・id昇順（決定論）。
> **ロスター変更時の再現性（注意）**：stream8 を **id昇順で敵ごと4回**消費するため、カオス敵の追加・id変更は以降のカオス敵の消費位置をずらし、**過去seedの再現が変わり得る**。長期的には `master_seed + enemy_id` から個別サブシードを導出する方式が安全（OPEN-013 の再現性検査に含める）。

### 10.1 modリスト（6種）

> **id列が正準キー**：`id`（romaji）が API・RunRecord・`mods.json` の正準キー。日本語の「mod名」は表示専用（フロント `labels.ts` の `MOD_LABEL` が対応）。

| id | mod名 | 効果（1枚） | スタック時（2枚） | 影響先 |
|----|-------|-----------|--------------|------|
| `mikiri` | **見切り** | evade weightを50%削減 | evade weight=0（完全無効化） | 行動テーブル weight |
| `kasoku_dome` | **加速止め** | ramp_incrementを50%削減 | ramp_increment=0 | ramp更新 |
| `juso` | **重装甲** | counter/heavy被ダメを固定値軽減 | 軽減値加算（上限base_damageの50%）| 被ダメ計算 |
| `hansha` | **反射** | counter被弾時に追加ダメを敵へ | 追加ダメ値加算 | 被ダメ処理後 |
| `yomi` | **先読み** | 各戦闘1ターン目行動を事前公開 | 2ターン目まで公開 | 情報開示 |
| `kouki` | **好機** | heavy_blow被弾時に追加攻撃1回 | クールダウン短縮（毎ターン可）| 被ダメ処理後 |

> **好機（kouki）の追撃仕様（実装準拠）**：heavy_blow 被弾時、`追撃 = round(player.attack × stance_multiplier)` を敵へ1回（**攻撃ブーストは乗らない**）。敵の行動テーブルは再ロールしない（フリーヒット）。クールダウンは 1枚=1（発動翌ターン以降に減衰）／2枚=0（毎ターン可）。post_damage フックで反射の後に処理。
> **重装甲（juso）の上限（実装準拠）**：`軽減 = int(min(固定軽減値, 0.5 × base_damage))`。`base_damage`＝そのヒットの軽減前被ダメ（§8.6）。
> **見切り（mikiri）の再配分（実装準拠）**：evade weight を係数倍（1枚×0.5／2枚×0）するだけで、行動ロールは `weighted_index` が**その時点の総和で正規化**する。よって削減分は「明示的に none へ寄せる」のではなく、**残り全行動（evadeの残分含む）へ比例的に再配分**される（合計weightが100未満でも正しく動く）。

### 10.4 modインタラクション（拡張スキーマ）

矛盾・シナジーを以下のスキーマで管理する。`type` と `is_intended` を持たせ、後からシナジー行を追加できる構造。

```
mod_interactions: [
  {
    mods: ["mikiri", "yomi"],
    type: "cancel",
    behavior: "先読みでevade予告されても与ダメ0は発生しない（見切り優先）。先読みは『evadeが来ない』確認のみ",
    is_intended: true
  },
  {
    mods: ["mikiri", "kouki"],
    type: "synergy",
    behavior: "evade weight=0により相対的にheavy_blowが来やすくなり、好機の発動頻度が上がる",
    is_intended: true
  },
  {
    mods: ["hansha", "juso"],
    type: "synergy",
    behavior: "被ダメ軽減後の値に反射追加ダメを乗せる。あえてcounterを受ける『被弾上等』立ち回りが成立",
    is_intended: true
  }
]
```
> ※ `mods` の値は **mod id**（`mods.json` も id で記述）。本文の効果文は §10.1 の日本語名で可読化している。
> **cancel（mikiri×yomi）の正確な挙動**：見切りは evade **weight を改変**するだけ（1枚=半減／2枚=0）。よって **2枚**なら evade は出ず先読みの evade 予告も起きない（cancel 成立）。**1枚**なら evade は半減で残り、出れば与ダメ0は発生する。上の `behavior` 文（mods.json 由来）は2枚時を要約したもので、1枚時は「evade予告が出にくくなる」が正確。効果文の最終正本は mods.json（表示用）で、文言精緻化は人間レビューに委ねる。

**運用方針（面白さの非対称な扱い）：**
- **死にmod**（腐る組み合わせ）：統計で検出して**潰す**
- **壊れmod**（爆発する組み合わせ）：統計で検出するが**残す**（クリア率を破壊するレベルのみ調整）
- `±8pt`の寄与制約は「常時の平均寄与」であり、「引けたときの爆発力」は均さない

**拡張性：** modを追加する際は「攻撃前/行動ロール後/被ダメ計算後」のフックに効果ハンドラを差し込むだけ。インタラクションは `synergy` 行を足すだけで「狙って組みたい組み合わせ」を増やせる。

### 10.5 コンバットログ（表示専用・使い捨て）

- 戦闘中の全ログを保持し、スクロールで遡れる（表示行数はUI側で調整、デフォルト8行）
- **combat_logは表示専用・使い捨て**。戦闘終了で破棄してよい。統計には使わない
- **RunRecordとは同期しない**（別目的のため）。combat_log=表示、RunRecord=統計と役割を完全分離
- これによりログのズレるバグ（表示は勝利・記録は敗北等）が構造的に起きない

> **ログ二重管理の解消**：combat_log（表示・使い捨て）とRunRecord（統計・永続）を別物として扱う。将来リプレイ機能が必要になっても**ログの永続保存は不要**——ただし再現には **seed に加えてプレイヤー操作履歴とデータ版が必要**（§19.2）。seed は RNG ストリームを再現するだけで、プレイヤーの選択分岐までは再現しない点に注意。

### 11.4 強敵リワード

強敵（`difficulty ≥ config.strong_enemy.difficulty_threshold`＝暫定4）を倒すと：
- ゴールド（チップ）ドロップ **×1.5**（floor_multiplierと重複適用）
- 宝箱確率 **+20pt（絶対値加算）**

宝箱の出現には**2つの経路**がある（`floor_generator.py`）。+20pt は「その宝箱に紐づく敵が強敵か」で判定する：

| 経路 | ノード種別 | 基準確率 | 強敵込み（+20pt） | 判定に使う敵 |
|------|-----------|:------:|:--------:|------|
| **撃破ドロップ** | 多親（敵ノード） | 30% | 50% | その多親の敵自身 |
| **dead-end宝箱** | 終端単親dead-end | 60% | 80% | dead-end を解放した親（=直前に倒した敵） |

> - **撃破ドロップ**：多親（ゲートルート）の敵を倒したとき、生成時抽選の `has_treasure` が真なら宝箱が出る（§4.2）。「単親dead-end 60%…強敵撃破後80%」の“撃破対象”は dead-end 自体ではなく**その親（解放時に倒した敵）**を指す。
> - **dead-end宝箱**：終端単親dead-end のノード自体が宝箱（`has_treasure` 真=中身あり／偽=空）。回復ノードに選ばれた dead-end は宝箱にならない（1フロア最大1回復・§4.3）。
> 「+20%」（相対）ではなく「+20pt」（絶対値加算）。30%→50%（×1.2の36%ではない）。
> 1F は `fixed_layout` のため撃破ドロップは無効（`drop_enabled=false`）。宝箱は A の反射確定1個のみ。

### 12.3 恒久強化システム（メタ進行・OPEN-002）

**仕組み：** ポイント割り振り型。1クリア=1ポイント獲得。5項目に自由配分。

| 強化項目 | 1レベルあたり効果 | 上限Lv | 最大累計 |
|---------|---------------|:----:|--------|
| +max_hp | +10 | 5 | +50 |
| +attack | +2 | 5 | +10 |
| +初期チップ（init_gold） | +15G | 5 | +75G |
| +gold_drop率 | +10% | 3 | +30% |
| -sinkコスト | -5G | 3 | -15G |

- 全項目MAX＝**21点**（上限Lv合計 5+5+5+3+3=21）＝**21クリア**で満額。**旧記述「26点/26クリア」は算術誤り**（config.json のコメントにも同じ26誤記が残るため human レビューで訂正）。ポイント数は `max_level` 合計から機械導出し手書きしない（「上限Lv合計＝満額ポイント」をCI検証・§20.5）。
- 数値はデータ駆動で調整、上限レベルの構造は確定
- **永続（実装準拠）**：メタ進行は DB の `ProfileRow`（`id=1` 固定・単一プロファイル）に保持（`points`＋各Lv `max_hp/attack/init_gold/gold_drop/sink_cost`）。`POST /run/new` が `crud.profile_levels()` を読んで初期 GameState へ反映し、`POST /upgrade`（`crud.allocate_upgrade`）が Profile へ恒久書き込み、クリア確定時に `award_points(+1)`。win-to-progress はこの経路で成立（§20・§25）。認証は非スコープ（単一プロファイル）＝§0.4。
- **余剰ポイント**：全項目が上限Lvに達した後は `allocate_upgrade` が拒否（400）し、`points` は余剰として貯まる（将来項目用のバンキング）。UpgradeAllocator は残ポイントありかつ未上限項目がある時のみ [+] を出す。
- **拡張性**：強化項目はテーブル定義。後から項目追加が容易

**フェーズB（スタンス）予約事項：**
- ダメージ計算は必ず `attack × multiplier` の形で記述（直接代入禁止）
- RNGストリームに `stance`（番号6）を予約
- フェーズB追加時は統計再検証が必要（想定済み）

## 13. チップ経済システム

> 本章ではプレイヤー通貨を「チップ」と呼ぶ（§0.3）。本文に残る「ゴールド/G」は表示上の名残で、内部キー・統計は歴史的経緯により `gold_*`/`init_gold` を維持する。

### 13.1 獲得（フロア別期待値、叩き台）

| フロア | 1F | 2F | 3F | 4F | 5F | 累計 |
|-------|:--:|:--:|:--:|:--:|:--:|:---:|
| 期待値 | 15-25G | 25-40G | 35-55G | 45-65G | 55-75G | 175-260G |

### 13.2 Sink一覧と使用タイミング

| sink | コスト | 効果 | 使用タイミング | 種別 |
|------|:-----:|------|------------|:---:|
| スカウト | 15G | 次ターン行動先読み（強敵戦で輝く） | **battle時のみ** | 守り |
| 小回復 | 20G×フロア係数 | **+15固定**回復 | **exploring/battle**（満タン時は不可＝400・`available_actions` 非提示） | 守り |
| 大回復 | 40G×フロア係数 | **+30固定**回復 | **exploring/battle**（満タン時は不可） | 守り |
| ゲート保証 | 50G×(1.5)^(n-1) | 大ダメ確率を削る（重ねがけ可・特殊維持） | **gate_preview時のみ** | 守り |
| 宝箱リロール | 30G | 宝箱を開封前に引き直し | **treasure_preview時のみ** | 守り |
| **攻撃ブースト** | 30G（叩き台） | **次の1撃のみ attack +100%** | **battle時のみ** | **攻め** |

> **「sink」と「/sink API」の別**：本表は**チップ消費アクション**の一覧。API的には回復/スカウト/攻撃ブースト/ゲート保証が `POST /sink`、**宝箱リロールのみ専用ルート `/treasure/reroll`**（§25.2）。
> **攻めのsink追加**：従来のsinkは全て「リスクを減らす」守りだった。攻撃ブーストは唯一の「攻め」のsink。次の1撃だけ `stance_multiplier` に **×2.0 を乗算**する（ダメージ式 `attack × stance_multiplier` は複数ソースの積。boost はその一因子）。

#### 回復コストのフロア係数

| | 1F | 2F | 3F | 4F | 5F |
|---|:--:|:--:|:--:|:--:|:--:|
| 小回復 | 20G | 25G | 30G | 35G | 40G |
| 大回復 | 40G | 50G | 60G | 70G | 80G |

終盤は回復が高額化し、無限回復ができなくなる。回復量固定（§7.3）と合わせて、終盤は「大きく削られて・少ししか回復できない」緊張感を作る。

#### スカウトの位置づけ

- 通常敵：15Gで次1ターン先読みは割高に感じる（使わなくても対処可能）
- 強敵戦（difficulty≥4）：「次にheavy_blowが来るか」を読む命綱になり、同じ15Gが安く感じる
- 暗黙知型（確率非公開）だからこそ、強敵の読めない恐怖に対して情報を売る価値が出る
- 攻撃ブーストとのシナジー：スカウトで危険を察知 → ブーストで先に倒し切る

#### 攻撃ブーストの設計意図

- レース系の敵に刺さる（早く倒せばramp_hitを受ける回数が減る）
- 強敵を早期決着させ被ダメ機会を減らす
- 「攻撃ブーストで早期決着 vs 回復でHP管理」の2戦略が生まれる
- 実装：次の1撃だけ `stance_multiplier` に ×2.0 を**乗算**（`config.attack_boost.multiplier`）。フェーズB（スタンス）と同じ計算経路（複数ソースの積）に乗る

#### sink コストとエッジケース（実装準拠）

- **-sinkコストの適用**：全 sink 共通に `最終コスト = max(0, round(base − 5×sink_costLv))`（`_sink_cost`）。回復は `base×フロア係数`、ゲート保証は `50×1.5^(n-1)` を base とし、割引は**最後に**減算する。
- **scout 無料化（OPEN-019）**：scout base=15 に対し sink_costLv=3 で −15 ⇒ **0G＝実質無料**（下限が `max(0,…)`）。毎ターン無料先読みは暗黙知型（§5）の緊張を崩すため、下限を 1G にクランプ（`max(1,…)`）するのが望ましい。要コード変更＝OPEN-019。
- **heal sink は battle 中ターンを消費しない（OPEN-020）**：`use_sink('heal_*')` は敵の行動ロールを誘発しない（`resolve_turn` を呼ばない）。被弾しそうな局面で攻撃せず回復を連打でき（チップが続く限り）戦闘リスクが下がる。クリア率25-40%と整合させるなら「battle中の heal も1ターン消費＝敵が反応」に寄せる案がある。設計判断＋コード変更＝OPEN-020。
- **攻撃ブーストの異常系（OPEN-021）**：(1) ブースト適用の1撃が evade で巻き戻ると boost は**消費済み**（`attack_boost_pending=False`）なのに与ダメ0＝30G丸損。(2) `attack_boost_pending=true` 中に `/sink attack_boost` を直POSTすると再課金（`available_actions` は非提示だがサーバ側 guard 無し）。持ち越し/返金・pending中の400拒否は OPEN-021（§25.4 異常系へも追記）。

### 13.3 貯め込み逓減（問F＝自然解決）

- 所持上限なし・減衰なし
- sinkを使わないと死にやすい難度設計で「使った方が得」を自然に成立させる
- Phase4で「ゴールドをほとんど使わずクリアするランの割合」を監視
- 多すぎる場合のみ対策（上限/減衰）を後から検討

## 17. 乱数アーキテクチャ

### 17.1 アルゴリズム
- **SFC32**（32bit）をPython・TypeScript双方で同一実装
- 同一シードで同一結果を黄金テストで確認
- **SFC32 はゲーム再現用**（決定論）であり、**秘密・トークン生成には使わない**（暗号用途ではない）。session_id 等の秘密は `secrets` 等で別途生成する

### 17.2 ドメイン別独立ストリーム

| ID | 用途 |
|:--:|------|
| 0 | フロア生成（ツリー・ノード配置） |
| 1 | 敵プール抽選 |
| 2 | 行動テーブルロール |
| 3 | 宝箱mod抽選 |
| 4 | 回復ノード（大/小） |
| 5 | ゲートイベント結果 |
| 6 | **stance（予約・未使用）** |
| 7 | 汎用 |
| 8 | **chaos（カオス敵の行動比率決定）** |

> **消費契約（実装準拠）**：`floor_generator` は stream0（FLOOR）で終端単親dead-endの宝箱presence、stream1（ENEMY_POOL）で敵配置shuffle、stream4（HEAL）で回復ノード選択、**stream7（GENERAL）で多親敵の撃破ドロップpresence**を引く。戦闘は stream2（BEHAVIOR）、宝箱の中身mod抽選は stream3（TREASURE）、ゲート結果は stream5（GATE）、カオス比率は stream8（CHAOS・敵あたり4回・id昇順）。stance（6）は予約・未使用。
> **先読みの消費（yomi/scout）**：yomi は `prepare_preview` が **stream2 から次行動を先引きしてキャッシュ**（`pending_action`）し、実ターンの `resolve_turn` がそのキャッシュを消費する（＝先読みが嘘にならない・二重消費しない）。scout は `top_behavior`（最大weightの示唆）を返すだけで**RNGを消費しない**。
> **stream7（汎用）の用途限定**：現状は多親敵の撃破ドロップpresenceに使用。再現性に影響する新用途は専用ストリームを割り当て、汎用へ混ぜない（§17.1「ストリームを混ぜない」）。

### 17.3 シード管理・ストリーム導出（実装準拠）
- 各ストリームは master seed から **`derived = master_seed ^ (stream_id × 0x9E3779B9)`（32bitマスク）** で種を分け、`Sfc32(derived)` を構成する（splitmix32 で a,b,c,d を充填 → 15回 warmup）。互いに独立。
- SFC32 本体・種導出・warmup 回数を含め **Python/TS で同一実装**にし、golden vector（`tests/test_rng.py`）へ一致させる（TS版の用途は §18.5）。
- botシミュレーションは固定シードパネル（seed 0〜999）で再現性を担保。
- **seed の範囲・生成**：`0 ≤ seed ≤ 2^32−1`（Pydantic `conint(ge=0, le=2**32-1)` で検証推奨）。未指定時はサーバが `secrets.randbits(32)` で生成。
- **seed・rng_streams は API 出力に含めない**（不変条件）。ただし `run_id = "run-{seed}"` はラン**終了後**の RunRecord にのみ現れる（進行中は snapshot.run_record=null のため seed は露出せず、seed-scum を防ぐ）。`snapshot()` にも含まれず、同一SFC32実装で全ロールを事前計算されて暗黙知/スカウト経済が崩れるのを防ぐ。スナップショットテストで両キーの非存在を assert する（§20.5）。

## 18. バランス検証フレームワーク

### 18.1 合格条件

| 指標 | 目標（効果量ベース） | 状態 |
|------|------|:---:|
| **強プレイのクリア率** | **25〜40%**（bot強化状態を固定して測定） | ★確定 |
| ランダムプレイのクリア率 | 1〜5% | 暫定 |
| スキル幅（強−ランダム差） | クリア率差 ≥ X pt（CI下限が0を跨がない＋最小効果量） | 併走 |
| 初手別クリア率差 | ±5pt以内（最大−最小の効果量で判定） | 暫定 |
| 選択感度 | 効果量 ≥ Y pt（p値のみで判定しない） | 併走 |
| 死亡フロア分布 | 終盤集中は許容。最終フロア以外の単一フロアが死亡の Z% を超えない | 暫定 |
| 単一mod寄与 | ±8pt以内（平均寄与のみ） | 暫定 |
| modペア寄与（synergy） | 主要ペアの交互作用が ±W pt 以内 | 暫定（追加・OPEN-023） |

> **有意性ハック回避（§18.4 Goodhart）**：bot大量試行では n が大きく僅差でも p<0.05・CI0非跨ぎを満たすため、スキル幅・選択感度・初手差は**最小効果量（X/Y pt）を CI下限とともに要求**する（`balance_stats.py` の TOST=同値検定も併用）。
> **死亡フロア分布**：難度ランプのあるパーマデスでは終盤集中が正常。「集中しない」は偽陽性を生むため、終盤集中を許容し「最終フロア以外の単一フロアが過度に偏らない」基準へ置換。
> **クリア率帯の測定条件**：帯（25-40%）は bot の `permanent_upgrades_state` に依存する（+attack等は全戦闘を短縮）。**未強化パネルを基準**とし、フル強化は別帯で管理（bot 強化状態を固定して測る）。
> **strong戦略の版固定**：クリア率帯は strong bot の賢さに対する相対値。`strategy_version` で strong 戦略を凍結し「確定帯は当該版に対してのみ有効」とする（戦略変更時は帯を再検証）。**バランス検証全体が bot の人間代表性に依存する**点は運用上の前提として明記。

## 19. テレメトリー（RunRecord）

### 19.1 スキーマ（全フィールド採用）

```
RunRecord:
  # ラン識別
  run_id: string               # = "run-{seed}"（session_id=uuid とは別物・同一seedで衝突し得る）
  seed: int
  timestamp: datetime          # 実装では created_at（DB server_default=now）として永続化

  # 結果
  cleared: bool
  floor_reached: int          # 1〜5
  total_turns: int

  # プレイヤー
  final_hp: int
  mods_acquired: string[]      # 取得modのリスト

  # 経済
  gold_earned: int
  gold_spent: { scout: int, heal_small: int, heal_large: int,
                gate_guarantee: int, treasure_reroll: int,
                attack_boost: int }    # 攻めのsink
  gate_guarantee_stacks: int           # ゲート保証の重ねがけ回数（合計）

  # 戦闘詳細
  enemies_defeated: [
    { enemy_id: string, experience: string, floor: int, turns: int }
  ]                            # 体験タイプも記録（mod×敵の化学反応分析用）
  death_cause: string | null   # "敵id:行動タイプ" または "gate:結果"（ゲート死。例 gate:major）
  death_floor: int | null

  # 統計用
  bot_type: string             # "strong" / "random"
  permanent_upgrades_state: { max_hp: int, attack: int,
                              init_gold: int, gold_drop: int, sink_cost: int }
```

> **フィールド定義の明確化（実装準拠）**：
> - `run_id = "run-{seed}"`。`session_id`（uuid・`session_store`）とは**別物**で、同一seedを使う bot パネルでは run_id が衝突し得る（`RunRecordRow.run_id` は index で unique 制約なし）。ラン⇄セッションの紐付けは §25。
> - `mods_acquired` は同mod複数取得を**重複保持（取得順）**。`total_turns` は戦闘ターン総和。`permanent_upgrades_state` の各intは**レベル値**（0〜上限Lv）。`bot_type` は `human`/`strong`/`random`。`enemies_defeated[].experience` は**日本語文字列**（§20・OPEN-012）。
>
> **不足フィールド（要追加・コード変更）**：
> - **`data_version`（OPEN-024）**：4JSONの内容ハッシュ or 版文字列。敵HP/gold/sink/恒久強化はPhase1〜4で調整中で、`/stats/history` に版違いレコードが混ざると統計が壊れる。全統計クエリを版でフィルタするため必須。現 `RunRecordRow` に無い。
> - **sink別 `use_count`（OPEN-025）**：回復は `20〜40G` とフロア係数で単価変動し -sinkコスト割引も掛かるため、`gold_spent` 合計から**使用回数を復元できない**。Phase4 の sink ROI（回数×効果）に必要。`gate_results`（per-floor：結果＋被ダメ）も同様に未記録で、特殊発生率・保証ROIの検証に要る。

### 19.2 用途
- Phase2以降の全統計検証の入力
- `enemies_defeated`に体験タイプを含むため「ずれ系敵が出ないランで見切りが腐ったか」を検出可能
- **リプレイ機能の前提（注意）**：combat_log は表示専用・非永続（§10.5）。将来リプレイを実装する場合、再現に必要なのは **seed＋プレイヤー操作履歴（選択ノード・sink使用・攻撃・宝箱開封/リロール・ゲート保証回数）＋データファイル版**。**seed だけでは操作分岐を再現できない**ため、その時点で操作履歴の永続化を別途追加する（現状RunRecordには操作履歴を保存していない）。

### 22.2 技術選定一覧

| レイヤー | 技術 | 選定理由 | 将来の移行先 |
|---------|------|---------|------------|
| フロントエンド | React + TypeScript + Vite | デファクト・起動が速い | — |

| DB | SQLite | 設定ゼロ・ローカル開発に最適 | PostgreSQL |
| 通信 | REST API | ターン制と相性◎・botと同じエンジンを使える | — |
| リポジトリ | モノレポ | 管理が楽・ポートフォリオで見せやすい | — |

### 22.3 設計原則（移行容易性の確保）

実装開始時点から以下を守ることで、将来の技術移行コストを最小化する。

| 原則 | 目的 |
|------|------|
| ゲームロジックは全てPython。Reactは計算・勝敗判定しない | botシミュレーターとUIで同じエンジンを共有 |
| UIは `available_actions` を**操作可否の正本**にする | フロントの条件分岐を排し、含まれない操作は非表示/disabled（§25.3） |
| phase不整合の拒否はサーバ側で必ず行う（§25.4） | クライアント改ざん・不正遷移への防御 |
| API通信は `gameApi.ts` に集約（直接fetchしない） | TanStack Query移行時にこのファイルだけ変更 |
| DB操作はSQLAlchemy経由（生SQLを書かない） | PostgreSQL移行コストを最小化（型・並行性差＝JSON列/`server_default`/autoincrement 等の検証は別途必要。「1行で移行」は楽観表現のため撤回） |
| ダメージ計算は `attack × multiplier` で記述 | フェーズB（stance）追加に備える |

## 25. APIエンドポイント仕様

### 25.1 設計方針

- ゲームの全ロジックはバックエンド。フロントは操作を送って新しい状態を受け取るだけ
- 各レスポンスは**完全なゲーム状態**を返す（フロントは差分計算不要）
- `session_id`（uuid）でランを識別。**進行中の GameState は `session_store` がプロセス内メモリで保持**し、DBへは**確定 RunRecord と Profile のみ**を永続化する（`session_store.py`）。**サーバ再起動で進行中ランは失われる**（単一プロセス前提・OPEN-007/026）。`GET /run/{id}`（再開）は同一プロセス生存中のみ成立。旧記述「DBに永続化」は実態と不一致だったため訂正。
- **完全状態返却の例外**：`/upgrade`・`/profile/upgrades` は `UpgradeState`、`/catalog/mods` は `ModCatalogItem[]`、`/stats/history` は `RunRecord[]` を返す（原則6の明示的例外）。

### 25.2 エンドポイント一覧

| メソッド | パス | 用途 | リクエスト | レスポンス |
|---------|------|------|----------|----------|
| POST | `/api/run/new` | 新規ラン開始 | `{ seed?: int, bot_type?: str }` | `GameState` |
| GET | `/api/run/{session_id}` | 状態取得（再開・同一プロセス生存中） | — | `GameState` |
| POST | `/api/run/{session_id}/select-node` | ノード選択 | `{ node_id }` | `GameState` |
| POST | `/api/run/{session_id}/attack` | 攻撃 | — | `GameState` |
| POST | `/api/run/{session_id}/guard` | 受け（防御・§8.4） | — | `GameState` |
| POST | `/api/run/{session_id}/sink` | sink使用 | `{ sink_type }` | `GameState` |
| POST | `/api/run/{session_id}/treasure/open` | 宝箱開封 | — | `GameState` |
| POST | `/api/run/{session_id}/treasure/reroll` | 宝箱リロール | — | `GameState` |
| POST | `/api/run/{session_id}/gate/resolve` | ゲート通過 | — | `GameState` |
| POST | `/api/run/{session_id}/continue` | モーダルphase前進（treasure_opened/heal/next_floor→exploring） | — | `GameState` |
| POST | `/api/run/{session_id}/upgrade` | 恒久強化割り振り | `{ upgrade_type }` | `UpgradeState` |
| GET | `/api/profile/upgrades` | 恒久強化状態（ClearedPage初期表示） | — | `UpgradeState` |
| GET | `/api/catalog/mods` | mod効果文カタログ（表示の正本） | — | `ModCatalogItem[]` |
| GET | `/api/stats/history` | RunRecord履歴 | `{ limit?: int=50 }` | `RunRecord[]` |

> **sink_typeの値**：`scout` / `heal_small` / `heal_large` / `gate_guarantee` / `attack_boost`（実装の `use_sink` が受け付ける値）。
> **宝箱リロールは専用ルート**：`/treasure/reroll` のみで実行する。`/sink` に `treasure_reroll` を渡すと **400**（実装は `use_sink` で未対応）。※ RunRecord の `gold_spent.treasure_reroll`（§19.1）はチップ消費の記録カテゴリとしては残る。
> **ゲート保証の重ねがけ**：`sink_type: "gate_guarantee"` を `gate_preview` phaseで複数回POSTできる。サーバーが現在の重ねがけ回数 `n` を保持し、コスト `50G×1.5^(n-1)` と削減量 `25%×0.5^(n-1)` を計算してGameStateに反映。ゴールド不足時は400を返す。
> **攻撃ブースト**：`sink_type: "attack_boost"` は `battle` phaseでのみ有効。次の `attack` 1回だけ `stance_multiplier` に ×2.0 を**乗算**（`guard` では消費しない）。
> **UpgradeState の形**：`{ points:int, levels:{max_hp,attack,init_gold,gold_drop,sink_cost}, maxes:{…} }`（`UpgradeStateResponse`）。`/upgrade`・`/profile/upgrades` が返す。理想は `/upgrade` も完全GameState（＋upgrade_state内包）だが現状は UpgradeState 単体（原則6の例外）。
> **冪等性・認証は非スコープ（OPEN-026）**：全 mutating POST に Idempotency-Key・state_version は無い。再送で `gate_guarantee` 二重課金・`/attack` 二重進行（RNGドリフト）が起き得る。単一プレイヤー・ローカル前提では実害限定だが、公開時は冪等キー＋楽観ロック＋所有者照合を必須化。`/stats/history` は無条件全件（`limit`のみ）＝スコープ化（client_id）＋件数上限を追跡。

### 25.3 GameStateレスポンスの形

> **実装に追随した版**。下記が `engine.snapshot()` の実形。過去ドラフトからの変更点：
> - `player.gold` → **`player.chips`**（§16.2 テーマ読替＝チップ）。`attack_boost_pending` を追加。
> - `floor` は `tree_shape`/`edges` 配列ではなく **`nodes`（id→ノードの dict）**。辺は各ノードの **`parents`** で表現し、`tree_shape` は floors.json 側の定義に集約。`locked` 単独フラグは廃止し **`state`（available/locked/resolved）** に統一。
> - トップレベルの `combat_log`/`available_sinks` は廃止 → ログは **`battle.log`**、sink候補は **`available_actions`（cost付き・上位互換）** に統合。

### 25.4 エラーハンドリング

| ステータス | 意味 |
|----------|------|
| 400 | 不正な操作（ロック中ノード選択・チップ不足・未対応sink_type等） |
| 404 | session_idが存在しない |
| 409 | phase不整合（戦闘中にノード選択等） |

**phase不整合の例（サーバ側で必ず拒否＝409）**：フロントで防いでいてもバックエンドの防御は必須。

| 現在phase | 不正操作 | 返す |
|----------|---------|:---:|
| `battle` | select-node | 409 |
| `exploring` | attack / treasure・gate系 | 409 |
| `treasure_opened` | treasure/reroll | 409 |
| `gate_resolve` | select-node / attack | 409 |
| `dead` / `cleared` | attack / sink / select-node | 409 |

> sink の許可phaseは §13.2 準拠（scout/attack_boost=battle、gate_guarantee=gate_preview、reroll=treasure_preview、回復=exploring/battle）。許可外phaseでの sink は **409**（`WrongPhase`）で拒否。

> **判定順（実装準拠）**：`get_engine_or_404`→**404**（session不在）／`WrongPhase`→**409**（phase不整合）／`InvalidMove`→**400**（ロックnode選択・不在node_id・チップ不足・満タン回復・未知sink/upgrade項目）。**チップ不足・ロックnode は 400**（`InvalidMove`）である点に注意（資源不足を422で別立てするかは将来）。
> **select-node の異常入力**：不在 node_id・前フロアの stale id（現フロア `nodes` に無い）は **400**、解決済み/ロック中の再選択も 400（`node_state != available`）。node_id はフロア間で L/M/R を再利用するが、フロア遷移で `resolved` リセット＆ `nodes` 再生成のため stale id は現フロアに無く 400 になる。
> **攻撃ブーストの二重課金（OPEN-021）**：`attack_boost_pending=true` 中の `/sink attack_boost` 再POSTは現状サーバ側 guard が無く再課金し得る（`available_actions` は非提示）。400（無効）で弾くのが望ましい。
> **エラーbody構造（OPEN-026）**：現状はHTTPステータスのみ。`{error_code, message, req_id}` で構造化し ErrorToast の分岐・ログ集計に載せるのが望ましい（運用・別タスク）。

### 25.5 型共有

`backend/app/schemas/api_schemas.py`（Pydantic）と `frontend/src/api/types.ts`（TypeScript）で同じ型を定義。
将来的にはOpenAPIスキーマからTypeScript型を自動生成することも可能（FastAPIがSwaggerを吐くため）。
