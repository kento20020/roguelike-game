## 0. 文書管理・本書の使い方

### 0.1 文書管理

| 項目 | 内容 |
|------|------|
| 文書名 | カジノタワー・ローグライト ゲーム仕様定義書 |
| ファイル | `docs/game_design_document.md`（**バージョンレス固定名**） |
| バージョン | v1.1（実装整合・ドキュメントのみ改訂） |
| ステータス | 実装フェーズ移行可能 |
| 対象読者 | ゲーム/UI実装者、データ調整担当、レビュワー |
| 技術構成 | React + TypeScript + Vite / FastAPI / SQLite |
| 正本データ | `backend/app/data/*.json`（§20.5） |
| 関連文書 | 本書 / API実形=`engine.snapshot()` / `backend/app/simulation/INTEGRATION.md` |

> **版管理ルール（齟齬防止）**：本書の**ファイル名はバージョンを含めず固定**（`game_design_document.md`）。版は①この文書管理表の「バージョン」、②タイトル行（`# ゲーム設計書 vX.Y`）、③巻末「付録: 変更履歴」、④git履歴の4箇所で管理する。**バージョンを上げてもファイル名・参照リンクは変更しない**ため、CLAUDE.md・README 等の参照が版ごとにズレることがない。版を上げる手順は「タイトル行を更新 → 変更履歴に1行追記 → コミット」のみ。

### 0.2 正本（source of truth）の優先順位

本書・JSON・コードで記述が食い違った場合、**何を真実とみなし、どちらを直すか**を以下で固定する。

| 対象 | 正本 |
|------|------|
| 設計意図・体験設計・状態遷移・ルールの構造 | **本書（GDD）** |
| 数値（戦闘係数・確率・敵パラメータ・sink・恒久強化） | **`backend/app/data/*.json`** |
| APIレスポンスの実形・フィールド名 | **`engine.snapshot()` / `backend/app/schemas`（Pydantic）** |

- ドリフトを検知したら、上表の**正本でない側を修正**し、巻末「変更履歴」に記録する。
- 本書本文の数表（敵HP表・ゲート確率表など）は**要約・参考**であり、実装は必ずJSONを読む（§20.5）。
- 「矛盾ゼロ」を保証する運用はしない。代わりに §20.5 の**機械検証**（weight合計100・ゲート合計1.0・アンロック整合）をCIで回し続け、ドリフトを検出する。

### 0.3 通貨・主要キーの正準（gold / chips）

通貨は実装上3つの呼び名が併存する。v1.1では**現状を正準として明文化**する（リネームはしない）。

| 層 | 正準名 | 例 |
|----|--------|----|
| 実行時ドメイン / フロント / API | **`chips`** | `player.chips`、`schemas/models.py` の `Player.chips`、`types.ts` |
| 永続・統計スキーマ（RunRecord/DB） | **`gold_*`**（歴史的経緯で保持） | `gold_earned` / `gold_spent`（`db/models.py`） |
| config 内部パラメータ名 | **`gold`** | `config.json` の `gold.floor_multiplier` |
| UI表示名 | **「チップ」** | ヘッダのチップ残高 |

- **変換点は1箇所**：実行時の `chips` を RunRecord 生成時に `gold_earned`/`gold_spent` へ写す。それ以外で名前を混ぜない。
- 本書本文で「ゴールド」「G」と書いている箇所は**表示・口語表現**であり、内部キーは上表に従う。
- その他の用語揺れも同様に実形へ寄せる：状態フェーズは `phase`（旧 `game_phase`）、ノードのロック状態は `state`（`available`/`locked`/`resolved`。旧 `locked` 単独フラグは廃止）。

## 1. ゲームコンセプト

### 1.1 コアコンセプト

> **「どの敵を選ぶかが未来を変える、確率で削り合うフロア制ローグライト」**

- 分岐するノードマップから**次に戦う敵を選ぶ**意思決定がゲームの核
- 倒した敵によって次に戦える敵がアンロックされ、**選択の連鎖**が生まれる
- 戦闘は確率ベース。攻撃するたびに敵が確率で反応し、**結果はロールで決まる**
- プレイヤーはHPをどれだけ温存して先に進めるかを**常に計算する**

### 1.2 ゲームの目的

カジノタワーの各階層にいる「ゲート（胴元の関門）」を通過して上の階層へ登り続けること。
5フロアのゲートを全て突破して頂上に到達すれば**クリア**。HP0でゲームオーバー（パーマデス）。

### 1.3 プレイヤーの動機

> **「カジノタワーの頂上に待つ"全てを賭けた一勝負"を目指して登り詰める」**

この一文がフレーバーテキスト・死亡/クリア画面・コピーライティング全体の軸になる。

> **テーマ転換**：当初の「地下カジノに潜る」から「カジノタワーを登り詰める」へ変更。UI描画が下から上（row1が画面下、ゲートが画面上）のSlay the Spire型になったことに合わせ、物語も「登る」で一貫させた。

## 2. ゲームループ

### 2.1 マクロループ（ラン間）

```
ゲーム開始
  → [ラン] 1Fから開始 → 探索・戦闘・ビルド構築 → 5Fクリア or HP0
  → クリア時: 恒久強化ポイント（+1）獲得 → 数値強化に割り振り
  → 次ランへ（恒久強化の分だけ有利な状態でスタート）
```

**win-to-progress**：死亡では恒久強化ポイントは得られない。クリアのみが積み上がる。

### 2.2 ミクロループ（ラン内：1フロア）

```
フロア開始
  → マップ表示（ツリー構造。row1の3体のみ選択可能）
  → ノード選択 → phase遷移して「戦闘/宝箱/回復/ゲート」を解決
  → 解決後: アンロック発生 → 次ノードが選択可能になる
  → ゲートを通過 → 次フロアへ
```

## 3. デザインの3本柱

**① 意味のある選択（Meaningful Choices）**
全ての選択肢にトレードオフを持たせる。「とりあえず強い1択」を作らない。

**② 公平なランダム性（Fair Randomness）**
ランダム性は「新鮮さ」のため、公平性は「意思決定の納得感」のため。運だけで死なせない。

**③ 知識が報われる（Knowledge is Power）**
キャラは死んでもプレイヤーの理解は蓄積する。上達実感を最重視する。

## 4. フロア構造とアンロック連鎖

> **描画方向**：ツリーは**下から上へ**描画する（row1が画面下、ゲートが画面上）。プレイヤーは画面下のrow1から選び、上のゲートへ登り詰める（Slay the Spire型）。データ構造の進行（row1→row2→gate）は変わらず、TreeCanvasのy座標を反転するだけ。ロジックには一切影響しない。

### 4.1 ツリー形状（全フロア）

| フロア | 形状 | row1 | row2 | row3 | ゲート経路 |
|--------|------|:----:|:----:|:----:|:---------:|
| 1F | 形B [3, 3] | 3体 | 3体 | — | 1本（固定チュートリアル） |
| 2F | 形A [3, 4] | 3体 | 4体 | — | ≥2本 |
| 3F | 形C [3, 5] | 3体 | 5体 | — | ≥2本 |
| 4F | 形C [3, 5] | 3体 | 5体 | — | ≥2本 |
| 5F | 形D [3, 4, 3] | 3体 | 4体 | 3体 | ≥2本 |

> **5Fゲート1本問題対策**：形Dではrow3（3体）のうち最低2体がゲートへの有効経路を持つことを必須とする。
> **row2の配置**：形Cのrow2（3F/4F）は floors.json の row2_pool から敵プール抽選（RNGストリーム1）で配置を決める。3F/4Fで挙動差はない（旧版の「（抽選）」注記は4Fのみに付いていたが、両者同一のため統一）。
> **フロア数**：v1.x では**5フロア固定**。本表・§7.4ゲート表・§20.1 floor_number 等が5前提。将来拡張はデータ駆動で可能だが `game_engine.MAX_FLOOR`・5F専用row3判定・テスト固定値の修正を伴う（§0.4）。

### 4.2 アンロック連鎖ルール（ハイブリッド型）

**基本原則：**
- **多親ノード**：隣接する2体の上位ノードから解放される → ゲートへの有効ルート
- **単親ノード**：1体の上位ノードのみから解放される → 行き止まり（dead-end）。宝箱・回復のみ配置

#### 形A [3, 4] のマッピング

```
row1:   [L]      [M]      [R]
         │ ╲    ╱ │ ╲    ╱ │
         │  ╲  ╱  │  ╲  ╱  │
row2:  [A]   [B]    [C]   [D]

A = L のみ      → 単親 dead-end（宝箱/回復）
B = L + M       → 多親（ゲートルート）
C = M + R       → 多親（ゲートルート）
D = R のみ      → 単親 dead-end（宝箱/回復）
```

#### 形B [3, 3] のマッピング（1F）

```
row1:   [L]    [M]    [R]
         │ ╲   ╱│╲   ╱ │
row2:  [A]   [B]    [C]

A = L のみ      → 単親 dead-end（反射mod確定配置：チュートリアル用）
B = L + M       → 多親（ゲートルート）
C = M + R       → 多親（ゲートルート）
```

#### 形C [3, 5] のマッピング

```
row1:    [L]       [M]       [R]
          │ ╲     ╱ │ ╲     ╱ │
row2:  [A]  [B]    [C]    [D]  [E]

A = L のみ      → 単親 dead-end
B = L + M       → 多親（ゲートルート）
C = M のみ      → 単親 dead-end（中央の宝箱/回復）
D = M + R       → 多親（ゲートルート）
E = R のみ      → 単親 dead-end
```

#### 形D [3, 4, 3] のマッピング（5F）

```
row1:   [L]    [M]    [R]
         │╲    ╱│╲    ╱│
row2:  [A]  [B]   [C]  [D]
         │ ╲  ╱ │ ╲  ╱ │
row3:    [X]    [Y]    [Z]

row1→row2: 形Aと同じ（A=単親, B=多親, C=多親, D=単親）
row2→row3:
  X = A + B       → 多親（ゲートルート①）
  Y = B + C       → 多親（ゲートルート②）
  Z = C + D       → 多親（ゲートルート③）
  ※ X/Y/Z のうち最低2本がゲートへ接続（4.1の制約を満たす）
```

### 4.3 回復ノードの配置ルール

- row1とrow2の**間**にのみ配置（row2の単親dead-endに設置）
- **ゲート直前の最終rowには配置しない**
- 1フロアにつき最大**1個**
- 1Fには配置しない

### 4.4 体験タイプの段階導入

| フロア | 初登場する体験タイプ |
|--------|----------------|
| 1F | 削り合い、賭け |
| 2F | レース（ramp） |
| 3F | ずれ（evade） |
| 5F | カオス（複合） |

## 5. 情報開示レイヤー

| レイヤー | 取得条件 | 開示される情報 |
|---------|---------|-------------|
| **L1** | マップ全体から常に見える | ノードの存在、種類、ロック状態 |
| **L2** | ノードに近づく/選択前確認 | 敵の体験タイプ（アイコン）、強敵インジケーター |
| **L3** | ノードをインタラクト（戦闘コミット前） | 敵名、最大HP、フレーバーテキスト |
| **L4（スカウト）** | チップsink（15G・**battle中のみ**） | 戦闘中の敵の次ターン行動テーブル結果を1ターン先読み |

> **確率開示方針（暗黙知型）**：行動テーブルの数値は**非公開**。プレイヤーが知れるのは体験タイプアイコンと強敵インジケーターのみ。詳細確率は遊んで学ぶ。スカウトで1ターン先読みのみ購入可能。

## 6. game_phase 状態遷移

### 6.1 全phase一覧（厳密型）

| phase | 意味 | 主な遷移先 |
|-------|------|----------|
| `exploring` | マップ上でノード選択中 | battle / treasure_preview / heal / gate_preview |
| `battle` | 戦闘中 | exploring（勝利）/ dead（HP0） |
| `treasure_preview` | 宝箱選択後・開封前（リロール可能） | treasure_opened（開封）/ treasure_preview のまま（リロールは中身を引き直すだけでphase不変・実装準拠）|
| `treasure_opened` | 宝箱開封後・mod確認中 | exploring |
| `heal` | 回復ノード解決中（大小決定済み） | exploring |
| `gate_preview` | ゲート選択後・通過前（ゲート保証sink使用可能） | gate_resolve |
| `gate_resolve` | ゲート結果ロール・適用中 | next_floor（1〜4F通過）/ **cleared（5F通過）** / dead（HP0） |
| `next_floor` | 次フロアへの遷移演出 | exploring |
| `cleared` | 5Fゲート通過・クリア | （恒久強化画面へ） |
| `dead` | HP0・ゲームオーバー | （死亡画面へ） |
| `pause` | ポーズ中（将来） | 直前のphaseへ復帰 |

| `hidden_room` | 特定条件で出現する隠し部屋 |

## 7. ノード・イベント

### 7.1 敵ノード

- 倒すと先のノードがアンロック

- `treasure_preview` phaseへ → 「開封する / リロール（30G）」を選択

### 7.3 回復ノード
- `heal` phaseへ → 大回復 / 小回復がランダム決定
- 使用は1回限り
- **回復量は固定値**：大回復 +30固定 / 小回復 +15固定
  - max_hpの%ではなく固定値。恒久強化でmax_hpが増える終盤ほど相対的に効果が薄くなる
- **回復sinkとは別系統**：回復ノード＝マップ上・無料・大小ランダム（運任せのドキドキ）／回復sink＝いつでも・有料・大小を選べる。「無料だが運任せ」vs「有料だが選べる」のトレードオフ。ギャンブルテーマと整合

### 7.4 ゲートイベント
- `gate_preview` phaseへ → ゲート保証sink使用可能（重ねがけ可）
- `gate_resolve` phaseで確率テーブルをロール

#### ゲートイベント結果テーブル（フロア別）

| 結果 | 1F | 2F | 3F | 4F | 5F | 被ダメ |
|------|:--:|:--:|:--:|:--:|:--:|------|
| 無傷通過 | 30% | 25% | 20% | 15% | 10% | 0 |
| 小ダメ通過 | 50% | 45% | 40% | 35% | 30% | max_hpの10% |
| 大ダメ通過 | 15% | 25% | 30% | 35% | 40% | max_hpの25% |
| 特殊 | 5% | 5% | 10% | 15% | 20% | 0（被ダメなし） |

> **「特殊」の効果について**：現状の実装では特殊＝**被ダメ0のみ**（無傷と同等）。`floors.json` は結果確率だけを定義し効果は持たず、コードにも追加効果（次フロア強化等）は**未実装**。将来拡張の余地（§21）。

#### ゲート保証（確率シフト型・重ねがけ可）

> **設計思想**：「確実に突破」はゲームバランスを損なうため採用しない。ゲート保証は**大ダメの確率を削るだけ**で、完全な安全は提供しない。

**基本ルール：**
- ゲート保証は**大ダメの確率の一部を、無傷・小ダメへ移す**
- **特殊（当たり）は減らさない**（保証を使っても一発逆転の目は残る）
- 同じゲートで**重ねがけ可能**。ただし効果半減＋コスト微増の二重ブレーキ

**重ねがけの数式：**
```
n回目のゲート保証:
  コスト     = round(50 × (1.5)^(n-1))           ← コスト微増（1.5倍ずつ・round）
  大ダメ削減量 = min(現在の大ダメ率, 25% × (0.5)^(n-1))  ← 効果半減＋下限クランプ
  ※ 削った分は無傷・小ダメへ半々split（各50%）。特殊は維持
```
> **下限クランプ（実装準拠）**：削減量は `min(現在の大ダメ率, 理論削減量)` を取るため、大ダメ確率が**負になることはない**（実装 `gate_resolver.py` の `removed = min(t["major"], reduction)`）。コストは `round` で整数化（§8.6 丸め規約）。

**5Fゲートでの重ねがけ例：**

| 回数 | この回のコスト | この回の削減量 | 大ダメ累計 | 累計コスト |
|:---:|:----------:|:---------:|:--------:|:--------:|
| 0回 | — | — | 40% | 0G |
| 1回 | 50G | -25% | 15% | 50G |
| 2回 | 75G | -12.5% | 2.5% | 125G |
| 3回 | 112G | -2.5%（クランプで2.5%しか削れない） | 0% | 237G |

効果半減で大ダメ削減は収束し（理論上の累計削減は最大50%付近）、コスト微増で所持チップへの負担が急増する。下限クランプにより大ダメ率は0%まで下がり得るが**負にはならず**、コストが先に尽きるため、チップで完全な安全は買えない。

> ゲート保証（50G）使用時は§13.2のsink一覧にも反映。

## 8. 戦闘フロー

### 8.1 rampとevadeの区別

| 概念 | 性質 | 処理タイミング | データの在り処 |
|------|------|-------------|-------------|
| **ramp** | 状態量（毎ターン増加する蓄積ダメージ） | 攻撃前に状態更新 | 敵の `ramp_value` |
| **evade** | 行動テーブルの一結果（そのターン攻撃をかわす） | 行動ロール後に処理 | 行動テーブルの `weight` |

### 8.2 1ターンの流れ

```
プレイヤーが「攻撃する」を選択
  ↓
[ramp更新] レース系のみ: ramp_value = base_initial + ramp_increment × (turns − 1)
           （毎ターン頭で再計算。1ターン目=base_initialのみ。§8.5）
  ↓
[stanceスロット] stance_multiplier = 1.0 固定（フェーズB用に予約。攻撃ブースト使用時のみ上書き）
  ↓
[与ダメ計算] player.attack × stance_multiplier → 敵HPに適用
  ↓
[行動テーブルを1回ロール] RNGストリーム2から weight比で抽選
      ├ "none"       → 被ダメ=0
      ├ "counter"    → 被ダメ=敵attack × counter_factor
      ├ "heavy_blow" → 被ダメ=敵attack × heavy_factor
      ├ "evade"      → 与ダメをキャンセル（巻き戻し）+ 被ダメ=0
      └ "ramp_hit"   → 被ダメ=現在のramp_value
  ↓
[mod適用] 重装甲の軽減・反射の追加ダメ・好機の追撃等
  ↓
[HP確認] 敵HP≤0 と プレイヤーHP≤0 が同時なら【勝利優先】（敵撃破を取る）
         敵HP≤0 → 勝利 / （敵生存かつ）プレイヤーHP≤0 → dead
  ↓
[ログ追記] 全ログ保持（§10.5）
```
> **同時死亡＝勝利優先（実装準拠）**：同一ターンで両者HP≤0になった場合は敵撃破を優先する（`combat_resolver.py` の `player_dead = player.hp<=0 and not enemy_dead`）。反射・好機で敵を倒し切れば、自分が0以下でも勝利になる。**このときプレイヤーHPは0にクランプされる（負値→0）。現状コードはHP1補正をしない**ため、HP0のまま `exploring` へ戻り得る（§1.2「HP0でゲームオーバー」は被弾・ゲート時の判定を指し、勝利優先の同時死亡はその例外）。"HP0でも生存" の違和感を消すために勝利時HPを1へ補正する案は**コード変更を伴うため OPEN-010（§21.2）**として保留。
> **evadeの処理順（実装準拠・注記）**：実装は「与ダメを先に敵HPへ適用 → 行動ロール → evadeなら巻き戻す（`enemy.hp += dealt`）」順。動作は正しいが「適用→巻き戻し」はやや脆い。将来は「行動ロール → evade判定 → 与ダメ算出」の順に整理する余地がある（仕様変更ではなく実装リファクタの候補）。

### 8.3 行動テーブル全タイプ

| タイプ | 被ダメ | 特記 |
|--------|------|------|
| `none` | 0 | |
| `counter` | 敵attack × counter_factor（既定1.0） | 削り合い系の主行動 |
| `heavy_blow` | 敵attack × heavy_factor（既定1.8） | 賭け系。敵ごとに上書き可 |
| `evade` | 0（与ダメも0） | ずれ系の主行動 |
| `ramp_hit` | current_ramp_value | レース系のみ |

> **係数の扱い（フォールバック設計）**：counter_factor / heavy_factor は config.json の全敵共通既定値（1.0 / 1.8）。敵が enemies.json で個別値を持てばそれを優先。コードは `enemy.get("heavy_factor", config["heavy_factor"])`。

**レース系の行動テーブル（全7体共通）：**
```
ramp_hit: 60%   （蓄積値を放出）
counter:  30%   （反撃）
none:     10%
```

### 8.4 戦闘内意思決定（A案）

戦闘中のプレイヤー行動は「攻撃する」のみ。意思決定は100%マップ層。
フェーズB（スタンス選択）は将来追加。条件は§12.3に予約。

### 8.5 ダメージ式

```
与ダメ = player.attack × player.stance_multiplier
            ↑ stance_multiplierは複数ソースの乗算
            最終 = stance係数(将来) × attack_boost係数(使用時2.0) × …
            現在は通常1.0、攻撃ブースト使用時のみ次の1撃が2.0

被ダメ（counter）  = enemy.attack × counter_factor（既定1.0、敵ごと上書き可）
被ダメ（heavy）    = enemy.attack × heavy_factor（既定1.8、敵ごと上書き可）
被ダメ（ramp_hit） = enemy.ramp_value
被ダメ（evade/none）= 0
最終被ダメ = max(0, 計算被ダメ − 重装甲の軽減値)
```

**ramp_value（蓄積ダメージ）の計算：**
```
ramp_value(n) = base_initial(=5) + ramp_increment × (n − 1)
                    ↑ 全レース敵共通     ↑ 敵ごと（inc=2〜8）
n = そのレース敵との戦闘の経過ターン数
```
- 1ターン目から base_initial(5) 分のダメージを持つ（最初から無害ではない）
- 2ターン目以降は敵ごとのincで個性が出る（inc=2はゆるやか、inc=8は急激）

**multiplierの乗算ルール：**
- `stance_multiplier` は複数ソースを掛け合わせる統一経路で実装
- 現在：攻撃ブーストのみ（次の1撃を×2.0）
- 将来：フェーズB（スタンス）が乗る → `compute_multiplier()` に1行足すだけ
- 攻撃的スタンス中にブーストを切ると最大火力（シナジー）。爆発力はbotで監視

### 8.6 数値の丸め規約（実装準拠）

小数が出る計算の整数化は**実装の実態に合わせて `round()` で統一**する。Pythonの `round()` は **ties-to-even（いわゆる銀行丸め）**——`.5` は最近接の偶数へ丸める（例: `round(112.5)=112` / `round(113.5)=114`）。TypeScript側で同一結果が必要な場合は Python互換（ties-to-even）の丸めを実装する。

| 計算 | 丸め | 実装箇所 |
|------|------|---------|
| 与ダメ / 被ダメ（counter/heavy/ramp等） | `round()` | `combat_resolver.py` |
| ramp_value | `round()` | `combat_resolver.py` |
| 敵HPのtierスケーリング | `round()` | `loader.py`（§11.3） |
| ゴールド（チップ）ドロップ・sinkコスト | `round()` | `game_engine.py` |
| ゲート保証コスト・ゲート被ダメ | `round()` | `gate_resolver.py` |
| **重装甲の軽減値** | `int()`（切り捨て）※唯一の例外 | `combat_resolver.py` |
| 回復量（+15/+30固定） | 丸め不要（整数定数） | — |

> 確率（0.0〜1.0）は内部ではfloatのまま扱い、UI表示時のみ百分率へ丸める。

## 9. 体験タイプ

| タイプ | 感情体験 | 代表行動 | row1枠 | L2アイコン |
|--------|---------|---------|:------:|:--------:|
| **削り合い** | じりじりした削り合い | counter主体 | 枠A | ⚔️ |
| **賭け** | 大当たり/大外れのスリル | heavy_blow/none | 枠B | 🎲 |
| **レース** | 放置するほどリスク増 | ramp_hit | 枠C | ⏫ |
| **ずれ** | 攻撃が空振りする徒労 | evade主体 | 枠C | 💨 |
| **カオス** | 複合・予測不能 | ランごとに変動 | 枠C | ❓ |

### 9.1 row制約

> **枠とノード位置の対応**：row1の **枠A=L（左）／枠B=M（中）／枠C=R（右）**（§4.2のL/M/Rに対応）。

**row1**：枠A(L)=削り合い、枠B(M)=賭け、枠C(R)=レース/ずれ/カオス
**row2**：同一体験タイプは最大2体まで
**row3（5F）**：カオス以外を最低1体含める

### 9.2 カオスタイプ設計（ランごとシード決定型）

カオス敵の行動テーブル比率は**ランごとにシードから決定**する。
「このランのカオスは何が来やすいか」を遊びながら読む体験になる。

```
ラン開始時、各カオス敵について（実装: chaos_weights.py）:
  対象4種 = {counter, heavy_blow, evade, ramp_hit}
  各種に最低保証 _FLOOR_PT = 5 を確保（合計20）→ 残り80を分配
  分配比率は 真の Dirichlet(1,1,1,1)（＝単体上の一様分布）:
    RNGストリーム8から U を引き、Gamma(1)=Exp(1) サンプル X = −ln(1−U) を4本生成し総和で正規化
  整数化の端数は最大剰余法(Hamilton)で配る（系統的偏りを作らない）
  → behaviors と同じ形式 list[(type, weight)]、weight合計=100 を返す
  消費する乱数は敵あたり4回（id昇順で消費＝決定論）
```

> **実装の補足**：旧実装の「一様値をそのまま正規化」は単体の中心へ集中し『heavy偏重/evade偏重』が出にくかったため、真のDirichletに修正済み（ランごとの偏りが出やすい）。なお最低保証 5pt×4=20 を引いた残り80をDirichlet配分するため、各カテゴリの取り得る範囲は **5%〜85%**（特定カテゴリが総量の過半に寄るランも一定割合で出る）。weightは **合計100の整数**（"合計1.0に正規化"ではない）。
> 同一ラン内では一貫しているため「学習可能」。ラン間では変わるためリプレイ性が出る。

矛盾・シナジーを以下のスキーマで管理する。`type` と `is_intended` を持たせ、後からシナジー行を追加できる構造。

```
mod_interactions: [
  {
    mods: ["mikiri", "yomi"],
    type: "cancel",
    behavior: "先読みでevade予告されても与ダメ0は発生しない（見切り優先）。先読みは『evadeが来ない』確認のみ",
    is_intended: true
  },
  {
    mods: ["mikiri", "kouki"],
    type: "synergy",
    behavior: "evade weight=0により相対的にheavy_blowが来やすくなり、好機の発動頻度が上がる",
    is_intended: true
  },
  {
    mods: ["hansha", "juso"],
    type: "synergy",
    behavior: "被ダメ軽減後の値に反射追加ダメを乗せる。あえてcounterを受ける『被弾上等』立ち回りが成立",
    is_intended: true
  }
]
```
> ※ `mods` の値は **mod id**（`mods.json` も id で記述）。本文の効果文は §10.1 の日本語名で可読化している。

**運用方針（面白さの非対称な扱い）：**
- **死にmod**（腐る組み合わせ）：統計で検出して**潰す**
- **壊れmod**（爆発する組み合わせ）：統計で検出するが**残す**（クリア率を破壊するレベルのみ調整）
- `±8pt`の寄与制約は「常時の平均寄与」であり、「引けたときの爆発力」は均さない

**拡張性：** modを追加する際は「攻撃前/行動ロール後/被ダメ計算後」のフックに効果ハンドラを差し込むだけ。インタラクションは `synergy` 行を足すだけで「狙って組みたい組み合わせ」を増やせる。

### 10.5 コンバットログ（表示専用・使い捨て）

- 戦闘中の全ログを保持し、スクロールで遡れる（表示行数はUI側で調整、デフォルト8行）
- **combat_logは表示専用・使い捨て**。戦闘終了で破棄してよい。統計には使わない
- **RunRecordとは同期しない**（別目的のため）。combat_log=表示、RunRecord=統計と役割を完全分離
- これによりログのズレるバグ（表示は勝利・記録は敗北等）が構造的に起きない

> **ログ二重管理の解消**：combat_log（表示・使い捨て）とRunRecord（統計・永続）を別物として扱う。将来リプレイ機能が必要になっても**ログの永続保存は不要**——ただし再現には **seed に加えてプレイヤー操作履歴とデータ版が必要**（§19.2）。seed は RNG ストリームを再現するだけで、プレイヤーの選択分岐までは再現しない点に注意。

> **正本は `enemies.json`**。本表は可読性のための要約であり、実装は必ずJSONを参照する。

### 11.4 強敵リワード

強敵（`difficulty ≥ 4`）を倒すと：
- ゴールドドロップ **×1.5**（floor_multiplierと重複適用）
- 宝箱配置確率 **+20pt（絶対値加算）**

| ノード種別 | 基準宝箱確率 | 強敵撃破後（+20pt） |
|-----------|:------:|:--------:|
| 多親ノード | 30% | 50% |
| 単親dead-end | 60% | 80% |

> 「+20%」（相対）ではなく「+20pt」（絶対値加算）。30%→50%（×1.2の36%ではない）。強敵を倒す動機づけとして体感できる上昇幅にする。

## 12. プレイヤー設計・恒久強化

### 12.1 基本パラメータ（基準体）

| パラメータ | 初期値 | 変化条件 |
|---------|:----:|--------|
| `hp` | 100 | 被ダメ・回復・ゲートで変動 |
| `max_hp` | 100 | 恒久強化（+max_hp） |
| `attack` | 15 | 恒久強化（+attack） |
| `chips` | 0 | 敵撃破・sink・恒久強化（+初期chips）。※恒久強化の内部キーは実装に合わせ `init_gold` を維持（§0.3 / §12.3） |
| `mods` | [] | 宝箱開封 |
| `stance_multiplier` | 1.0 | フェーズB（現在固定） |

### 12.2 ダメージ式・スケーリング

**敵HPスケーリング：** `enemy.hp = base_hp × (1.0 + 0.15 × (tier - 1))`

| tier | 1 | 2 | 3 | 4 | 5 |
|:---:|:--:|:--:|:--:|:--:|:--:|
| 倍率 | 1.00 | 1.15 | 1.30 | 1.45 | 1.60 |

**ゴールドドロップ：** `gold_base × floor_multiplier × 強敵ボーナス`

| フロア | 1F | 2F | 3F | 4F | 5F |
|:-----:|:--:|:--:|:--:|:--:|:--:|
| floor_multiplier | 1.00 | 1.25 | 1.50 | 1.75 | 2.00 |

### 12.3 恒久強化システム（問E）

**仕組み：** ポイント割り振り型。1クリア=1ポイント獲得。5項目に自由配分。

| 強化項目 | 1レベルあたり効果 | 上限Lv | 最大累計 |
|---------|---------------|:----:|--------|
| +max_hp | +10 | 5 | +50 |
| +attack | +2 | 5 | +10 |
| +初期gold | +15G | 5 | +75G |
| +gold_drop率 | +10% | 3 | +30% |
| -sinkコスト | -5G | 3 | -15G |

- 全項目MAX（26点）まで26クリア必要
- 数値はデータ駆動で調整、上限レベルの構造は確定
- **拡張性**：強化項目はテーブル定義。後から項目追加が容易

**フェーズB（スタンス）予約事項：**
- ダメージ計算は必ず `attack × multiplier` の形で記述（直接代入禁止）
- RNGストリームに `stance`（番号6）を予約
- フェーズB追加時は統計再検証が必要（想定済み）

## 13. チップ経済システム

> 本章ではプレイヤー通貨を「チップ」と呼ぶ（§0.3）。本文に残る「ゴールド/G」は表示上の名残で、内部キー・統計は歴史的経緯により `gold_*`/`init_gold` を維持する。

### 13.1 獲得（フロア別期待値、叩き台）

| フロア | 1F | 2F | 3F | 4F | 5F | 累計 |
|-------|:--:|:--:|:--:|:--:|:--:|:---:|
| 期待値 | 15-25G | 25-40G | 35-55G | 45-65G | 55-75G | 175-260G |

### 13.2 Sink一覧と使用タイミング

| sink | コスト | 効果 | 使用タイミング | 種別 |
|------|:-----:|------|------------|:---:|
| スカウト | 15G | 次ターン行動先読み（強敵戦で輝く） | **battle時のみ** | 守り |
| 小回復 | 20G×フロア係数 | **+15固定**回復 | **いつでも**（満タンでも可、溢れは捨て） | 守り |
| 大回復 | 40G×フロア係数 | **+30固定**回復 | **いつでも** | 守り |
| ゲート保証 | 50G×(1.5)^(n-1) | 大ダメ確率を削る（重ねがけ可・特殊維持） | **gate_preview時のみ** | 守り |
| 宝箱リロール | 30G | 宝箱を開封前に引き直し | **treasure_preview時のみ** | 守り |
| **攻撃ブースト** | 30G（叩き台） | **次の1撃のみ attack +100%** | **battle時のみ** | **攻め** |

> **「sink」と「/sink API」の別**：本表は**チップ消費アクション**の一覧。API的には回復/スカウト/攻撃ブースト/ゲート保証が `POST /sink`、**宝箱リロールのみ専用ルート `/treasure/reroll`**（§25.2）。
> **攻めのsink追加**：従来のsinkは全て「リスクを減らす」守りだった。攻撃ブーストは唯一の「攻め」のsink。次の1撃だけattackを上書きする（ダメージ式 `attack × stance_multiplier` の multiplier を一時上書き）。

#### 回復コストのフロア係数

| | 1F | 2F | 3F | 4F | 5F |
|---|:--:|:--:|:--:|:--:|:--:|
| 小回復 | 20G | 25G | 30G | 35G | 40G |
| 大回復 | 40G | 50G | 60G | 70G | 80G |

終盤は回復が高額化し、無限回復ができなくなる。回復量固定（§7.3）と合わせて、終盤は「大きく削られて・少ししか回復できない」緊張感を作る。

#### スカウトの位置づけ

- 通常敵：15Gで次1ターン先読みは割高に感じる（使わなくても対処可能）
- 強敵戦（difficulty≥4）：「次にheavy_blowが来るか」を読む命綱になり、同じ15Gが安く感じる
- 暗黙知型（確率非公開）だからこそ、強敵の読めない恐怖に対して情報を売る価値が出る
- 攻撃ブーストとのシナジー：スカウトで危険を察知 → ブーストで先に倒し切る

#### 攻撃ブーストの設計意図

- レース系の敵に刺さる（早く倒せばramp_hitを受ける回数が減る）
- 強敵を早期決着させ被ダメ機会を減らす
- 「攻撃ブーストで早期決着 vs 回復でHP管理」の2戦略が生まれる
- 実装：`stance_multiplier` を次の1撃だけ上書き。フェーズB（スタンス）と同じ計算経路に乗る

### 13.3 貯め込み逓減（問F＝自然解決）

- 所持上限なし・減衰なし
- sinkを使わないと死にやすい難度設計で「使った方が得」を自然に成立させる
- Phase4で「ゴールドをほとんど使わずクリアするランの割合」を監視
- 多すぎる場合のみ対策（上限/減衰）を後から検討

- アンロック整合（多親=親2／単親=親1）・存在しないノード参照なし

**API**
- 全エンドポイントが正常系/異常系テストを通過
- phase不整合=409／チップ不足・未対応操作=400／不明session=404（§25.4）

**UI**
- 各phaseに対応画面が表示される／`available_actions` 外の操作は実行不可
- ツリーは row1=画面下・ゲート=画面上で描画（§4・§26.1）

**RNG / テレメトリー**
- 同一seed・同一操作列で同一結果（Python/TS黄金テスト）
- ラン終了時に RunRecord が保存され、`cleared`/`dead` が正しく記録される

## 19. テレメトリー（RunRecord）

### 19.1 スキーマ（全フィールド採用）

```
RunRecord:
  # ラン識別
  run_id: string
  seed: int
  timestamp: datetime          # 実装では created_at（DB server_default=now）として永続化

  # 結果
  cleared: bool
  floor_reached: int          # 1〜5
  total_turns: int

  # プレイヤー
  final_hp: int
  mods_acquired: string[]      # 取得modのリスト

  # 経済
  gold_earned: int
  gold_spent: { scout: int, heal_small: int, heal_large: int,
                gate_guarantee: int, treasure_reroll: int,
                attack_boost: int }    # 攻めのsink
  gate_guarantee_stacks: int           # ゲート保証の重ねがけ回数（合計）

  # 戦闘詳細
  enemies_defeated: [
    { enemy_id: string, experience: string, floor: int, turns: int }
  ]                            # 体験タイプも記録（mod×敵の化学反応分析用）
  death_cause: string | null   # 死亡時の敵id・行動タイプ
  death_floor: int | null

  # 統計用
  bot_type: string             # "strong" / "random"
  permanent_upgrades_state: { max_hp: int, attack: int,
                              init_gold: int, gold_drop: int, sink_cost: int }
```

### 19.2 用途
- Phase2以降の全統計検証の入力
- `enemies_defeated`に体験タイプを含むため「ずれ系敵が出ないランで見切りが腐ったか」を検出可能
- **リプレイ機能の前提（注意）**：combat_log は表示専用・非永続（§10.5）。将来リプレイを実装する場合、再現に必要なのは **seed＋プレイヤー操作履歴（選択ノード・sink使用・攻撃・宝箱開封/リロール・ゲート保証回数）＋データファイル版**。**seed だけでは操作分岐を再現できない**ため、その時点で操作履歴の永続化を別途追加する（現状RunRecordには操作履歴を保存していない）。

### 22.2 技術選定一覧

| レイヤー | 技術 | 選定理由 | 将来の移行先 |
|---------|------|---------|------------|
| フロントエンド | React + TypeScript + Vite | デファクト・起動が速い | — |
| 状態管理 | Zustand | 11phaseの管理に強い・2KB軽量 | + TanStack Query |
| スタイリング | Tailwind + clsx + CSS Variables | テーマ一元管理・ランタイムコストゼロ | — |
| バックエンド | Python + FastAPI | Swagger自動生成・型安全・非同期 | — |
| ORM | SQLAlchemy | DB切り替えがコード変更最小 | — |
| DB | SQLite | 設定ゼロ・ローカル開発に最適 | PostgreSQL |
| 通信 | REST API | ターン制と相性◎・botと同じエンジンを使える | — |
| リポジトリ | モノレポ | 管理が楽・ポートフォリオで見せやすい | — |

### 22.3 設計原則（移行容易性の確保）

実装開始時点から以下を守ることで、将来の技術移行コストを最小化する。

| 原則 | 目的 |
|------|------|
| ゲームロジックは全てPython。Reactは計算・勝敗判定しない | botシミュレーターとUIで同じエンジンを共有 |
| UIは `available_actions` を**操作可否の正本**にする | フロントの条件分岐を排し、含まれない操作は非表示/disabled（§25.3） |
| phase不整合の拒否はサーバ側で必ず行う（§25.4） | クライアント改ざん・不正遷移への防御 |
| API通信は `gameApi.ts` に集約（直接fetchしない） | TanStack Query移行時にこのファイルだけ変更 |
| DB操作はSQLAlchemy経由（生SQLを書かない） | PostgreSQL移行をコード1行で実現 |
| ダメージ計算は `attack × multiplier` で記述 | フェーズB（stance）追加に備える |

## 25. APIエンドポイント仕様

### 25.1 設計方針

- ゲームの全ロジックはバックエンド。フロントは操作を送って新しい状態を受け取るだけ
- 各レスポンスは**完全なゲーム状態**を返す（フロントは差分計算不要）
- `session_id` でランを識別。DBに永続化

### 25.2 エンドポイント一覧

| メソッド | パス | 用途 | リクエスト | レスポンス |
|---------|------|------|----------|----------|
| POST | `/api/run/new` | 新規ラン開始 | `{ seed?: int }` | `GameState` |
| GET | `/api/run/{session_id}` | 状態取得（再開） | — | `GameState` |
| POST | `/api/run/{session_id}/select-node` | ノード選択 | `{ node_id }` | `GameState` |
| POST | `/api/run/{session_id}/attack` | 攻撃 | — | `GameState` |
| POST | `/api/run/{session_id}/sink` | sink使用 | `{ sink_type }` | `GameState` |
| POST | `/api/run/{session_id}/treasure/open` | 宝箱開封 | — | `GameState` |
| POST | `/api/run/{session_id}/treasure/reroll` | 宝箱リロール | — | `GameState` |
| POST | `/api/run/{session_id}/gate/resolve` | ゲート通過 | — | `GameState` |
| POST | `/api/run/{session_id}/upgrade` | 恒久強化割り振り | `{ upgrade_type }` | `UpgradeState` |
| GET | `/api/stats/history` | RunRecord履歴 | — | `RunRecord[]` |

> **sink_typeの値**：`scout` / `heal_small` / `heal_large` / `gate_guarantee` / `attack_boost`（実装の `use_sink` が受け付ける値）。
> **宝箱リロールは専用ルート**：`/treasure/reroll` のみで実行する。`/sink` に `treasure_reroll` を渡すと **400**（実装は `use_sink` で未対応）。※ RunRecord の `gold_spent.treasure_reroll`（§19.1）はチップ消費の記録カテゴリとしては残る。
> **ゲート保証の重ねがけ**：`sink_type: "gate_guarantee"` を `gate_preview` phaseで複数回POSTできる。サーバーが現在の重ねがけ回数 `n` を保持し、コスト `50G×1.5^(n-1)` と削減量 `25%×0.5^(n-1)` を計算してGameStateに反映。ゴールド不足時は400を返す。
> **攻撃ブースト**：`sink_type: "attack_boost"` は `battle` phaseでのみ有効。次の `attack` 1回だけ `stance_multiplier` を上書き。

### 25.3 GameStateレスポンスの形

> **実装に追随した版**。下記が `engine.snapshot()` の実形。過去ドラフトからの変更点：
> - `player.gold` → **`player.chips`**（§16.2 テーマ読替＝チップ）。`attack_boost_pending` を追加。
> - `floor` は `tree_shape`/`edges` 配列ではなく **`nodes`（id→ノードの dict）**。辺は各ノードの **`parents`** で表現し、`tree_shape` は floors.json 側の定義に集約。`locked` 単独フラグは廃止し **`state`（available/locked/resolved）** に統一。
> - トップレベルの `combat_log`/`available_sinks` は廃止 → ログは **`battle.log`**、sink候補は **`available_actions`（cost付き・上位互換）** に統合。
> - `run_record` をトップレベルに含む（決算・履歴用）。

```json
{
  "session_id": "uuid",
  "phase": "exploring",
  "current_floor": 2,
  "player": {
    "hp": 80, "max_hp": 100, "attack": 15,
    "chips": 45, "mods": ["hansha", "mikiri"],
    "stance_multiplier": 1.0, "attack_boost_pending": false
  },
  "floor": {
    "floor_number": 2,
    "nodes": {
      "L": { "id": "L", "kind": "enemy", "row": 1, "parents": [], "parent_type": "root",
             "resolved": false, "state": "available",
             "experience": "削り合い", "name": "…", "is_strong": false, "max_hp": 23 }
    }
  },
  "battle": null,
  "pending": {},
  "available_actions": [
    { "type": "select_node", "node": "L" },
    { "type": "use_sink", "sink": "heal_small", "cost": 20 }
  ],
  "run_record": null
}
```

### 25.4 エラーハンドリング

| ステータス | 意味 |
|----------|------|
| 400 | 不正な操作（ロック中ノード選択・チップ不足・未対応sink_type等） |
| 404 | session_idが存在しない |
| 409 | phase不整合（戦闘中にノード選択等） |

**phase不整合の例（サーバ側で必ず拒否＝409）**：フロントで防いでいてもバックエンドの防御は必須。

| 現在phase | 不正操作 | 返す |
|----------|---------|:---:|
| `battle` | select-node | 409 |
| `exploring` | attack / treasure・gate系 | 409 |
| `treasure_opened` | treasure/reroll | 409 |
| `gate_resolve` | select-node / attack | 409 |
| `dead` / `cleared` | attack / sink / select-node | 409 |

> sink の許可phaseは §13.2 準拠（scout/attack_boost=battle、gate_guarantee=gate_preview、reroll=treasure_preview、回復=いつでも）。許可外phaseでの sink も 409/400 で拒否。

### 25.5 型共有

`backend/app/schemas/api_schemas.py`（Pydantic）と `frontend/src/api/types.ts`（TypeScript）で同じ型を定義。
将来的にはOpenAPIスキーマからTypeScript型を自動生成することも可能（FastAPIがSwaggerを吐くため）。
