## 1. 運用視点（Ops / SRE）

### ① 実務で求められる視点 — 現場の問いに直すと

| 現場の問い | 背後にある概念 |
|---|---|
| 「いま本番で何が起きているか、ログだけで再現できるか？」 | 可観測性（ログ・メトリクス・トレースの3本柱） |
| 「このリリース、失敗したら5分で戻せるか？」 | 変更管理・ロールバック設計・リリース手順の文書化 |
| 「障害の一報を受けた人が、担当者を起こさずに一次対応できるか？」 | runbook・オンコール設計・ポストモーテム文化 |
| 「どこまで壊れたら『障害』なのか、基準は合意されているか？」 | SLO / エラーバジェット（"全部完璧" は目標にならない） |
| 「環境ごとの差分は環境変数だけに閉じているか？」 | 12-Factor App・設定とコードの分離 |

実務の運用は「障害をゼロにする」仕事ではなく、**「障害が起きたときの検知・切り分け・復旧を速くする」仕事**。平常時に仕込んだもの（ログの相関ID、ヘルスチェック、バックアップ手順）だけが障害時に使える。障害当日に新しく作れるものは何もない、というのが最重要の感覚。

### ② このリポジトリでの実例

- `X-Request-ID` ミドルウェア＝トレースの最小形。「1リクエストの一生をログで追える」状態を作った
- `runbook.md` の実手順化＝「知っている人の頭の中」を文書に移した。属人性の排除
- Alembic 導入＝スキーマ変更を「再現可能・巻き戻し可能な手順」にした。DBの変更管理そのもの
- `.env.example`＝環境差分の目録。新しい環境を立てる人への申し送り

### ③ 学習ロードマップ

**今すぐ（〜半年）**
- Linux とシェルの基礎（プロセス・ポート・ログの場所・`journalctl`/`tail -f` で調べる習慣）
- GitHub Actions で CI を1本組む（このリポジトリの `pytest` + `typecheck` を PR ごとに回すのが最適な練習台）
- 構造化ログ（JSON ログ）と ログレベルの使い分けを body で覚える

**1〜2年**
- Docker / コンテナ（「自分のマシンでは動く」を卒業する技術）
- 監視スタックを1回自分で立てる: Prometheus + Grafana、または OpenTelemetry。ダッシュボードを1枚作ると「メトリクスとは何か」が腹落ちする
- 書籍: **『SRE サイトリライアビリティエンジニアリング』（Google）**——特に「ポストモーテム」「リリースエンジニアリング」の章。**『入門 監視』（Mike Julian）** は薄くて実務的
- クラウド基礎（AWS でも GCP でも1つ。資格なら SAA / ACE は地図として有効）

**10年視点**
- IaC（Terraform）→ プラットフォームエンジニアリング（開発者向けの社内基盤を作る側）へ。運用は「手を動かす仕事」から「仕組みを設計する仕事」に重心が移り続けており、コードが書ける運用者の市場価値は上がり続ける

## 2. 開発視点（Dev / ソフトウェア設計）

### ① 実務で求められる視点

| 現場の問い | 背後にある概念 |
|---|---|
| 「この変更で壊れていないと、どうやって言い切るか？」 | テストは安全網。リファクタリングの速度はテストの質で決まる |
| 「このモジュールが絶対に守るべき約束は何か？」 | 不変条件（invariant）・契約による設計 |
| 「仕様とコード、どちらが正しいか揉めたとき、正本はどこか？」 | 正本（source of truth）の明文化・docs as code |
| 「リトライで運良く通る設計と、構造的に正しい設計、どちらか？」 | 構成的アルゴリズム（correct by construction） |
| 「半年後の自分が読んで、なぜこうしたか分かるか？」 | ADR・コミットメッセージ・設計意図の記録 |

2年目で一番差がつくのは「動くコードを書ける」の先、**「壊れたとき・変えるときに強いコードを書ける」**か。それを支えるのがテスト設計と不変条件の言語化。

### ② このリポジトリでの実例

- 形状決め打ちテスト → 不変条件テストへの書き換え（`test_floor_generator.py`）: 「2Fの2行目は3ノード」ではなく「多親は必ず隣接2親・全ノード到達可能」を全seed横断で検証。実装の自由度を保ったまま正しさを固定する
- あみだくじ格子生成: リトライループで invariant を満たすまで引き直すのではなく、**生成手順そのものが invariant を保証する**構成にした
- `_resolve_battle_turn` への共通化: 攻撃・ガード・回復が同じターン解決経路を通ることで「回復だけ ramp が進まない」類のバグを構造的に排除
- CLAUDE.md の「正本の優先順位」表: 仕様とコードの二重管理を防ぐ統治ルール

### ③ 学習ロードマップ

**今すぐ（〜半年）**
- テスト設計: 「正常系1本」から卒業し、境界値・異常系・不変条件の3層で考える癖。Python なら **Hypothesis**（プロパティベーステスト）を1回触ると世界が変わる
- 型を「注釈」でなく「設計道具」として使う: Pydantic / TypeScript の型で「不正な状態を表現できなくする」練習
- 書籍: **『リファクタリング（第2版）』（Martin Fowler）**——カタログとして常備

**1〜2年**
- 書籍: **『A Philosophy of Software Design』（John Ousterhout）**——「深いモジュール」「複雑性は依存と不明瞭さ」という語彙が設計レビューの共通言語になる。**『テスト駆動開発』（Kent Beck）**
- ADR（Architecture Decision Record）を実務で書き始める（このリポジトリの `docs/adr/` が例）
- 設計パターンより先に「凝集度・結合度・レイヤー分離」を実例で説明できるようになる

**10年視点**
- ドメイン駆動設計（DDD）・イベント駆動アーキテクチャは、システムが大きくなったとき必ず再会するので、概念だけ先に知っておく（『ドメイン駆動設計をはじめよう』などの入門から）
- AI コーディング時代に価値が残るのは「何を作るべきかの仕様化」「正しさの検証設計」「invariant の言語化」——まさに本書のテーマ。コードを打つ速度より、**受け入れ条件を定義する能力**に投資する

## 3. データエンジニア視点（DE）

### ① 実務で求められる視点

| 現場の問い | 背後にある概念 |
|---|---|
| 「このデータ、いつの・どのルールで作られたものか区別できるか？」 | データの世代管理（バージョン刻印）・リネージ |
| 「スキーマを変えたら、過去データと分析クエリはどうなるか？」 | スキーマ進化・後方互換・マイグレーション |
| 「表示用のデータと分析用のデータ、混ぜていないか？」 | 用途別のデータ分離（OLTP/OLAP の原型） |
| 「壊れたデータが入ってきたら、どこで検知するか？」 | データ品質検証・データコントラクト |
| 「同じ処理を2回流したら二重計上にならないか？」 | 冪等性 |

DE の本質は「パイプラインを書く」ことではなく、**「後から分析する人が信頼できるデータを、壊れない形で残す」**こと。データは書いた瞬間より、1年後に読むときに価値が問われる。

### ② このリポジトリでの実例

- `data_version`（4つの JSON の sha256）＋ `strategy_version`（bot 世代札）: 「この記録はどのバランス・どの bot で生まれたか」を行ごとに刻印。**バランス改定をまたいだ統計の混合を防ぐ**——実務の「施策前後のデータを混ぜて平均を出してしまう」事故と同型
- `combat_log`（表示用・使い捨て）と `RunRecord`（統計用・永続）の分離を「同期しない」とまで明文化: 用途の違うデータを1つのテーブルで兼用すると、どちらの要件変更でも壊れる
- `loader.validate()`（weight 合計100・ゲート表合計1.0・enum 検査）: データコントラクトの最小形。「入口で落とす」方が「集計で気づく」より1000倍安い
- Alembic の 0002 を冪等に書いた（列の存在を確認してから追加）: 移行スクリプトは「何回流しても同じ結果」が原則

### ③ 学習ロードマップ

**今すぐ（〜半年）**
- SQL を「書ける」から「読める・説明できる」へ: 実行計画（`EXPLAIN`）、インデックスが効く条件、JOIN の種類を自分の言葉で
- このリポジトリの `game.db` を素材に、run_records を集計する分析クエリを10本書いてみる（クリア率の推移、sink 使用の分布、など）
- 正規化（第3正規形まで）と「あえて非正規化する」判断基準

**1〜2年**
- 分析用モデリング: **Kimball のスタースキーマ**（ファクト／ディメンション）。書籍なら『データマネジメントが30分でわかる本』→『The Data Warehouse Toolkit』
- **dbt** を1回触る（SQL 変換にテストとリネージが付く体験）。クラウド DWH（BigQuery が無料枠で試しやすい）
- ワークフローオーケストレーション（Airflow / Dagster）の概念——「リトライ・依存・冪等」を仕組みで担保する世界

**10年視点**
- lakehouse（Iceberg / Delta）、ストリーミング（Kafka / Flink）、データコントラクトの標準化が主戦場。ただし根っこは今も昔も「**スキーマ進化と品質保証**」で、本リポジトリでやった data_version / validate / Alembic はそのミニチュア。この原型を説明できる人は、道具が変わっても通用する

## 4. データサイエンティスト視点（DS）

### ① 実務で求められる視点

| 現場の問い | 背後にある概念 |
|---|---|
| 「その差、偶然の範囲では？ N はいくつ？」 | 推定・信頼区間・検定（点推定だけで意思決定しない） |
| 「同じ分析をもう一度流して、同じ結果が出るか？」 | 再現性（seed 固定・環境固定・データ固定） |
| 「その指標を目標にした瞬間、何がハックされるか？」 | Goodhart の法則（指標は合格条件であって最適化目標ではない） |
| 「計測は施策の前に仕込んであるか？」 | テレメトリファースト（後から過去は測れない） |
| 「オフライン評価とオンラインの実態はズレていないか？」 | シミュレーション評価と実環境のギャップ |

DS の実務は「モデルを作る」より先に、**「意思決定に耐える計測を設計する」**が来る。分析の失敗の大半はモデルではなく、データの取り方と指標の設計で起きる。

### ② このリポジトリでの実例

- bot ハーネス N=1000 で「maxed クリア率 4.3%、95%CI [3.2, 5.7]」と**区間で**報告: 「クリア率が下がった」ではなく「どのくらい確からしく下がったか」を示す
- 同一 seed → 同一 RunRecord の黄金テスト: 分析の再現性をテストスイートで機械的に担保している（実務では「ノートブックがもう動かない」が頻出事故）
- CLAUDE.md の「統計指標は合格条件であって最適化目標ではない」: Goodhart 回避を統治ルールとして明文化。バランス調整の最終判断を人間（デザイナー）に残した
- `action_counts` / `gate_results` / `run_actions`（全ラン操作履歴）: 「後で聞きたくなる質問」を先回りして計測に落とした。テレメトリファーストの実践

### ③ 学習ロードマップ

**今すぐ（〜半年）**
- 統計の基礎を「使える」レベルで: 平均と分散、二項比率の信頼区間、p値の意味と限界。書籍なら『統計学入門』（東大出版・赤本）か、実務寄りに『データ分析のための統計学入門』
- pandas（または polars）で本リポジトリの run_records / run_actions を分析してみる——**自分が仕様を知っているデータ**は最高の教材
- 可視化の基本: 「1グラフ1メッセージ」、分布はヒストグラム、比率の比較には区間を添える

**1〜2年**
- A/B テストと実験計画: 書籍 **『A/B テスト実践ガイド』（Kohavi ほか, 原題 Trustworthy Online Controlled Experiments）**——実験の落とし穴カタログとして10年もつ
- 因果推論の入門（『効果検証入門』安井翔太）: 「相関と因果」を実務語で説明できるようになる
- 機械学習の基礎（scikit-learn で一巡 → 評価指標の設計に重心）

**10年視点**
- LLM 時代でも「オフライン評価ハーネスの設計」「指標のハック耐性」「再現性」は普遍。むしろ AI の出力品質を測る evals 設計として需要が急増している。本リポジトリの bot ハーネス＝ evals の原型、と捉えると接続が見える

## 5. セキュリティ視点（Sec）

### ① 実務で求められる視点

| 現場の問い | 背後にある概念 |
|---|---|
| 「クライアントから来る値のうち、信用してよいものは？」→ 答えは常に「ゼロ」 | サーバ権威・入力検証・信頼境界 |
| 「このレスポンス、知る必要のない情報まで返していないか？」 | 最小開示（need-to-know）・情報露出 |
| 「秘密情報（鍵・パスワード）は、コードと分離されているか？」 | シークレット管理・.env・リポジトリ履歴の汚染防止 |
| 「依存ライブラリの脆弱性、誰がいつ気づく仕組みか？」 | SCA・サプライチェーンセキュリティ |
| 「攻撃者になったつもりで、この機能の悪用シナリオを3つ言えるか？」 | 脅威モデリング（STRIDE） |

セキュリティは「専門家が後から監査するもの」ではなく、**設計時の習慣**。「入口で検証・出口で最小開示・秘密は分離」の3点だけでも、実務の事故の大半を防げる。

### ② このリポジトリでの実例

- seed 非露出（進行中 `run_record=null`）: 未来の乱数を予測できる情報を渡さない。ゲームでは seed-scum 防止だが、実務では「セッショントークンや内部IDの露出」と同型の**情報露出**問題
- OPEN-015 の未探索ノードマスク: サーバが「開示レベル」を制御し、クライアントに渡した時点で公開情報とみなす。**「フロントで隠す」は隠したことにならない**という原則の実践
- `Field(ge=0, le=2**32-1)` / `Query(ge=1, le=500)`: 入口検証。バリデーションはフレームワークの宣言で書くと漏れない
- CORS を許可オリジン列挙に限定・`.env` 分離: least privilege と秘密情報管理の最小形

### ③ 学習ロードマップ

**今すぐ（〜半年）**
- **OWASP Top 10** を「名前を知っている」から「自分のコードのどこが該当しうるか言える」へ。各項目を本リポジトリに当てはめてみる（SQLi → SQLAlchemy 経由だから？ XSS → React のエスケープは何を守り何を守らない？）
- GitHub の **Dependabot / secret scanning** を自分のリポジトリで有効化する（5分でできる実務スキル）
- 「git 履歴に一度入れた秘密は消せない（漏れたら即ローテーション）」を原則として体に入れる

**1〜2年**
- 認証・認可: セッション vs JWT、**OAuth 2.0 / OIDC** の登場人物（このゲームに「ユーザーログイン」を足すとしたら？を設計練習に）
- 脅威モデリング（STRIDE）を1機能に対してやってみる——「攻撃者の目」を持つ訓練として最も費用対効果が高い
- 書籍: **『安全なウェブサイトの作り方』（IPA・無料）** → 『Webセキュリティ実践入門（徳丸本）』。資格なら情報処理安全確保支援士は日本の実務で通用する地図

**10年視点**
- ゼロトラスト（境界防御からの転換）、サプライチェーン（SBOM / SLSA）、そして **AI システムのセキュリティ**（プロンプトインジェクション＝「入力検証と信頼境界」の新しい顔）。原則は変わらず「信頼境界を明確にし、境界を越える入力を検証する」——今回サーバ権威でやったことの延長線上にある

## 6. 共通: 学び方そのもののコツ

1. **「自分のプロジェクトに1個ずつ導入する」が最強の学習法。** 本を読み切ってから使うのではなく、章ごとにこのリポジトリへ適用する。CI を張る、Hypothesis でテストを1本書く、分析クエリを書く、Dependabot を入れる——すべて今日から着手できる
2. **5視点は別の職種ではなく、同じシステムを見る5つのレンズ。** 今回のリライトでも、1つの変更（例: `run_actions` 追加）が Dev（設計）・DE（スキーマ）・DS（分析可能性）・Ops（マイグレーション手順）・Sec（露出範囲）の全部に触れた。「自分は開発だから運用は関係ない」と切ると、設計の質が頭打ちになる
3. **語彙に投資する。** 「不変条件」「冪等性」「信頼境界」「エラーバジェット」——概念に名前が付くと、レビューで指摘でき、設計で先回りできるようになる。読書の価値の半分は語彙
4. **2年目→5年目の分水嶺は「なぜ」を書けるか。** コード・コミット・ADR・ポストモーテムに意図を残す習慣は、どの専門に進んでも土台になる

### このリポジトリを練習台にした演習課題（すぐ着手できる順）

| 演習 | 鍛えられる視点 |
|---|---|
| GitHub Actions で PR ごとに pytest + typecheck を回す CI を張る | Ops |
| run_records を pandas で読み、深度化前後のクリア率を区間付きで比較する | DS |
| Hypothesis で `generate_floor` のプロパティテストを1本追加する | Dev |
| run_actions から「死亡直前5ターンの行動分布」を集計するクエリを書く | DE |
| 「ユーザーログイン機能を足す」と仮定して STRIDE で脅威を列挙してみる | Sec |
