**フロア構成の正確な言い方**: ゲーム仕様としては**5フロア固定**。v1.4 で可変化されたのはフロア数ではなく**各フロア内の探索マップの深度**（row 数が 1F=2 〜 5F=6 の深度カーブ＋あみだくじ型接続のランタイム生成）。

## 1. 変遷タイムライン — 6つの時代

開発は性格の異なる6期に分かれる。理想的な順序で進んだわけではなく、**第3期の機能ラッシュのあとに監査で土台を立て直した（第4期）**——このジグザグ自体がこのプロジェクトの正直な記録であり、後述の Zenn ネタの核でもある。

### 第1期: 設計固め（リポジトリ作成前 〜 v1.0 / 6-23）`[正本反映済み]`

コードより先に設計書があった。changelog の v0.6〜v0.9 は初期実装コミット（6-22）以前の設計フェーズの記録（証跡: changelog v0.6〜v0.9 エントリに実装参照が一切なく、v0.8 で初めて「実装のための技術仕様を追加」とある）。この時点で確定していたもの:

- パーマデス／5フロア／ダメージ式（`attack × multiplier`）／確率開示の方針
  - **確率開示の正確な定義**: 内部確率値そのものは非表示（暗黙知型）。ただし後の「ディーラー調書」（第3期）は*プレイヤー自身が観測した頻度*を表示するもので、矛盾ではなく「真の確率は見せない・体験の統計は見せる」という2層構造
- **乱数アーキテクチャ（SFC32・用途別9独立ストリーム）と検証フレームワーク**（「強プレイのクリア率25〜40%」という合格帯を設計書に書いた）
- アンロック連鎖のハイブリッド型（多親=隣接2体／単親=1体）、ゲート保証の確率シフト型、ゴールド経済の二重ブレーキ
- v0.8: 技術スタック確定（React+TypeScript+Vite / Zustand / Tailwind / FastAPI / SQLite）
- v1.0（6-23）: データファイル（config/enemies/mods/floors.json＝全36体・6mod・5フロア）を機械検証パス済みで確定。**テーマ転換「地下に潜る→カジノタワーを登る」**（UI が下から上に登る Slay the Spire 型になったことに物語を追随させた）

> この期の特徴: 「数値は JSON が正本、GDD 本文の数表は要約」という**データ駆動の統治構造**が最初から敷かれていた。ただし「JSON が正本」という宣言だけでは「コードが本当にその JSON を読んでいるか」は保証されない——この穴は第6期に現実の事故として顕在化する（mods.json 死にデータ事件・§1 第6期）。

### 第3期: 機能ラッシュ — 「死んだ後が面白い」の作り込み（7-03〜7-05）`[正本反映済み]`

5本の feature ブランチを並行で走らせ統合した、純粋な機能開発期（統合は squash 前提のブランチ運用ではなくコンフリクトを手動解消しながらの merge——この反省が後の CONTRIBUTING「1テーマ=1ブランチ=1PR・squash merge」制定につながる）。

- **検死レポート＆リプレイシアター**: 致命ターンの反実仮想（「受けていれば生きていた」）＋全ターンリプレイ。反実仮想は「同一 seed・同一敵行動で、該当ターンの選択だけ差し替えて再解決」という条件付きの再計算（seed 決定論が前提）
- **ディーラー調書**: 自分が実際に見た敵行動の頻度統計。**Wilson 信頼区間**を「観測が少ない敵ほど目安の幅が広い」という UI 上の質感に翻訳
- **サイドベット「読み宣言」**: stream2 ロール再利用で**新規 RNG 消費ゼロ**（seed 再現性を壊さない工夫）
- **テル（行動の前兆）**: feature flag つき最小スコープ試作
- **演出基盤（juice foundation）**: ネオン・マーキー共通基盤、トランプ風カードモチーフ

> 8アイディア中5つを統合し、残り（Provably Fair 演出・悪魔の契約 mod・デイリーシード等）は「詳細仕様待ちで見送り」と明記。**採用と見送りを両方記録する**習慣がここで定着。

## 2. 導入した技術 — 導入順に、なぜその時だったか

「何を使ったか」より「**なぜその順番だったか**」に価値がある。導入の依存関係はほぼ一本の幹から生えている:

```
seed 決定論（SFC32×9ストリーム）─┬─ bot シミュレーション ─┬─ CRN（共通乱数）─ 統計検証パイプライン（Phase1〜3）
```

## 3. 導入しなかった技術 — 何を、なぜ、いつまで見送るか

不採用判断は2つの原則に貫かれている:
**(a) 新規インフラ・依存を増やさない最小フットプリント**、**(b) 移行容易性は設計で担保し、移行自体は今しない**。

不採用は永続の判断ではないため、**再検討トリガー**（この条件が来たら判断を見直す）を付す。

| 不採用技術 | 採用した代替 | 理由 | 再検討トリガー |
|---|---|---|---|
| **Redis**（セッション外部化） | SQLite WAL＋LRU＋アクションログ再生 | 新規インフラを増やさない。エンジンの純粋関数性で「seed＋操作列」から状態再構築できる | workers>1 が必要になった時／複数コンテナ運用／復元 latency が体感に響く同時接続数 |
| **GameState 全スナップショット**（永続化の対案） | アクションログ再生方式 | フィールド追加のたびに保存/復元コードの同期が必要で、将来の変更に追従しない | ラン内 action 数が増え再生 p95 が劣化した時（checkpoint snapshot 併用を検討） |
| **APScheduler**（周期タスク） | FastAPI lifespan + asyncio.create_task | 新規依存を増やさない最小フットプリント | 周期ジョブが増えて cron 式・分散実行・欠損リトライが必要になった時 |
| **Celery**（検死計算の非同期化） | BackgroundTasks＋同期直実行 | 計算量がミリ秒〜数百ms のため過剰設計 | 失われては困る重要処理を非同期化したくなった時（BackgroundTasks はプロセス終了で消える） |
| **PostgreSQL**（本番DB） | SQLite 先行＋SQLAlchemy 経由に統一 | ローカル設定ゼロ優先。「1行で移行できる」という初期の楽観表現は v1.2 で**撤回**（JSON 列・server_default・並行性差の検証が別途必要と明記） | 水平スケール／複数 writer／DB locked 頻発 |
| **TanStack Query** | `gameApi.ts` に fetch を1ファイル集約 | 現時点の API 数では不要。将来の移行点を1箇所に限定する設計だけ先に敷いた | エンドポイント数・キャッシュ要件・楽観更新の需要が増えた時 |
| **ruff format**（自動フォーマッタ） | lint のみ（line-length 100 に緩和） | 一括リフローが `git blame` を破壊する。安全な自動修正（未使用 import 整理等）のみ適用 | 大規模リファクタで blame が既に切れるタイミング |
| **coverage 閾値ゲート** | 計測・可視化のみ＋不変条件テスト必須 | **Goodhart 回避**: 全体カバレッジという統計指標を最適化目標にしない。品質はリスクベースのゲート（不変条件・バランス回帰・契約テスト）で守る | —（哲学であり数値条件で覆さない。ゲート漏れの事故が起きたら個別テストを足す） |
| **mypy strict 全面化** | モジュール単位 overrides で段階厳格化 | エンジンが Optional 状態機械設計で、narrowing なしアクセスをテストで保護。実行時 assert 追加（＝ロジック変更）なしには解消できない | エンジンの状態機械を型で表現し直すリファクタ時 |
| **E501/UP045/UP047/B905 の即時適用** | TODO つき ignore | E501 の93件は主に日本語コメント（全角幅）。UP045 は56件が機能価値ゼロの差分 | 各 TODO の専用 PR（段階導入計画に記載済み） |
| **B008（呼び出しデフォルト引数）** | 恒久 ignore | FastAPI の `Depends()` イディオムはこのフレームワークでは正しい書き方 | —（恒久） |
| **10本目の RNG ストリーム**（フェーズB用） | stream6（旧 stance 予約枠）を接続生成へ転用 | 「9本の独立ストリーム」不変条件を維持 | フェーズB（スタンス）実装時に OPEN-006 で設計 |
| **チャートライブラリ（recharts 等）** | 未導入 | 親アイディア（検死カーブ描画）自体が未実装 | 検死レポートのグラフ化を実装する時 |
| **改善アイディア4/6/7/8**（Provably Fair 演出・悪魔の契約・juiciness 拡張・デイリーシード） | 見送り（記録は残す） | 詳細仕様待ち | 各アイディアの仕様が書けた時（proposals に残存） |
| **docs-ci の path フィルタ** | 常時実行（意図的例外）`[未マージ]` | check_docs.py は docs⇄コードの二辺比較のため、paths だとスクリプトが読むファイル一覧との**二重管理**になり追随漏れが再発 | check_docs.py の実行時間が CI の律速になった時（まず検査単位の高速化、フィルタは最後の手段） |

**A-1. 「AI に仕様を壊されないために — 個人開発に spec-first と変更クラス分類を入れた話」**
- 対象読者: Claude Code / Copilot で個人開発している人
- 読者の悩み: AI に任せると仕様が勝手に変わる・docs が腐る・main が荒れる
- 持ち帰り: 変更クラス S/F/R/B/D の表・「ついで仕様変更禁止」・AI 提案も S クラス扱い・保護ファイル制・squash merge で試行錯誤をブランチに閉じる運用
- 構成: 事故（または事故りかけ）の具体例→変更クラス表→PR 運用→効果と限界。CONTRIBUTING を貼るだけでなく「なぜその規約が生まれたか」の物語で運ぶ

**A-2. 「設計書を腐らせない — docs と API のズレを CI で落とす」**
- 対象読者: 設計書を書いても腐らせてしまう人・AI 生成 docs の管理に悩む人
- 読者の悩み: docs はあるが信用できない。どこが最新か分からない
- 持ち帰り: 最小例（FastAPI routes⇄契約表の AST 突合）から始めて schemas ミラー→「path フィルタは二重管理」の考察→CI YAML へと段階的に。**「CI で完全に防げる」とは書かない**——意味的齟齬は人間レビューの領分、という線引きまでが持ち帰り
- 材料: 完備（check_docs.py 11検査＋docs-ci.yml）

**A-3. 「既存 Python プロジェクトに ruff と mypy を後入れする現実解 — 216件を一気に直さない」**
- 対象読者: 動いている Python プロジェクトに静的解析を後付けしたい人
- 読者の悩み: 一括適用すると差分が爆発し blame が壊れ、チームが疲弊する
- 持ち帰り: ベースライン計測→捨てるルール/後回しルールの判断基準（E501=日本語コメント問題・B008=フレームワークイディオム・UP045=機能価値ゼロ差分）→ ruff format を使わない判断（blame 保全）→ mypy overrides で状態機械設計と共存。pyproject 断片つき
- 注意: linter 宗教戦争にしない。「チームが疲弊しない導入」が主題

**A-4. 「AI レビューの指摘は仮説として扱う — 実は docs が古いだけだった8つの『重大欠落』」**
- 対象読者: AI レビュー導入を検討している人
- 読者の悩み: AI の指摘が正しいのか判断できない
- 持ち帰り: 「指摘は仮説、裁定は実体との突合」という運用。指摘8項目が実は実装済み（docs が古いだけ）だった実例＝**AI レビューは docs の鮮度検査としても機能する**という発見
- 注意: 「AI が間違っていた」と見せすぎると AI 批判記事として消費され本質がズレる。公開時はレビュー原文の扱い（モデル名・引用範囲）を整理してから

**A-5. 「カバレッジ閾値ではなく、不変条件テストで守る CI 設計」**
- 対象読者: テスト文化・CI 設計に関心のあるエンジニア
- 読者の悩み: カバレッジ90%なのにバグが出る／数値ゲートが形骸化する
- 持ち帰り: 「全体カバレッジ閾値なし・ただし不変条件テストとバランス回帰ゲートは必須」というリスクベースの品質ゲート設計
- 注意: 冒頭で「品質ゲートなし、ではない」と明記（coverage 不要論に誤読されやすいテーマ）。短めのオピニオン記事向き

### 系統B: ゲーム検証編（尖って深く刺さる順）

**B-1. 「ゲームバランス調整は『同じ seed 同士』で比べると差が見える — CRN 入門」**
- 対象読者: バランス調整が勘と手作業になっているゲーム開発者
- 読者の悩み: 「調整の効果があったのか」をラン数を無限に増やさず確かめたい
- 持ち帰り: 乱数が違うと比較がブレる→同一 seed 集合で介入前後を対にする（CRN）→対応のある二値比較（McNemar は最後に紹介する程度に抑える）。統計用語を入口に置かない
- 材料: 完備（v1.10 の G1 セット選定・7案比較）。「N=1000 で数 pt の差が見えた」は本プロジェクトの条件下の実測として書く（一般化しない）

**B-2. 「『取ると弱くなるスキル』を統計で見つけたら、設定ファイルが読まれていないバグまで見つかった」**
- 対象読者: B-1 の読者＋データサイエンス層
- 読者の悩み: スキルが多すぎて総当たり比較が破綻する・多重比較で偽発見だらけになる
- 持ち帰り: leave-one/two-out ablation・anytime-valid CI（途中で覗いても壊れない）・e-BH による FDR 制御。trap mod 検出→感度実験で「変化しない」異常→ハードコード発見→**修正後に**再実験して「数値では救えない」を実証→リワーク判断、という一連の流れ
- 山場: **検定パイプラインがバグ検知器になる**。強い題材ゆえに、公開前に時系列（バグ修正 PR #37 → 是正実験 PR #38）と数値を changelog と突合する fact-check 必須
- 新規性: e-value / anytime-valid CI をゲームバランスに適用した日本語事例としては珍しいはず（断定はしない）

**B-3. 「Redis なしでセッションを復元する — 小規模ゲームでアクションログ再生を選んだ理由」**
- 対象読者: FastAPI / 小規模個人開発でインフラを増やしたくない人
- 読者の悩み: プロセス再起動でセッションが飛ぶ。Redis を入れるほどでもない
- 持ち帰り: (seed, upgrades, 操作列) の純粋関数 → active_sessions 1テーブル＋再生関数。スナップショット方式との比較表。**冒頭に適用条件を明記**（単一ホスト・workers=1・短いラン長。外れたら Redis/checkpoint を再検討）
- 注意: 「本物のイベントソーシング」と言いすぎない（条件付きの最小形だから成立している）。小ネタ: run_id 衝突事件（v1.6）と二次回帰の顛末
- B-4 が前提編

**B-4. 「同じ seed で同じ結果を再現するために、乱数ストリームを9本に分けた」**
- 対象読者: ローグライク開発者・リプレイ/デイリーシード機能を作りたい人
- 読者の悩み: 機能追加のたびに乱数の消費順が変わりリプレイが壊れる
- 持ち帰り: 用途別独立ストリーム（機能追加が他の乱数列を汚染しない）・Python/TS 黄金テスト・決定論が可能にした3機能（検死の反実仮想「受けていれば生きていた」・サイドベットのロール再利用・アクションログ再生）
- 注意: 再現条件は「同一エンジン版・同一データの下で」と正確に書く。暗号用途ではない・Provably Fair ではない、も明記

**B-5. 「『ずっと防御』が最適解になるゲームを、数値ではなくルールで直した」**
- 対象読者: ゲームデザイナー・ゲーム AI 層
- 読者の悩み: 数値をいくら調整しても単調な最適解が消えない
- 持ち帰り: 支配戦略は数値圧縮でなくルール（ジャストガード＝情報を賭けに変える・重ねがけ減衰＝スパムの期待値を落とす）で殺す。dominance（盲受け−受けなし）と skill_expression（賢い受け−受けなし）という指標設計、9パラメータ組×3方策の感度分析で「全組合せで成立」を確認してから採用する手順
- 注意: 「常に損」は bot 方策条件下の結果。人間プレイでの体感は人間プレイテストで検証予定、と分けて書く
- 材料: 完備（proposals/guard_redesign.md §8）

**B-6. 「勝たないと成長しない設計をやめた理由 — climb-to-progress への ADR 更新」**
- 対象読者: ゲームデザイン層＋ADR 実践層
- 読者の悩み: メタ進行（周回報酬）の設計に正解がない・過去の判断理由が消える
- 持ち帰り: ADR-0004 でリスク（初クリアまで報酬ゼロ＝離脱点）を明示的に引き受けていた→外部レビューで同じ点を突かれた→引き受けていたリスクなので再設計判断が速かった、という ADR 運用の実利。階層比例獲得×乗数コスト＝周回耐性25倍の設計計算
- **公開条件: 実装・ADR supersede・バランス再検証の完了後**（決定だけの記事は説得力が弱い）。ただし意思決定の生ログは今のうちに残してある（2026-07-15_gameplay_review_decisions.md）——決定が熱いうちの記録が記事の鮮度になる

## 6. 総括 — この3週間の変遷が示すもの

1. **順序はおおむね思想通り、ズレは監査で補正した**: 「設計書→エンジン→bot 検証→UI」の原則は守られたが、機能ラッシュ（第3期）が土台整備（第4期）に先行するズレも起きた。重要なのは理想順序ではなく、**監査（健康診断・DevOps 監査・ギャップ監査）を定期的に入れてズレを検知し、まとめて是正するリズム**が機能したこと。ただし後追い監査は規模が大きくなるほどコストが跳ねる——今回は間に合ったが、今後は大型機能の前に軽量監査を挟むのが安全
2. **不採用の記録＋再検討トリガーが資産**: Redis・APScheduler・Celery・coverage 閾値・ruff format——「入れなかった理由」が changelog / docstring / pyproject コメントに残っているため、将来の再検討時に同じ議論を繰り返さない。本レポートで各判断に再検討トリガーを付し、判断の固定化も防ぐ
3. **検証装置への先行投資が二重に回収された**: 第1期の seed 決定論と bot ハーネスが、(a) 予定通りの用途（統計検証・検死リプレイ・セッション永続化）と、(b) 想定外の用途（感度実験の統計的異常からハードコードバグを検出）の両方で効いた。ただし検証装置は万能ではない——「JSON が正本」の宣言と「コードが JSON を読んでいるテスト」は別物だという教訓（mods.json 事件）も同時に得た
4. **ドキュメントは書くものではなく整合させるもの**: drift は必ず起きる前提で、機械検査（check_docs 11検査）・版統治（changelog 正本）・課題規律（OPEN-xxx）を敷いた。機械検査が届かない意味的齟齬は人間監査と外部 AI レビューで補う二段構え。**状態の線引き（完了/条件付き/決定済み未実装/未マージ）を曖昧にしないこと**が、この体制の次の規律である
