# 健康診断＆設計書準拠リライト 詳細レポート（v1.4）

> 2026-07-06 実施。対象: カジノタワー ローグライト（React + FastAPI モノレポ）。
> 読者想定: 2年目のSEが「次のステップアップ」として読める粒度で、各修正の **Why（何が問題だったか）** と **How（どう直したか）**、その背後にある**10年持つ一般原則**を書く。

## 0. 健康診断の結論（一致度サマリ）

設計書（docs/ 分割GDD v1.3）と実装を全域照合した結果:

- **コアの戦闘ロジックは設計書とほぼ完全一致**していた。ダメージ式（attack × multiplier）・ramp式・ゲート保証・phase状態機械・例外→HTTPマッピング・combat_log/RunRecord分離・生SQLゼロ・RNG 9ストリームの消費契約——設計の背骨は健全。
- 乖離は3種類に分類できた:
  1. **設計書の不変条件がコードで破れている**（最重要）: seed非露出（§17.3）と「HP0=ゲームオーバー」（OPEN-010）
  2. **設計書が「望ましい」と方針まで書いてあるのに未実装**: OPEN-012/013/015/016/017/019/020/021/024/025
  3. **コードが設計書より先行**: 検死リプレイ・ディーラー調書・サイドベット・テル試作が正本docs未反映。/health・CI も「未整備」と書かれたまま実在
- 本リライトで 1・2 をコードで解消し、3 を docs 側へ昇格させた。さらに提案書 `floor_depth_randomization.md`（フロア可変深度化＋あみだくじ型接続生成）をクラスS手順で正本化して実装した。

**変更していないもの**: 既存の数値バランス（config/enemies/mods の値）、SFC32 本体、combat_log/RunRecord 分離原則、behaviors weight 合計100。新規追加した数値（深度カーブ・depth_scaling）はすべて「叩き台・要デザイナーレビュー」コメント付き。

## 1. 運用視点（Ops）

### 何を直したか
| 修正 | Why | How |
|------|-----|-----|
| **Alembic 導入** | `create_all` はテーブルは作るが**既存テーブルに列を足せない**。スキーマを進化させる正規手段が無く、列追加のたびに「DBを消して作り直す」＝恒久強化・調書の実績データを失う運用だった | `0001_baseline`（現行スキーマ）＋`0002_telemetry`（列追加）の2段構成。SQLite の ALTER 制約に `render_as_batch=True`。既存DBは `stamp 0001 → upgrade head`。`create_all` と共存するため 0002 は存在チェック付き冪等にした |
| **ログ＋リクエストID** | 例外はクライアントへ返すだけで**サーバに何も残らず**、障害後の再現が「ユーザの記憶」頼みだった | `basicConfig`＋`X-Request-ID` ミドルウェア。4xx は WARNING、未処理500はスタックトレース付き ERROR。レスポンスヘッダのIDでログと突合できる |
| **.env.example / CORS 環境変数化** | 設定がコードに埋まっていると「別環境で立てる」の再現手順が口伝になる | `DATABASE_URL`/`ALLOWED_ORIGINS`/`LOG_LEVEL` を環境変数化し、雛形を `.env.example` に固定 |
| **runbook の実手順化** | 「未整備」と書かれた骨子だけの runbook は、障害時に開いても何も得られない | 死活確認・ログ追跡・Alembic手順・SQLiteバックアップ・データ版切り戻しを実際に動く手順として記載 |
| **回帰基準の再生成手順の実行** | バランスに影響する変更を入れたら、回帰ゲートの基準も**同じコミットで**更新しないとCIが嘘をつく | `gen_baseline` を規定手順どおり実行し、基準変化（後述）を changelog と §18.2 に明記 |

### 2年目SEへ: ここで学ぶ一般原則
- **「動いている」と「運用できる」は別物**。今回のコードは全テスト緑で動いていたが、ログ・移行・設定分離が無い状態は「事故が起きた瞬間に詰む」構え。運用整備は機能追加より地味だが、個人開発でも**未来の自分という別人**のためにやる価値がある。
- **スキーマ移行は「必要になってから」では遅い**。最初の `ALTER TABLE` が必要になった日が導入日で、そのときには既に守るべきデータがある。マイグレーションは「変更の履歴をコードとして残す」文化であり、10年運用の背骨。
- **Windows の罠は実在する**（今回の実例: alembic.ini を configparser が cp932 で読むため、設定ファイルに全角文字・em-dash があるだけで全コマンドが死ぬ）。「環境差はCIで殺す」が原則だが、まず**壊れ方を記録しておく**（runbookに書いた）。

### 対応不要と判断したもの（過剰対策の回避）
- **APM/分散トレーシング・Docker化・ログ集約基盤**: 単一プロセス・単一プレイヤーのローカルアプリに対して費用対効果が合わない。`X-Request-ID`＋標準ログで十分。公開運用を始める時に再評価。
- **セッションの外部永続化（OPEN-007 のフル対応）**: rng 状態を含む全直列化が必要で工数大。docs も「仕様: 再起動で消える」と明記済み。まず遊ばれてから。

## 2. 開発視点（Dev）

### 何を直したか
| 修正 | Why | How |
|------|-----|-----|
| **不変条件の回復（OPEN-010）** | 「HP0=ゲームオーバー」という**ゲームの公理**が、相打ち勝利の1ケースだけ破れていた。不変条件の例外は、以降のすべての推論（UI表示・回復sinkの可否・統計）に「ただしHP0生存を除く」という但し書きを強制する | `combat_resolver` の判定部で勝利時 `hp = max(1, hp)`。**先に相打ちシナリオの失敗するテストを書き**、赤→緑を確認 |
| **異常系ガード4件（OPEN-016/017/019/021）** | 「効果ゼロの操作をサーバが受け付ける」のは、単なるバグ以上に**設計原則（§22.3: 効果0の操作はサーバが拒否）との矛盾**だった。UI非提示だけで守るのは、APIを直接叩けば破れる紙の壁 | すべて**サーバ側で 400**＋`available_actions` 非提示の二重化。テスト先行 |
| **テスト戦略の転換（フロア生成）** | 旧テストは「2Fは形A・GATEの親はB/C」と**特定の生成結果**を固定していた。ランダム生成に変えた瞬間に全部壊れる書き方 | 「多親=隣接2/単親=1/dead-end単親/全ノード到達可能/同一seed同一結果」という**不変条件（プロパティ）をseed横断で検証する**テストへ全面書き換え。生成器の中に `validate_floor()` を置き、テストが無い実行時にも同じ不変条件が守られるようにした |
| **契約の破れ修復（tell_reliability）** | エンジンは値を作っていたのに Pydantic スキーマに無く、**APIレスポンスで黙って消えていた**。フロントは「常にundefined」を読む＝誰も気づかない型契約の破れ | `BattleOut` にフィールド追加。教訓として「エンジンのsnapshotを直接見るテスト」だけでなく**API直列化を通したテスト**が要る（§25.5 の型共有はスキーマに書いた分しか守られない） |
| **lint 基盤** | `npm run lint` が定義されているのに eslint が未インストール＝「実行されないチェックは存在しないのと同じ」 | eslint flat config（typescript-eslint＋react-hooks）を導入し 0 errors に。hooks の依存配列チェックはReactの実バグ検出器として費用対効果が高い |

### 2年目SEへ: ここで学ぶ一般原則
- **不変条件駆動で考える**。このリポジトリの良さは「壊してはいけない不変条件」がCLAUDE.mdに列挙されていること。設計とは機能の列挙ではなく**成立し続ける性質の宣言**で、テストはその性質の実行可能な形。今回の書き換えの半分は「文章だった不変条件を、失敗できるテストに変換する」作業だった。
- **決め打ちテストとプロパティテストを使い分ける**。固定シナリオの決め打ちは読みやすいが、仕様の自由度（ランダム生成）を殺す。「何が変わってよくて、何が変わってはいけないか」を分離するのがテスト設計の本体。
- **ガードは提示層と実行層の両方に**。UIで隠すのはUX、サーバで拒否するのが契約。前者だけの防御は防御ではない。
- **構成的保証 > 事後検証**。あみだくじ格子は「生成してから検証して失敗したらリトライ」ではなく、**そもそも不変条件を破れない生成手順**（単調ステアケースの長さ2窓）を設計した。リトライループはデバッグ困難な確率的失敗を持ち込む。生成アルゴリズムを選ぶときは「正しさが構造から出る」形を第一候補に。

## 3. データエンジニア視点（DE）

### 何を直したか
| 修正 | Why | How |
|------|-----|-----|
| **data_version（OPEN-024）** | バランス数値は今後も変わる。**どの数値世代で生まれたレコードか**が無いと、改定を跨いだ統計は毒入りになる（平均クリア率が「いつのゲームの話か」不明になる） | 4つの正本JSONの内容 sha256（12hex）を `GameData.load()` で計算し、RunRecord 保存時に刻印。ファイル名やバージョン番号でなく**内容ハッシュ**なので、書き換え忘れが起きない |
| **strategy_version** | bot の方策改良も同型の統計汚染を起こす（「strong bot のクリア率」は方策の関数） | `bots.STRATEGY_VERSION` を保存。human は NULL＝「人間はバージョン管理できない」ことの明示 |
| **回数系テレメトリ（OPEN-025）** | `gold_spent`（金額合計）から使用回数は復元できない（単価がフロア係数と割引で変動するため）。ROI=回数×効果の分析が原理的に不可能だった | `sink_use_counts`・`gate_results`（per-floor）・`action_counts`（attack/guard/heal別）を記録。**集計後に情報を落とすな、落とすなら復元可能な形で**の実践 |
| **run_actions（操作履歴の全ラン永続化）** | 検死用の turn_history は「死んだランだけ」保存されていた。クリアランの履歴が無いと「勝ちパターンの分析」が永遠にできない | 終局時に全ランの turn_history を `run_actions` へ一括INSERT（ターン毎INSERTはしない=書き込み経路は1つ）。将来の検死フル化・デイリーシード比較の共通基盤 |
| **enum 正準化（OPEN-012）** | 統計のグループキーが日本語文字列だと、エンコーディング・表記ゆれ・国際化の全部で事故る | `grind/gamble/race/dodge/chaos` に正準化し、表示変換をフロントの1箇所（labels.ts）へ。**「保存する値」と「見せる文字列」の分離** |
| **旧データの扱い** | マイグレーションで旧行を書き換えると原本性が壊れる | 旧行は NULL のまま保持し、API層（to_dict）で既定値に丸める。日本語 experience の旧レコードは data_version で世代が分かれるため集計時に分離可能 |

### 2年目SEへ: ここで学ぶ一般原則
- **データには必ず「世代札」を付ける**。スキーマのバージョン（Alembic）と、**意味のバージョン**（data_version/strategy_version）は別物。後者を忘れると、スキーマは同じでも意味が違うレコードが混ざる。これは10年後、機械学習の学習データ管理でもまったく同じ問題として現れる（feature_version / model_version）。
- **「後で計算できるか」を保存時に自問する**。金額合計だけ保存して回数を捨てた瞬間、単価が変動する世界では回数は永遠に失われる。ストレージは安く、失われた情報は買い戻せない。
- **書き込み経路は絞る**。chips→gold_* の写しが1経路である設計（§0.3）は今回も守った。テレメトリ追加でも「_spend を通る」「終局時に1回」のように経路を集約すると、二重計上バグの入り口が減る。

## 4. データサイエンティスト視点（DS）

### 何を直したか / 何を守ったか
| 項目 | Why | How |
|------|-----|-----|
| **seed非露出の回復** | 進行中APIにseedが漏れていた＝同じSFC32実装があれば全ロールを事前計算でき、**「観測から学ぶ」という計測対象そのもの（暗黙知ゲーム）が成立しなくなる**。統計以前に、実験環境の汚染 | 進行中 `run_record=null`。非露出をスナップショットテストで恒久化（「二度と黙って壊れない」） |
| **決定論の維持** | 再現性はこのプロジェクトの実験基盤（CRN・黄金テスト・検死の反実仮想はすべて決定論の上に建っている） | トポロジー生成は未使用だった stream6 を転用し、**既存8本の消費契約を一切変えない**。バージョン内では同一seed→同一結果を維持（テストで担保） |
| **回帰ゲートの正しい運用** | フロア深度化＋heal 1ターン消費で maxed 強botクリアが **18/120 → 6/120** に低下した。これを「テストが落ちたから数値を調整して通す」と**Goodhartの罠**（指標が目標になる）に落ちる | 規定の承認手順（gen_baseline 再生成）で基準を更新し、**数値調整はしなかった**。「帯25〜40%に対して未達」という事実を §18.2 に明記してデザイナー判断へ回した。調整ノブ（depth・depth_scaling・回復経済・guard係数）も列挙済み |
| **検死・調書の統計的誠実さ（正本昇格分）** | 実装済み機能に良い性質があった: 調書は**自分の観測頻度のみ**をWilson区間つきで見せ（真のweightは非開示）、検死は決定論rolloutの**実測**を返す | この「実測と推定を混ぜない」「開示不変条件を守る」性質を api_contract/data_model に明文化し、劣化を防ぐ |
| **分析可能性の底上げ** | 上記DEのテレメトリ群 | guard使用率の推移・sink ROI・per-floorゲート結果・（run_actionsから）行動系列分析が版フィルタ付きで可能になった |

### 2年目SEへ: ここで学ぶ一般原則
- **計測系は「合格条件」であって「最適化目標」ではない**（CLAUDE.md の Goodhart 回避）。CIの回帰ゲートが赤くなったとき、取れる行動は3つ——(1)バグなら直す、(2)意図的変更なら基準を更新して記録する、(3)**指標に合わせてゲームを歪めるのは選ばない**。今回は(2)を選び、価値判断は人間に返した。
- **再現性は機能である**。「同一seed→同一結果」はテストの都合ではなく、反実仮想（もしガードしていれば）を**事実として**提示できるプロダクト価値の源泉。乱数を触る変更では「どのストリームを何回消費するか」を仕様として扱う。
- **観測データと真値を混ぜない**。調書がWilson CIを表示するのは飾りではなく「n が小さいうちは断定しない」という統計的態度のUI化。10年後どんなダッシュボードを作るときも、点推定だけ見せる誘惑に抵抗すること。

## 5. セキュリティ視点（Sec）

### 何を直したか
| 修正 | Why | How |
|------|-----|-----|
| **seed非露出（再掲・最重要）** | ゲームにおける seed は**秘密情報**（サーバ権威の根拠）。漏れれば全乱数が予測可能＝チート可能。「情報の非対称性が商品」のゲームでは機密性そのものが仕様 | 終端のみ開示＋テストで固定。**秘密は「出さない」だけでなく「出していないことを継続的に検証する」** |
| **情報開示の最小権限化（OPEN-015）** | L3情報（敵名・最大HP）が未探索ノードにも送出されていた。UIが表示していなくても**レスポンスに載った時点で開示済み**（DevToolsで見える） | `_node_view` を state 別マスクに。need-to-know をサーバ側で施行。なお `catalog/enemies` は id/name/experience のみで weight を含まず、マスクの抜け道にならないことも確認済み |
| **入力検証** | `seed` は範囲外を暗黙丸め（&MASK）、`limit` は上限なし＝全件取得可能。今は実害が小さくても、**入口で契約を明示しない API は将来の攻撃面** | Pydantic `Field(ge=0, le=2^32-1)`・`Query(ge=1, le=500)`。不正入力は 422 で入口拒否 |
| **CORS の最小化** | `allow_origins=["*"]` は「どのサイトからでも叩いてよい」という宣言。credentials無しでもポートフォリオ公開時に不要な面を晒す | 既定を Vite dev の2オリジンに限定し、公開時は `ALLOWED_ORIGINS` で明示。**デフォルトを安全側に** |
| **エラー情報の制御** | 未処理500がそのまま伝播するとスタックトレース等の内部情報が漏れる恐れ | 500 は固定メッセージを返し、詳細はサーバログにのみ残す |
| **乱数の用途分離（確認）** | — | SFC32はゲーム再現専用、session_id は `uuid4`、seed生成は `secrets.randbits`。決定論RNGを秘密生成に使っていないことを監査で確認（§17.1どおり・変更不要） |

### 2年目SEへ: ここで学ぶ一般原則
- **セキュリティ＝認証・暗号だけではない**。今回やったのは「情報フロー制御」——何をいつ誰に見せるかをサーバが施行すること。ゲームの開示レベル設計（L1〜L4）は、業務システムの権限設計と同じ問題。**クライアントに送った情報は全て開示済み**という原則は10年変わらない。
- **賢いクライアントを信用しない**。`available_actions` に出さない＝防御ではない。すべての防御はサーバ側の 400/409 が本体で、UIは体験のための飾り。
- **対応不要の判断も書く**: 認証・レート制限・冪等キー（OPEN-026）は単一プレイヤー・ローカル前提では**非スコープが正しい**。ただし「公開する日」が来たら必須になる項目として docs に残してある。やらない理由を文書化するのも security work。

## 6. フロア可変深度化＋あみだくじ生成（今回最大の機能変更）

- **何を**: 2F以降の接続を floors.json の静的データからランタイム生成へ転換。深度カーブ 1F=2行（固定）→ 5F=6行。幅2〜3の格子で分岐/合流。敵は統合プールから袋方式（枯渇時のみ重複解禁）。深いrowほどHP/goldに乗算傾斜。
- **Why**: 「フロアごとに2〜3回の3択」に収束していた探索を、道中ずっと続く選択に変える（柱①）。接続の記憶ではなく敵の手筋読み（柱③）へ学習軸を寄せる意図的トレードオフ（提案書 §2）。
- **How（技術的な要点）**:
  - 不変条件（多親=隣接2/単親=1/dead-end単親/GATE経路≥2/全ノード到達可能）を**生成手順そのものが保証**する「単調ステアケースの長さ2窓」方式
  - 乱数は予約枠 stream6 の転用で **9本不変条件と既存ストリームの消費契約を無傷**に
  - `validate_floor()` が生成のたびに全不変条件を機械検証（テストが無い本番実行でも守られる）
  - エンジン側（node_state/select_node/gate）は元々 row 数非依存の汎用実装だったため**無改修**（提案書の事前調査どおり）。UI の TreeCanvas も動的レイアウト済みで無改修
- **残る宿題（デザイナー判断）**: クリア率が maxed 6/120 に低下。深度カーブ・depth_scaling（現在 +10%/row）・回復経済の再調整が Phase1 前に必要（§18.2 注記）。

## 7. 対応不要・要人間判断リスト（明示）

## 8. 10年後を見据えて（次の一手の地図）

1. **PostgreSQL 移行は「1行」ではないが、道は舗装済み**: 接続は session.py の DATABASE_URL に集約、生SQLゼロ、Alembic 導入済み。移行日の作業は「dialect差異の検証（JSON列・server_default）＋データ移送」に縮んだ。
2. **テレメトリは資産になる**: data_version/strategy_version 付きの RunRecord と run_actions は、そのまま「バランス調整の実験ログ」。人間データが貯まれば、検死レポートのフルビジョン（WinModel勝率カーブ・反実仮想分岐）や bot方策の教師データに直結する。**今日のスキーマ設計が10年後の分析可能性を決める**。
3. **不変条件のテスト化は複利で効く**: 今回テストにした性質（seed非露出・HP0禁止・格子不変条件・weight合計100）は、今後どんな機能を足しても「黙って壊れない」。新機能のたびに「この機能が壊しうる不変条件はどれか」を最初に問う習慣が、リグレッションの総量を決める。
4. **「提案→クラスS昇格→実装」の統治は回っている**: floor_depth_randomization が実例。アイディアをいきなり実装せず、正本に仕様として起こしてから書く流れは、チームが2人・10人になっても壊れないプロセスの原型。
5. **次に効く一手（優先順）**: ①OPEN-018+バランス再調整（ゲームの手触りが決まる） ②人間プレイデータの収集開始（テレメトリが揃った今がスタートライン） ③エラーbodyの構造化（OPEN-026の一部・ErrorToastの分岐が賢くなる） ④pending の TypedDict/判別共用体化（dict[str, Any] の残りの緩さ）。
