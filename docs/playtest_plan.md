# 人間プレイテスト計画（Playtest Plan）

> 本書は [operations.md](operations.md) §18.6（人間プレイテスト計画）を実施可能な計画へ具体化したものである（v1.9 新設・デザイナーレビュー 2026-07-11 反映）。位置づけ・Goodhart 回避の原則は §18.6・§18.4 の記述を継承し、本書はそれを上書きしない。

## 1. 目的

bot シミュレーション（§18.1〜§18.5）は、クリア率・スキル幅・mod 寄与・sink ROI など**統計的に測れるもの**には強い。一方で、以下は bot では原理的に測れない。

- ルールを理解できたか（L1〜L4 の情報開示・guard/attack の2択・sink の使いどころ）
- 選択に納得できたか、死亡を理不尽と感じなかったか
- もう一度遊びたいと思えたか
- UI 上で重要情報を見落としていないか（frontend_design.md §28.7 の優先度設計が機能しているか）

本テストはこれら**理解度・納得感・再挑戦意欲**を検証する。

## 2. 位置づけ

- §18.6 のとおり、**Phase1（クリア率帯確定）の後**に実施する最小構成のテストである。深度カーブ・depth_scaling 等の数値調整（§18.2・OPEN-030・[balance_model.md](balance_model.md)）が済んでいない状態でテストしても、体験の悪さが「未調整の数値」由来か「設計そのもの」由来か切り分けられないため。
- **Goodhart 回避（§18.4 準拠）**：本テストの結果は合格/不合格の閾値を持たない。観測結果は**デザイナーの判断材料**であり、最適化目標ではない。「〇%が理不尽と回答したら失格」のような機械的な合否判定は設けない。
- bot によるバランス検証全体が「bot の人間代表性」という前提に依存している（§18.1 注記）。本テストはこの前提を裏取りする役割も兼ねる。

## 3. 対象者区分・人数（叩き台）

§18.6 の「3〜5人（ローグライト経験者2以上＋未経験1以上）」を3区分へ再配分する。人数は叩き台であり、最終確定はデザイナー。

| 区分 | 人数（叩き台） | 選定基準 |
|---|:---:|---|
| ローグライト経験者 | 2 | Slay the Spire / Balatro / Dicey Dungeons 等のノード選択＋ビルド構築型を経験済み（PRD §27.1 Primary 層に相当） |
| 確率ゲーム経験者 | 1〜2 | ローグライトは未経験だが、ポーカー・麻雀・TCGドラフト等で確率・期待値判断に慣れている |
| 初見 | 1 | ローグライトも確率ゲームも未経験 |
| 合計 | 4〜5人 | 各3ラン以上（§18.6） |

## 4. 実施手順

1. **環境準備**
   - `backend/`: `uvicorn main:app --reload`（`.env` は本番相当にせず開発既定でよい）
   - `frontend/`: `npm run dev`
   - テスト期間中は `backend/app/data/*.json` を変更しない（§5 の data_version 固定のため）
   - seed は指定せず `POST /run/new` に任せてよい（未指定ならサーバがランダム生成）。同一被験者に同一 seed を強制する必要はない
2. **観察**
   - 被験者はテスターの補助なしで UI を操作する。テスターは画面を横から観察し、詰まった箇所・迷った箇所をメモする
   - プレイ中は極力介入しない（発見型チュートリアル §14.1 の前提を壊さないため、操作方法を教えない）
   - 各被験者につき3ラン以上（死亡/クリア問わず）を目安とする
3. **ヒアリング**
   - 全ラン終了後、§7 の質問例を用いた半構造化インタビューを行う
   - 死亡ラン後は可能な範囲で検死レポート（§15.2）・調書（§15.3）画面を見せながら振り返る

## 5. 記録方法

- 被験者は通常の UI から `POST /run/new` を叩く。UI クライアントは `bot_type` を送出しない規約（api_contract.md §25.2）のため、RunRecord には `bot_type=human` として記録される。
- 統計比較は **`data_version` を固定した状態**で行う（4JSON の sha256 短縮ハッシュ・data_model.md §19.1）。テスト期間中に `app/data/*.json` を変更すると `data_version` が変わり、セッション間の比較ができなくなるため、テスト完了までデータ変更を凍結する。
- 収集元は RunRecord（`GET /api/stats/history`）に加え、死亡ランは検死レポート（`GET /api/run/{id}/postmortem`。戦闘死のみ、ゲート死は404）、プレイ全体を通じては調書（`GET /api/profile/dossier`）も参照可能。

## 6. 観察項目表

| 観点 | 見ること |
|---|---|
| 理解 | L2（体験タイプアイコン・強敵表示）を見て行動を変えているか／guard と attack の使い分けを理解しているか／sink（scout・heal・gate_guarantee・attack_boost）の使いどころが分かっているか（§14.3 の「初回5分で理解させること」の達成確認） |
| 意思決定 | ノード選択の理由を説明できるか／ゲート保証の重ねがけ（§7.4）を使うか・その根拠／攻撃ブーストと回復のどちらを選ぶか（§13.2 の2戦略） |
| 納得感 | 死亡時に理不尽と感じたか／検死レポート（回避不能・回避可能・相打ち勝利のいずれか）を見て納得が変わったか／ゲート死（検死対象外）への反応（PRD §3.1 の担保確認） |
| UI | 自分の HP・敵の次行動の危険予兆・`available_actions` を見落としていないか／未インタラクト敵の「賭博者」表示（§5 L3マスク）に混乱しないか（frontend_design.md §28.7 の優先度検証） |
| 再挑戦 | 死亡後すぐ次のランを始めたか（PRD §27.3「リトライ10秒以内」の体感確認）／調書・検死を見返したか／「もう一度遊びたい」と自発的に言ったか |

## 7. 質問例

1. 死因は理解できましたか？
2. 次に改善できそうだと思いましたか？
3. 一番悩んだ選択はどこですか？
4. チップを使うタイミングは分かりましたか？
5. もう一度遊びたいですか？
6. （死因理解の深掘り）検死レポート・調書は見ましたか？見た場合、見る前と後で死因の納得感は変わりましたか？
7. （チップ使用の深掘り）スカウト・回復・攻撃ブースト・ゲート保証は、それぞれどんな場面で使いましたか？使わなかったものがあれば理由も聞く

## 8. 記録テンプレート

被験者・ランごとに以下を記録する。

```
日時：
被験者区分：ローグライト経験者 / 確率ゲーム経験者 / 初見
run_id：
data_version：
結果：cleared / dead（floor_reached: ）
観察メモ（詰まった画面・迷った選択）：
Q1〜Q7 回答：
テスターの所感（デザイナー判断材料としてのメモ。合否判定はしない）：
```
